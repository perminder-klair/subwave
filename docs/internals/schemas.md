# Internals: shared zod schemas and the `/settings` patch registry

Why validation is split the way it is between `controller/src/schemas/`, the
generated web mirror, `settings.update()` and the route middleware. The short
invariants are in the root `CLAUDE.md`; read the matching section here before
converting another shape or "simplifying" a validator.

Two themes run through all of it. First, **the mirror is a hard constraint**:
`web/lib/schemas.generated.ts` is concatenated and compiled in the browser
build, so a mirrored module may import only `zod` and may not reference a
sibling. Second, **a conversion must preserve behaviour byte-for-byte** —
the hand-rolled branches carry accidental leniency (five numeric coercion
families, four string families) and tightening any of it is a behaviour change
that belongs in its own PR.

Covers: the mirror mechanism, stations/shows/schedule conversions, the
`/settings` patch registry, what deliberately did not convert and why, and the
public-vs-operator validation split.

- **Shared form schemas (zod)**: a validated shape is defined ONCE in `controller/src/schemas/<feature>.ts` and mirrored into `web/lib/schemas.generated.ts` by `npm run gen:schemas`, with `lint.yml` regenerating + `git diff --exit-code`ing it — same mechanism as the theme-token mirror, and for the same reason (the web package can't import `controller/src` at build time: separate package, separate Docker build context). **Files under `src/schemas/` may import ONLY from `zod`** — enforced twice, by a `no-restricted-imports` rule in `controller/eslint.config.mjs` (the merge gate) and by `gen-schemas.ts` itself at generate time (which also catches `export … from`, a module reference no import check sees), because the file is copied verbatim into the browser bundle and has to resolve in the WEB build. Rules that aren't pure functions of one value go in a `*-server.ts` sibling, which is NOT mirrored: for webhooks that's the `authHeader: 'set'` redaction sentinel (needs the existing list) and `resolveWebhookIds` — id minting (a side effect) plus cross-item de-duplication (needs sibling awareness). Never hand-edit the generated mirror. **Both the strict and the lenient path run the schema**: `validate*Strict` throws, `normalize*` repairs-or-drops and never throws, but neither restates a rule — see `controller/CLAUDE.md`. `middleware/validate.ts`'s `validateBody()` runs the schema at the route boundary and returns `{ error, fieldErrors }` — `error` is the flat string every existing client already reads from a 400, `fieldErrors` is keyed by dotted path (`webhooks.1.url`), which is also react-hook-form's `setError` syntax, so a server-only rule lands on the right input. **It does NOT replace `settings.update()`'s validation** — `update()` is reached by backup import and onboarding too and stays the authoritative chokepoint, so `validate*Strict` keeps its name and signature and calls the same schema. Web forms bind via `lib/form.ts`'s `useZodForm`. The react-hook-form half now covers the **entity editors** — TakeoverCard, Festivals, Moods, Skills, Blocklist, the seven imaging create/import modals, the onboarding wizard, Personas (+ its persona/prompt card files), Shows, Playlist Builder, alongside webhooks/stations — with the bound field components (`TextField`/`TextareaField`/`SelectField`/`SwitchField`/`ToggleGroupField`) living in `web/lib/form-fields.tsx` beside `form.ts`. The nine `settings/` sections stay on their pre-existing **per-control save** instead — there is no single submit to bind a `useZodForm` to: `SettingsPanel` owns one hydrate-once lifecycle shared by all nine, and each panel's `SaveBar` commits one setting at a time rather than a whole-form submit — which is also why **16 of the `/settings` patch registry's 42 keys still resist a stateless schema and stay hand-rolled** (see the patch-registry bullet below): their rules read POST-MERGE state (`llm`/`tts`/`embedding`'s cross-field clamps), depend on an open runtime-discovered map (`skills.enabled`), or fork on which keys ride in THIS patch (`djPrompt`/`activeDjPromptId`) — none of which a stateless `useZodForm` resolver, bound once per render, can express. There is deliberately **no `ui/form.tsx`**: shadcn's `Field` primitives are already vendored and `FieldError` already takes react-hook-form's `{ message }` shape (this now also matches current upstream shadcn, which ships no `form.tsx` of its own either). Converted so far: **webhooks** (#1323), **stations**, **shows**, **skills**, **playlists**, **imaging**, **onboarding probes**, the **public request boxes** (#1337 — `schemas/request.ts` homes `REQUEST_TEXT_MAX`/`REQUEST_NAME_MAX`, `request-guard.ts`'s name cap is an alias, and every skin's box runs the mirrored schema pre-flight through the ONE `PlayerCore.submitRequest` action rather than per-skin; over-cap text/name now refuse instead of silently truncating) the **schedule** and the first slice of the **`/settings` patch registry** (#1348, see below) — which closed imaging's half-conversion by putting its toggles (`jingleRatio`, `beds`, `sfx`) on the schema alongside the create/upload bodies #1337 had already converted. **A mirrored module may not import another mirrored module** — the mirror is one flat concatenation and `gen-schemas.ts` rejects every specifier but `zod`, so each schema module stands alone; a constant two features share is homed in the first one converted and re-exported (that's why `SHOW_ID_RE` lives in `schemas/show.ts` and `settings/vocab.ts`'s `ID_RE` is an alias of it).
- **Stations on the shared schema** (#1337): `schemas/station.ts` owns `STATION_ID_RE`, `MAX_STATIONS` and **`slugifyStationName`** — `stations/pure.ts` re-exports all three, so no call site moved. Moving slugify is the point: `StationsPanel` carried a hand-copied reimplementation for its slug preview and it had already drifted, omitting the `STATION_ID_RE.test(slug) ? slug : 'station'` fallback, so a name of pure punctuation previewed blank and then arrived as `/station`. Never reintroduce a local copy. Stations have **no `settings.update()` and no `validate*Strict`/`normalize*` pair** — the chokepoint is `manager.createStation`/`renameStation`, which run the same schema `validateBody()` runs at the route, because a route is not the only way in. Two deliberate tightenings, both replacing a **silent repair**: an over-80-char name is rejected rather than `.slice(0, 80)`d, and an unrecognised `mode` is rejected rather than coerced to `fresh` by `mode === 'duplicate' ? … : …` (silently building an EMPTY station when the operator asked for a copy is the expensive direction); `renameStation` likewise no longer falls back to the station's own slug on a blank name. The server-only rules sit in `station-server.ts`: `uniqueStationId` (takes the existing entry NAMES, not a root path — the `existsSync` check it replaced also saw `active.json`, so pass every entry, not just directories) and `stationCapMessage` — the cap is what `webhooksSchema` states inline as `.max(WEBHOOKS_LIMIT)`, and it can't live in the station schema for the same reason it can there, since POST /stations submits ONE station and the rack it joins is known only to the server. **`StationCreateError.field` is the `fieldErrors` channel** — carried as a property, never recovered downstream by matching the message text — and it is set only for a failure a field can fix: `mode` for "no active station to duplicate from" (the operator's way out is to pick Fresh), and deliberately **nothing** for a full rack, because no value typed in the create dialog resolves it. This is the form that finally exercises `applyServerFieldErrors`, which #1323 left wired but structurally unreachable; confirmed in a browser, not assumed — the payload lands on the mode radiogroup, the name input stays valid, and the id in `aria-describedby` is really in the DOM. Pinned by `scripts/station-schema.test.ts`.
- **Shows on the shared schema** (#1337): the first shape that **cannot be validated against itself** — the host must name a real persona, `moods` a live mood, `themeId` an installed theme, and `maxTrackSeconds` clears the crossfade-derived floor — so `schemas/show.ts` exports a **factory**, `showSchema(ctx)`, and those four inputs travel as ONE `ShowSchemaContext` that is never unpacked into per-field arguments (the shape the old four-parameter `validateShowsStrict(raw, personas, allowedThemeIds, moodNames)` grew into; same rule as `PickerScope`). **Three context fields are nullable and null always means "this caller cannot check that rule"** — that is how the strict save path and the lenient load path share one schema without either restating a rule: load runs before the mood cache exists (`moodNames: null`), has no theme registry (`themeIds: null`), and clamps to the hard bounds rather than the floor (`minTrackSeconds: null`). `personaIds` is deliberately NOT nullable — a show whose host doesn't exist has no owner on either path (strict throws, lenient drops the row: same rule, different consequence, which is the split that's allowed). Three route/validator callers run it, plus the browser: `validateShowsStrict`, `normalizeShows`, and `POST /shows` via **`validateBodyAsync`** (new in `middleware/validate.ts` — a schema that can't exist until the request does; a resolver that throws yields 500, not 400, because failing to READ the context is not the operator's input being bad). **The legacy-singular refusal (#929's `mood`/`genre`/`energy`/`fromYear`/`toYear`/`maxTrackMinutes`) lives INSIDE the schema, before the object**, and must stay there: `z.object` strips unknown keys, so the first version — a pre-check in `validateShowsStrict` — left `POST /shows` silently dropping a legacy `mood` and answering 200, which is the exact silent loss the refusal exists to prevent. The lenient path never trips it (`migrateLegacyShowFields` folds and deletes those keys first) — that split was the operator's call, on the understanding that a backup restore is the one caller meeting old data, which is why the message names the fields and the recovery. Two things are deliberately NOT tightened the way webhooks were: **booleans stay `=== true`** (both paths already agreed, and tightening one would split them) and **a malformed id is re-minted, not rejected** (a show id is what every weekly-grid slot points at, so refusing one would turn a single bad id in a backup into a refusal to restore the station). Web-side this deleted **five** hand-copied mirrors — the caps in `shows/types.ts`, `hydrateShow`'s legacy coercion, and `showValid`, which now runs the real schema so the editor's badge and Save gate also catch a backwards era window, a sub-floor track cap and a guest who is also the host. `PLAYLISTS_MAX` covered both playlist caps and is now two constants. Pinned by `scripts/show-schema.test.ts`; `show-filter-cap`/`playlists-cap` kept their behavioural half and now assert the UI *derives* its caps rather than scraping a literal out of the file.
- **Schedule on the shared schema** (#1337): `schemas/schedule.ts` owns the weekly grid AND the timed takeover (#930) — `SCHEDULE_DAYS`/`SCHEDULE_HOURS`, `emptyWeek`, `OVERRIDE_MIN_MINUTES`/`OVERRIDE_MAX_MINUTES` and the `ScheduleOverride` shape, all re-exported by `settings/vocab.ts` so no call site moved. **The takeover target is nullable and the two nulls are different things** (#1507): `showId: null` INSIDE the override is Default programming — a live, timed takeover that suppresses the weekly grid so the station runs autonomous music under the selected active persona — while an outer `scheduleOverride: null` means there is no takeover at all. Both must survive a round trip distinctly, which is why the strict path, the lenient load and the patch registry (`scheduleOverrideSchema(…).nullable()`) all carry the same union, and why the roster integrity sweep in `update()` clears a dangling STRING target without touching a null one. **Every reader asks through `takeoverShowId()` / `isDefaultTakeover()`, exported from the same module** — the target is three-way, not two-way (a show, Default programming, or something that names neither), and the two obvious inline spellings disagree about that third case: `showId === null` reads a malformed target as a show pin, `typeof showId === 'string'` reads it as Default programming. Both are wrong — pre-#1507 a target naming nothing real simply voided the takeover — and with the question inlined at nine call sites across the resolver, the sweep, the janitor, the programme span, the route and both admin screens, the two spellings had already drifted apart inside one PR. Never reintroduce an inline `showId` test; the predicates take a loose `{ showId?: unknown }` precisely so the route's request body and the admin form's submitted values can ask the same way a stored override does. Like shows it is a **factory** (`scheduleSchema(ctx)`), and its one nullable context field carries **three** postures rather than two: strict (`update()`, unknown show THROWS), lenient (load, unknown show is blanked by `repairScheduleForLoad`), and the ROUTE — `PUT /schedule` runs the schema with `showIds: null` for SHAPE only, then resolves ids through the pure `resolveScheduleSlots`, which **drops and counts** rather than rejecting. That third posture must never become a schema rule: the editor can hold a locally-added show the operator hasn't saved yet, so the route deliberately answers 200 with `dropped`. Two deliberate tightenings: a day present but not exactly 24 entries is now refused at the route (it was silently padded, while `validateScheduleStrict` behind `update()` had always refused it — so the two disagreed about the same data), and an empty `showId` on `POST /schedule/override` 400s instead of reaching the roster lookup and 404ing as `no such show: `. Expiry is the one rule the two paths don't share and it rides the context as `now` (load passes a clock and drops an expired pin; `update()` passes `null`, because a window that has merely run out is not the operator's input being wrong). Web-side this deleted `TakeoverCard`'s hand-copied `MIN_MINUTES`/`MAX_MINUTES` pair — it carried a "Mirror the controller" comment, the surest sign of a constant about to drift — and the bare `7`/`24` literals scattered through `schedule/lib.ts`. Pinned by `scripts/schedule-schema.test.ts`.
- **The `/settings` patch registry** (#1348, split out of #1337): `POST /settings` is the one body that is a **partial patch over 42 top-level keys**, not an object, so there is no single schema to hand `validateBody` — one over the whole settings object would `z.object`-strip whatever a form learns to send next. `settings/patch-registry.ts` is the frame instead: `SETTINGS_PATCH_KEYS` (every key `update()` acts on, **in branch order**), `SETTINGS_PATCH_SCHEMAS` (the converted subset), `parseSettingsPatchKey()` (strict, used INSIDE `update()`, throws a plain `Error`) and `validateSettingsPatch()` (route posture, via `middleware/validate.ts`'s `validateSettingsBody()`, returns `{error, fieldErrors}`) — the same schema on both, which is what finally gives the dozen panels posting here the `fieldErrors` channel #1323 built. Converting a key is ONE edit: add its schema to the registry and switch its branch to `parseSettingsPatchKey`; the other 39 keep their hand-rolled branches, so the frame lands without a flag day. Branch order is load-bearing twice — `update()` applies moods before the orphan guard and personas before shows before schedule, and the route iterating the same order means it names the SAME first failure rather than a second opinion that depends on JSON key order. **Unknown top-level keys are rejected at the ROUTE and never inside `update()`**: `routes/backup.ts` hands `update()` a whole backup `settings.json`, so a key from a newer version must cost one setting, not the entire restore — the same reason unknown fields INSIDE a block are dropped rather than refused. The flat `error` string is the zod message **verbatim** — the one place that bypasses `firstMessage`, because every message here is custom and already names its full dotted field, so prefixing would read `crossSec: beds.crossSec must be …`; that invariant is enforced structurally (hostile values thrown at every registered schema) rather than trusted. **26 of the 42 keys are converted, at zero behaviour change**, and that fidelity is most of the work: the branches carry accidental leniency the obvious conversion silently removes. **FIVE numeric coercion families** are in play and reusing the wrong one changes behaviour in one direction or the other — `parseInt` (truncates a float, reads leading digits from junk), `parseFloat`, `Number` (refuses `'10abc'`, but `''`/`null`/`[]` are 0 — the opposite of parseInt on both counts), `Number`+`floor`, and `Number`+`round` where the round runs BEFORE the bounds test, so `likes.maxTracks: 0.6` is accepted as 1 while `0.4` is refused and `25.4` is accepted while `25.5` is refused. Plus **FOUR string families**: `String(x)` with no trim (`search.apiKey` stores `'null'` for null), `String(x).trim()`, `String(x ?? '').trim()` (scrobble — null CLEARS the field), and a `typeof` check that refuses (`search.baseUrl` only, where `scrobble.listenbrainz.baseUrl` with the same message tail coerces instead). Each has its own helper and they are deliberately NOT unified. Also verbatim: `ui.skin` is DROPPED when it doesn't match rather than refused (and `String(null)` is `'null'`, which matches the slug pattern and is stored today), `weather.locationName` ignores a non-string or blank so the label can never be blanked while `onAirLocation` accepts `''` to reset its fallback, an emptied `station` resolves to the product default and that resolution can itself flip the restart flag, `archive.retentionDays`' message keeps its EN DASH (U+2013), and the `'set'` redaction sentinel guards ONLY the secret fields — a username of literally `set` has always been stored as such. Tightening any of these is defensible (webhooks did exactly that in #1337) but it is a behaviour change and belongs in a PR that says so, never smuggled in with a conversion. Constants moved into `schemas/settings.ts` and re-exported from `vocab.ts`/`defaults.ts` per the "first feature converted owns it" rule — the three bitrate vocabularies, `LOUDNESS_SOURCES`, `SEARCH_PROVIDERS`, the mood vocabulary and limits, and the crossfade/loudness/beds/jingle bounds (which deleted `BedsSection`'s bare `60`/`15`). The **mood family** (`moods`, `moodSchedule`, `weatherMoods`, `festivals`) is the first FACTORY entry — `SettingsPatchContext.moodNames` is nullable and null means "this caller cannot check that rule", so the route validates SHAPE only (it cannot know the effective vocabulary, which depends on whether `moods` rides in the same body) and `update()` checks membership against the same-patch list. `validateMoodsStrict` and its three siblings are now thin wrappers over those schemas, so the rules live once. Pinned by `scripts/settings-patch-schema.test.ts` (61 tests) plus the pre-existing `scripts/moods.test.ts`, which exercises the old validator API against the new implementation.
- **What deliberately did NOT convert, and why** (#1348): six keys resist a stateless schema, and the reason is the same each time — the rule is a function of state the patch does not contain. **`llm`**: all eight clamps (`clampNumCtx`, `clampAgentTimeout`, `clampNoRepeatWindow`, …) fall back to the **CURRENT stored value** on a wrong type, `applyInlineKey` is a set/delete against a `keys` map that is never in the patch (and `''` DELETES a credential), `applyLlmLegPatch` re-derives `baseUrl` from `providerBaseUrls` on **every** call including an empty one, and the "openai-compatible needs baseUrl" refusal is a whole-object invariant that can fire on a patch mentioning neither field. **`tts`**: six cross-field rules read POST-MERGE state — `cloud.voice`'s allow-empty depends on the effective provider, the apiKey clear compares against the PRE-patch provider, `fish-audio` clears the key unconditionally, and `fallback` merges over the stored slot before validating. **`embedding`**: `providerBaseUrls` merges into the existing map with delete-on-empty, `baseUrl` is a write-through into that map under a provider that may come from `llm`, and a re-derive runs on every update whether or not `embedding` was patched. **`skills`**: `enabled` is an intentionally OPEN map (the catalogue is discovered from disk at runtime and both the seeded and custom readings depend on it staying sparse), and disabling a skill WRITES into `next.personas`. **`requests`** and **`privacy`** are the two that converted PARTIALLY, and the split is instructive: their field rules are pure and live in the schema, while the state-dependent half stays in `update()` — `requests`' per-field fallback to the CURRENT value (the schema decides "usable or absent", the applier supplies the fallback, which is what keeps an emptied input from clamping to the field's floor and closing the request line) and `privacy`'s lock-needs-a-password invariant (it reads the MERGED state, so a lock turned on by this patch can be satisfied by a password already stored). Note `requests`' booleans are `typeof === 'boolean'` — a truthy non-boolean is IGNORED, the exact opposite of `ui`/`privacy`'s `!!`, and neither may be unified onto the other. Plus **`maxTrackSeconds`**, which is one branch over TWO keys with a precedence rule and a crossfade-derived floor, and the `djPrompt`/`activeDjPromptId`/`activePersonaId` trio, whose throw-vs-silent-repair fork keys on WHICH KEYS ARE IN THE PATCH rather than on any value. `personas`/`djPrompts` are convertible but need a `*-server.ts` sibling first: `mintId` is `randomBytes` and mirrored modules must stay side-effect free. None of this is a blocker for anything — each key keeps its hand-rolled branch and its exact behaviour, and the registry tolerates that by design.
- **`validatePublicBody` vs `validateBody`** (`middleware/validate.ts`): `POST /request` is the one LISTENER-facing form and mounts the public variant. Two differences, both about who reads the string. The message carries **no dotted-path prefix** — `firstMessage` prefixes unconditionally, which is right when an operator has to find `webhooks.1.url` among nine rows and wrong when a request box renders the text on its own, and routing `schemas/request.ts` through the operator middleware put `text: ` in front of every message on the wire while the browser (reading `issues[0].message`) saw them bare: one schema, two different strings. And the 400 also carries `success: false` + `message`, because the **native app posts `/request` directly with no pre-flight** and reads `data.message`; it ships through the app stores, so an already-installed build meets tomorrow's refusal and would otherwise render an empty failure card. Don't "simplify" the public route back onto `validateBody`.
