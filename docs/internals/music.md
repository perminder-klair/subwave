# Internals: music library, tagging and the picker

Why the library, tagging and track-selection code is shaped the way it is. The
short invariants are in the root `CLAUDE.md`; read the matching section here
before changing any of them — several record a measured property of a real
library (an 11k-track station) that is not obvious from the code.

Covers: Subsonic ingest, multi-value genres, scene consolidation, era-year
resolution, the similarity/embedding text, audio-mood calibration and propagated
energy, LLM provider wiring, the tagging stamp, library coverage, the
artist-variety guard, the album cooldown, full playlist rotation, minimum
track length, seed-vs-pick,
dead-air trim, festivals, listener request hardening, likes, and the blocklist
rules.

**Agentic Musical Leanings.** Discovery and guard re-picks receive no persona
preferences. A separate review keeps the discovered baseline by default. It can replace it
only when a supported preference advantage genuinely
settles a close or convincingly comparable possible-flow choice. Shared matches
(such as rock on both tracks) are compatibility, not a Leanings advantage.
The compact review exposes `leaningsAdvantages`, reserves evidence slots for
distinguishing preferences among close/possible-flow candidates, and runs the
model when a viable challenger exists and either holds an exact advantage or
some preference is open to interpretation — otherwise no answer could pass the
validator, so the call is skipped. Descriptive preferences may use a grounded
editorial comparison: exact quoted facts from both tracks, the active preference
and a genuine difference are checked in code. Three rules bound it
(`interpretableAgenticLeanings`, `EDITORIAL_LEANINGS_FIELDS`). The facts must
describe the music — genre, moods, Last.fm tags, instrumental — never year or
station history, which differ between almost any two tracks and so ground any
comparison. A phrase some track in the pool matches literally is one the tags
can carry, so a replacement claiming it needs the exact match. And while the
host has any preference, a guest phrase needs an exact match too. This verifies
the evidence, not the subjective musical judgement. Comparisons and their
evidence kind remain in review diagnostics.
Weak-flow matches cannot occupy the reserved evidence slots ahead of a viable challenger. Both routes join stored
Last.fm tags into private review copies of the baseline and candidates, after
initial selection; discovery payloads and the picker’s candidate map stay
unchanged. Including the baseline prevents shared tags earning false credit.
The private review receives up to 24 tags per track as evidence for interpretation.
The tags are existing library evidence, not a new Last.fm fetch. A station
with descriptive Leanings reviews more often, adding token use and latency;
there remains at most one review call per pick.
Both routes bound that review by the operator's existing `llm.agentTimeoutMs`
(45 seconds by default), covering retries and cancelling generation. A timed-out
review keeps the preliminary choice, logs its failure and cannot apply a late
replacement. The general request timeout still applies when it is shorter.
The final validator independently rejects a basis already supported by the
baseline, even if the model proposes a swap. Short genres such as jazz,
rock and soul are valid phrases. Parse each persona independently, including
noun-phrase fallback, then merge with the host owning duplicate phrases.
Leanings are positive-only (#1994): the review swaps only towards a phrase and
credits it as a "taste for" that phrase, so a sentence or clause that steers
away ("Avoids stadium rock", "…, never metal", "Does not favour…", "…, except
X") yields no phrase. It used to become one, through the noun-phrase fallback
when nothing positive sat beside it. A contrast, comma or "and" before a
trigger opens a new clause, so "Hates X, loves Y" keeps Y, unless the negation
before it is still waiting for its verb ("Never, ever enjoys…", "Doesn't,
frankly, enjoy…"). An item that names no taste ("anything", "all genres") goes
with whatever was excluded after it: "anything except metal" kept as
"anything" would be a taste that covers metal. Negation that qualifies a
preference keeps it ("records that are not overproduced", "dub with no
vocals"), but a qualifier with nothing before it ("…, with no metal") is an
exclusion. "no wave" is a genre, idioms of fondness ("can't get enough of",
"not least") are not negations, a capitalised name given as an example after
like / such as / including / especially / e.g. ("ska punk like No Doubt") is an
act, and the cue boundaries are Unicode-aware so "Noël" holds no "no". When
unsure the reader drops rather than risk a negative becoming a phrase, and a
list stops at its first negative item, so some losses are known, for example:
a Title Case name holding a cue word anywhere else ends its list ("Rancid, No
Doubt and The Specials" keeps only Rancid, "ska punk: No Doubt, Rancid" keeps
nothing); "warm but not twee indie pop" keeps only "warm"; a list of clauses
stops at its first negative one ("Loves soul, avoids metal, enjoys funk" keeps
only soul); and idioms that read as negation ("Can't stop playing Motown",
"Doesn't just love soul") yield nothing. Nor is the cue list complete the other
way: a verb it does not know ("Bans stadium rock"), "nothing" and "refused"
(each also a band), and an aside that ends on a noun ("Not in a million years,
enjoys metal") still leave a phrase. There is no negative channel: the review
prompt and its credit line speak only of preferences to swap towards, and the
Leanings-blind baseline would air an avoided track anyway, so a veto would
promise an exclusion it cannot keep. The persona editor says so and points
exclusions at show filters and the Library's Blocked (never play) rules.
Pinned by `scripts/leanings-negative-phrases.test.ts`.
`dj-agent/leanings-review.ts` owns extraction, source priority, evidence
validation and reason filtering. A viable host match, including the baseline,
excludes guest evidence; a guest can nudge only when no viable host match exists.
The displayed reason credits the actual preference owner. Operator history keeps
that reason, while `session.windowMessages()` removes preference claims before
selection or request speech reads it, including recovered legacy pick notes.
Replay calls copy active settings into temporary state before importing config,
so their telemetry cannot consume the station's token budget.

**Automatic ID-rotation recovery (#1699).** Pruning walks request a complete
Subsonic enumeration. A failed album fetch or malformed catalogue response
aborts the walk before adoption or pruning; already-upserted metadata may
remain, but existing tags and vectors survive and the automatic run can retry.
Other discovery/count callers retain their best-effort enumeration. A transient
empty manual reconcile still skips pruning and exits successfully. Automatic
recovery does not treat that exit as repair: it remains retryable unless its
confirmed legacy row has disappeared and the canonical row exists.

The child emits `[catalogue]` only after a nonempty authoritative walk finishes
adoption and pruning, before MusicBrainz enrichment. The controller first settles
the durable rotation journal, clears the picker and show-playlist caches, refreshes
playlist-rule membership, and rebuilds `auto.m3u`. An unchanged playlist ID is
not proof its member IDs survived the upgrade. Cache invalidation also prevents
older in-flight requests from refilling the cache. Reconcile completion waits
for the early refresh and retries it if needed before recipe sync; a full tag
run still rebuilds at exit because its later phases change the pool's moods.
Failed or deferred state migration keeps automatic recovery retryable.

- **Subsonic**: keep using `getAnnotatedUri` for anything going to Liquidsoap — raw URLs lose metadata until ID3 arrives, and the `on_metadata` hook needs `subsonic_id` for `/cover/:id` artwork.
- **Genres are multi-value**: `subsonic.songGenres(song)` is the single ingest normaliser (OpenSubsonic `genres: [{name}]` array → `string[]`, legacy scalar fallback). library.db stores `genres` as a JSON array; the scalar `genre` column is GENERATED (genres[0], indexable) — write `genres`, never `genre`. Matching is any-of via `show-filter.ts trackGenres/genreMatches`; LLM-facing shapes carry all tags comma-joined in the `genre` field. **Genre matching is one-directional**: a track's tag may REFINE the show's genre (a "Punk" show admits a `Punk Rock` track) but never broaden it (a "Pop Punk" show rejects a plain `Pop` track), and containment is word-boundary aligned so a "Rap" show doesn't pull `Trap`. The reverse direction is what let strict shows leak broad tags — don't reintroduce it. Note the resolver `subsonic.resolveGenreName` is still deliberately loose both ways: it maps free text to a real library tag for listener requests and server-side fetches, so a show whose genre isn't a library tag can still broaden there (see issue for the fetch-hint/match-target split).
- **Scene vocabulary (#1577)**: "scene" is what the Observatory calls a genre tag and the word the operator asked in terms of, so the consolidation tool uses it; the storage is `tracks.genres`. After a full pass a real catalogue carries near-duplicate spellings that each hold a handful of tracks, and the Tagging panel's **Scene vocabulary** section lists every distinct value with its count (`library-db/scenes.ts sceneVocabulary`, a `json_each` walk over the mirror — uncached and NOT scoped to tagged rows, since an untagged track's genre is as noisy as a tagged one's) and merges a ticked set into one survivor. **A merge is two halves and both are required**: the REWRITE (`db.mergeScenes`, one transaction over just the rows carrying a retired value — the dedupe and the order-preserving rewrite are done row-at-a-time in JS so they state the same rules `songGenres` applies at ingest, once, rather than twice in two languages; the scalar `genre` column is GENERATED so it follows, and a rewritten row with a text vector is marked `text_vector_dirty` because the genre line is in the embed text) and the durable RULE (`music/scene-vocab.ts`, `state/scene-aliases.json`, applied by `subsonic.songGenres`). **Without the rule the feature is a no-op within one cycle**: the mirror is rebuilt from Navidrome on every walk and `upsertTrackMeta` writes the walked genres over the stored ones, so a merge with no memory is undone by the next tag pass — which is the pass that produced the noise. `library.consolidateScenes` is where the two are paired, and it records the rule FIRST so a rolled-back rewrite still leaves the fold in place. The alias map is kept FLAT (a target that is itself retired resolves through; existing rules pointing at a source are repointed) so the lookup is one hop and a cycle cannot be stored — **except on a REVERSAL**, where the target resolves back onto a value this same merge is retiring: resolving through there cancels the merge against itself, every source drops out as a self-merge, and the operator gets a 200 naming the spelling they were trying to replace (#1580 review), so the typed target stands and the old rule is repointed instead. A rule's `from` is a fold KEY and its `to` a stored spelling, so **the two sides may look identical and still do work** ("rock" → "Rock" canonicalises every case and spacing variant); neither `planAliases` nor the file loader may drop a rule for reading like an identity, because that is exactly what a pure case merge is and dropping it let the next walk write the retired spelling straight back. For the same reason a source counts as "already the target" only when it matches VERBATIM — the case-insensitive test rewrote nothing on a case-only merge while reporting success. At the cap the OLDEST rule goes, never the one just recorded: a head slice discarded the new rule while its row rewrite still committed, which is a merge that unwinds at the next walk. The fold is case- and whitespace-insensitive but **never punctuation-insensitive** — "Hip Hop" and "Hip-Hop" are different labels and which survives is the operator's call, and folding them in the listing would hide the thing they came to fix. Sources match the EXACT stored value the operator ticked, so a rule can still be broader than the rewrite that came with it (an untickled case variant folds at the next walk rather than now) — that gap is the design, not a bug. The trim-and-dedupe both halves apply is `scene-vocab.dedupeScenes`, stated once and shared by `applyAliases` (ingest) and `mergeScenes` (rewrite). Loading is lazy and SYNCHRONOUS because `songGenres` runs in two processes (controller + tagger child) and a boot hook one of them forgets is a silently inert feature. This is post-hoc curation and touches nothing the tagger asks for, so `TAGGER_CONTRACT_VERSION` stays put. Forgetting a rule stops future folds and leaves the rewritten rows alone — several spellings became one, and which row had which is exactly what the merge discarded. Pinned by `scripts/scene-vocab.test.ts` (real SQLite: the generated column, the dedupe, the dirty-vector marking and the walk round trip would all pass a pure test while broken).

- **What a merge orphans, named before it runs (#1593)**: retiring a value is right — the operator asked for it — but a show genre filter, a never-play rule or a sync playlist's `knobs.genres` still naming the retired spelling then stops selecting it, with no error and no visible cause: the library is correct and the schedule quietly stops working. `music/scene-references.ts` scans those stores and `POST /library/scenes/references` answers the same question the merge will, from the same call, so the preview in the Scene vocabulary section and the merge response cannot disagree. **Naming the affected shows is the whole feature** — a generic "this may affect filters" is the non-advice the operator already assumed. **The orphan test is two questions asked at different strengths.** Does the filter value NAME the retired spelling (a MUTUAL match — each side covers the other, which under `genreMatches`' boundary containment can only happen when the two normalise equal), and does it still catch the survivor (asked ONE-WAY, the direction the pick paths ask it)? The asymmetry is the whole correctness of the thing: a `Punk` show CATCHES `Punk Rock` by refinement, so a one-way first question reported it orphaned on any merge moving punk rock elsewhere while every track tagged plain `Punk` still matched — that show has NARROWED, not broken, and narrowing happens on nearly every merge touching an overlapping genre, which is exactly the generic non-advice being replaced. So `rock` → `Rock`, `Hip-Hop` → `Hip Hop` and (against a `Punk` show) `Punk Rock` → `Post-Punk` or `Punk Rock` → `Downtempo` all produce no warning, while `trip-hop` → `Downtempo` against a `Trip Hop` show does. Both questions go through the predicate the matching side really runs, never a local comparison, and the target resolves through `planAliases` first so a typed target that is itself already retired is judged as the value that will really survive. **`tag` rules are scanned too, with their own predicate**: `field: 'tag'` matches `trackAllTags` (genres ∪ moods ∪ audio moods ∪ Last.fm tags) by `normText` EXACT, which folds case, whitespace and curly-vs-straight apostrophes (#1611) but NO other punctuation — so a `Trip-Hop` → `Trip Hop` merge is harmless to every genre filter and silences a tag rule spelled `trip-hop`, and a scan running one fold over both stores would call that merge harmless when it is not. The five remaining rule fields name values from vocabularies a genre merge cannot reach. **What is deliberately NOT established is that an orphaned filter matches nothing**: the value may still be caught by another spelling in the vocabulary, and a tag rule reaches three more namespaces, so answering would mean the `json_each` walk that `GET /library/scenes` is fetched-on-expand to avoid (#1570). `remaining` is therefore the rest of that filter's OWN list and the copy claims no more. It is a **warning only**: nothing blocks the merge and nothing rewrites the filter, because genre matching is one-directional and repointing a filter changes what the show MEANS. The blocking twin is `settings/validate.ts assertNoOrphanMoods`, which can refuse — a mood is a closed vocabulary, a genre filter is free text resolved against the library at pick time. Pinned by `scripts/scene-references.test.ts`.
- **Library coverage never counts on the read path (#1570)**: `GET /library/coverage` is polled by the admin Library page, and `coverage.total` comes from `subsonic.iterateAllSongs()` — a `getAlbum` call **per album**, so a few thousand sequential Navidrome requests on a 29k-track library. `library-coverage.get()` is therefore a pure read of the last-known count: it serves DB counts (`countTagged`, `analysedCount`, the vector tallies) plus whatever `total` the last scan found, stamped `scannedAt`. Only `refresh()` walks, and exactly three things call it — the operator's own `POST /library/coverage/refresh` (the panel's Count-library button), and the two ends of a tagger run, which is walking the catalogue anyway: at **start**, guarded on `hasCount()`, because a never-counted library has a null `total` that nulls every percentage on the panel and the hero meter would otherwise read "—" for the whole first run; and at **exit**, where the fresh figure lands. The GET deliberately carries **no `?refresh=1`**: counting is a command, and a read that can start a walk is the shape something eventually polls by accident. The trap this replaces was a 6h staleness check *inside* `get()`: opening the Library page after a controller restart, or six hours after the last visit, silently fired the whole walk, which is the shape the operator sees as "the page checks my library every time I open it". **A library reset is not a walker** — `POST /library/reset` deletes `library.db` and touches nothing in Navidrome, so the `total` a refresh would recompute is already correct; the refresh that used to sit there spent thousands of `getAlbum` calls on the one action an operator least expects to hit the music server. Because nothing recounts unattended any more, the count **persists** to `state/library-count.json` (`{version, total, scannedAt}`, written atomically, a missing or corrupt file reading as "never counted"). Without that, an in-memory cache would blank the total — and every percentage derived from it — on every controller restart, and `scannedAt` could never show an age older than process uptime, which is precisely the staleness the stamp exists to expose. `scanning` and `scanError` are deliberately NOT persisted: they describe this process's attempt, and a stored `scanning: true` from a killed container would spin forever. A **failed** count is recorded rather than only logged (`scanError` on the payload, rendered beside the total), because the scan is fire-and-forget behind a button whose only other feedback is the number appearing — silently failing reads to the operator as nothing having happened; a failed re-count keeps the previous total and its age rather than blanking the panel over a blip. The same reasoning governs the web side (`web/components/admin/library/LibraryContext.tsx`): the coverage query still runs on mount because the read is now cheap, but nothing puts it on a timer except a live tagging run (the % must visibly climb) and an in-flight count (`scanning`, watched at 3s until the new total lands). `total` being null is a first-class state — "not counted yet", not 100% and not an error — and the number always renders with its age, because it is the one figure on that panel that is not live. Pinned by `scripts/library-coverage.test.ts`.
- **Admin library reads stay off the wide rows (#1937)**: a `tracks` row carries kilobytes of analysis JSON (beat/bar grids, pace, structure, outro), so any full scan of it reads most of the file, which is ~2 GB at 150k tracks, synchronously on the controller's event loop. A Library page load ran several such scans, and the coverage poll repeated four of them every 3 s during a tagging run (measured 0.3 s per poll and 0.8 s per `stats()` on a desktop at 150k, several times that on NAS-class hardware), which is how `/health` came to wait 10 s behind them. Three rules keep these reads cheap. (1) **Every admin count reads an index, never the rows.** `ensureStatsIndexes()` builds them at open, outside the `user_version` chain: `idx_tracks_analysed`, `idx_tracks_vocal_measured`, `idx_tracks_fail_count` and the covering `idx_tracks_stats`. They are accelerators, not schema, so a failed build never fails `open()`: the first open after an upgrade builds them in whichever process gets there first, and a second opener (the tagger or analyzer child) would otherwise wait out the busy timeout on that build's write lock and throw. It warns instead, keeps what was built, and the next open retries; the counts stay exact meanwhile, just slower. Each build is a full scan on the opener's thread, so it logs how many are missing and then its elapsed time; every other open reads `sqlite_master` once and logs nothing. The vocal one is an EXPRESSION index over `vocal_ranges_json IS NOT NULL`, because a partial index keyed on some other column stopped being chosen once `ANALYZE` had run. The count SQL is spelled to match (`(vocal_ranges_json IS NOT NULL) = 1`, a bare `analyze_fail_count >= N`), and `computeStats()` reads the mirror total and the tagged totals as two reads so neither visits a wide row. (2) **An unchanged library is never recounted.** `stats()` and `library-coverage`'s DB counts are reused while `changeToken()` matches. That is the same token the Observatory ETag trusts, and it moves on a commit from any connection, the tagger child included. Coverage has no TTL, so it is never staler than a fresh read; `stats()` keeps its 5 s TTL as the floor, so it is never staler than before. `labelOnlyVectorCount()` stays outside the coverage snapshot because its own 5-minute TTL would otherwise be outlived by a snapshot held on an idle library. (3) **Browse pages ids, then reads the page.** `filter()` sorts `SELECT id` and fetches the ≤200 wide rows by id. `SELECT *` straight into an ORDER BY drags every matching row's JSON through the sorter: 1.1 s for a mid-library page at 150k, 0.17 s paged by id. Sidebar `<Link>` prefetch is not part of the problem: the admin pages are server components wrapping client panels that fetch on mount, so an RSC prefetch never reaches the controller. Pinned by `scripts/admin-library-reads.test.ts` (plans with and without `ANALYZE`, row-for-row equality with the original SQL, reuse and invalidation). `npm run bench:admin` reproduces the numbers.
- **Genre suggestions walk in slices and answer from the last walk (#1976)**: the Show editor's related-genre chips (`GET /library/genres/related`, `music/genre-suggest.ts`) average every embedded track's text vector per genre. No index covers that, because it reads one vec0 vector per track, and at 150k it took 3.2 s in one synchronous call. Its cache key (`stats().updatedAt` plus `vectorCount()`) moved with every tagger batch, so each open during a tagging run stalled every other request for ~3.6 s, and even an unchanged library paid ~25 ms per open for the `vectorCount()` in the key. Four rules. (1) **The walk yields.** `addGenreVectors()` reads tracks in rowid order until a 25 ms budget runs out, stops on a track boundary so no track is half-counted, and closes its statement before returning. `genreSuggest()` hands the event loop back between slices, and inside the pairwise genre pass, which is quadratic in the genre count. The tracks rowid range must drive the slice's outer loop: a plan that sorted would re-read the whole library on every slice's first step. (2) **A request waits on a changed library only once the last walk is past its max age.** Until then it gets the last result at once, and one walk re-reads behind it. The cache is keyed on the walk's own inputs (rule 4), so a library whose genres, tags and vectors are untouched is never re-walked, however old its walk and however long the station plays. A changed one is re-walked at most once per `GENRE_SUGGEST_REFRESH_FLOOR_MS` (60 s), counted from the walk's start, because a tagging run writes every batch. The max age (`GENRE_SUGGEST_MAX_AGE_MS`, 10 min, also counted from the walk's start) exists because answering from the last walk alone made its age a function of how often the editor is opened, not of time: an editor opened on Monday and next on Friday was served Monday's walk, without a week of tagging's genres or counts (#1991). Past it the request waits for the re-read, joining one already in flight. The walk yields between slices, so the wait costs that one request the walk's wall time (~0.4 s at 20k, linear in the embedded tracks) and every other request nothing. So suggestions are never more than the max age behind the library. A failed re-walk logs once, however many requests were waiting on it, answers them with the last result, and waits out the floor before the next attempt. The first walk on a handle has no last result and is always awaited. (3) **A reopened library never gets the old handle's result.** The cache and the in-flight walk are both keyed on the handle nonce, and a walk whose handle is swapped mid-way throws rather than mixing two libraries. A request that was waiting on that walk, first walk or past the max age, waits once more, on the new handle's walk, rather than answering 500, which leaves the editor with no chips at all. A second swap inside that wait fails the request: retrying is for a swap that has finished, not for chasing a library that keeps moving. The retry keys on the nonce, that is on a swap that has finished: during a restore's copy no handle is open yet, so a walk failing there is an ordinary failure (a first walk answers 500, a re-walk past the max age answers with the last result). The walk still reads `stats()` once, for the tagged count per genre, and reads it with the TTL skipped (`stats({ fresh: true })`): the payload is cached under the token read before the walk, so a TTL-held tally from before that token would be served to every open until the next write to its inputs. So a cold `stats()` (~0.4 s at 150k, the same read `/settings` and browse make) is the longest single block a walk can contain; its centroid slices stay near 30 ms. (4) **The change signal is the walk's inputs, never the library's commits** (`library-db/genre-inputs.ts`). The cache is keyed on `genreInputsToken()`: the handle nonce plus a one-row `genre_inputs.version`, read by primary key in one statement with a by-name lookup of its three triggers. Keyed on `changeToken()`, as #1976 first did, every aired track's `plays` row was a change, and with the max age a playing station would make every editor open after a ten-minute gap wait for a whole walk (~3 s at 150k) over genres that could not have moved. The version moves on every write to what the walk reads and on nothing else. SQLite triggers on `tracks` bump it on insert, on delete, and on an update that changes `id`, `genres` or `moods`. Any change of moods counts, not only tagged-ness, because the tagged test parses JSON and a trigger that throws fails the writer's statement rather than a read. Triggers fire for every connection, so the tagger and analyzer children and raw SQL are covered as much as this module. `track_vectors` is vec0, which takes no trigger, so every function that writes it calls `touchGenreInputs()` after the write, inside its transaction where it has one. A bump before the write could cache old vectors under the new version; one after can at worst cause an extra walk. The table and triggers sit outside the `user_version` chain and are re-ensured on every open, like `track_facet_status`, so a migration that rebuilds `tracks` (and drops its triggers with it) gets them back; a changed trigger needs a new name, since `IF NOT EXISTS` never replaces one. The ensure reads `sqlite_master` first and writes only what is missing, in one transaction: every process opens through it, and a write on every open (even an `INSERT OR IGNORE` that inserts nothing) takes the write lock, so a tagger or analyzer child opening while another connection is mid-write waited out the busy timeout and failed its `open()`. The ensure is fail-open, like `ensureStatsIndexes()`: an open that cannot put the table and triggers in place (an upgrade's first open while another connection writes for longer than the busy timeout) warns and finishes opening. Throwing was not the retry it looked like: `open()` sets the handle before `migrate()`, so the next `load()` found the handle set and skipped `migrate()`, and that process ran on without the table, every editor open answering 500 and every vector writer throwing after its write. So until an open has the table, its version row and all three triggers in place, the token falls back to `changeToken()` and a bump with no table to bump is a no-op: suggestions are re-walked more often, never frozen, and the next open retries. A missing trigger counts even with the table and row there, because a version nothing bumps would serve one walk forever. A migration that drops `tracks.genres` or `tracks.moods` must drop `genre_inputs_tracks_update` first: SQLite refuses to drop a column a trigger names. Plays, analysis results, audio vectors and mood labels, energy corrections, enrichment and an unchanged metadata resync leave it where it was. The write side costs about 5 µs per row whose genres change (20k such metadata upserts: ~1.67 s with the triggers, ~1.57 s without), and the vector bump is one single-row update per embed, inside the noise of a vec0 insert. Pinned by `scripts/genre-suggest.test.ts` (equivalence with the original single statement down to one-track slices, plans with and without `ANALYZE`, loop yields, floor, max age, single flight, tally freshness, failure, handle swap and its one retry, a playing station never waiting) and `scripts/genre-inputs.test.ts` (every write path that changes the walk's output moves the token, from a second connection too; the on-air writes do not; a source scan pairs every `track_vectors` write with a bump; a DB from before the table gets it, and a lone missing trigger is put back; an open that finds them in place takes no write lock; an open that cannot put them in place still opens, on the token that moves on every commit, whether the table or only a trigger is missing). `npm run bench:admin` reproduces the numbers.
- **Era years (#842)**: a track's era is judged by `show-filter.resolveEraYear`, never raw `year` — the resolved `original_year` wins (walk-time album `originalReleaseDate` on non-compilation albums; MusicBrainz phase-0 enrichment for compilation tracks), and a **compilation's plain `year` is untrusted** (it's the compilation's own release date, so unresolved comp tracks read as unknown-year and drop from era windows). SQL-side era filters (`library-db.filter` yearFrom/yearTo, seed decade bucketing) mirror the same precedence — keep JS and SQL in agreement. `music/musicbrainz.ts` is keyless but hard-throttled to 1 req/s with a descriptive User-Agent (MB policy) — don't widen it; misses are stamped (`original_year_checked_at`) so passes never re-query them. **Every listener-facing surface reads the RESOLVED year, never `song.year`** (#1418): the Liquidsoap annotation (`subsonic.getAnnotatedUri`), the DJ's "Now starting:" line (`llm/internal/prompts/scripts.ts` — this is what the station SAYS), the picker's slim projection (`picker/slim.ts`), and `/now-playing` (`routes/public.ts`, which is where the skins' year comes from — `now-playing.json` carries no year of its own, radio.liq writes title/artist/album/id only). Each had read the raw column, so a reissue anthology had the DJ announcing 2012 over a 1964 Stax single even when the era pipeline had resolved it. Unknown means the field is **omitted, not zeroed** — the same "leave it out rather than assert the wrong decade" rule the era filter follows. Admin surfaces (library table, playlist builder) deliberately keep the raw `year`: the operator is looking at the file. Signals: Navidrome's flag; a Various-Artists album artist; a record with **no lead artist at the front of it** (≥5 distinct *lead* artists, ≥8 tracks, top lead under 30%); a title that says it is a collection (short, specific word list); or a date range in the title that CLOSES before the album's year — the single-artist anthology no artist-count signal can see ("The Atco/Atlantic Singles 1968–1974" on a 2015 release). - **Tempo timing is octave-safe at consumption (#1417)**: `librosa.beat.beat_track` can return the DOUBLE on slow material; the measured failures were one-directional, with true 62–88 BPM tracks stored at 124–176. Attempts to choose the octave from onset alternation, `start_bpm` voting and tempogram harmonics did not separate real-audio positives from backbeat controls well enough to ship, so the analyser keeps its raw reading and does **not** force a library re-analysis. `music/mix.ts:timingBpm` instead folds readings at or above 110 downward by octaves before any single-track duration is derived. A true fast track remains musically aligned at half-time (every other beat); a genuine slow reading is never multiplied into a half-bar. The fold is shared by adaptive/ending/washout canvases, washout delay, loop length and chop period, while stored/display BPM, playlist filtering and embedding text remain untouched until an estimator is validated against a real corpus. **Every effect period reaches its audible window by HALVING, never by clamping** — the fix's own first cut clamped after folding, and because the clamp bound over the whole 110–160 band it returned a flat 0.75 s chop gate for the commonest tempi in a library (1.38 beats at 110 rising to 1.90 at 152), so the gate walked the grid and cut mid-note; the washout tap collapsed to a flat 0.45 s for every reading from 110 to 200 and stopped being a dotted eighth of anything. A clamped period is a number inside the window that is a subdivision of nothing. Halving also makes `chopPeriodFor`/`washoutDelayFor`/`loopBarFor` octave-invariant **at any tempo**, so they do not depend on the 110 line at all — only the bar-snapped canvases do, which is why a double landing below 110 (a true 52 read as 104) is left alone rather than guessed at. `scripts/mix-fx.test.ts` pins half/double invariance across every timing consumer AND the grid property itself — each period must be a power-of-two multiple of the raw beat, swept over 30–300 BPM. Equality between two readings alone does not pin this: two equally off-grid values compare equal, which is how the clamp regression passed its own invariance test.
- **Audio-mood calibration + propagated energy (#1362)**: CLAP cosines are **not comparable across moods** — each prompt sits at its own baseline in the shared space, so picking "this track's top-scoring moods" off raw cosines ranks PROMPTS, not tracks (measured on an 11k library: `energetic` fired on 61.7% of tracks and `rainy` on 43.5%, against `calm` 0.9% and `spiritual` 0.2% — a property of the vocabulary, not the music). `music/audio-calibration.ts` is the one place that fixes this: per-mood library-wide mean/sd → `z = (score - mean) / sd`, then the SAME relative top-K selection on the z axis (margin in **standard deviations**, `DEFAULT_MARGIN_SD`, not raw cosine — the old 0.05 has no meaning here). Baselines are computed from **every stored score map, library-wide**, never from a subset: a distribution built only from the tracks the tagger found hardest to read is a biased yardstick. Below `MIN_BASELINE_TRACKS` (200) selection falls back to raw and is byte-for-byte the pre-#1362 path — `topAudioMoods` is now a thin wrapper over `selectAudioMoods(scores, null)` and keeps its own unit test. **The floor is applied PER MOOD, by pruning, not by gating the set** (`prunedBaselines`, the one path `loadBaselines`/`runPropagatedEnergyPass` both take): per-mood `n` diverges — a mood added to the vocabulary since the last full re-score is only scored on tracks analysed after it — so an established mood can sit at n=5000 beside a new one at n=12, and gating on the MAXIMUM `n` (the original reading) let the thin one into the baselines, where its near-degenerate sd is restrained only by `MIN_SD` and its z explodes into a mood that wins every track: the exact #1362 failure, one mood at a time. Requiring EVERY mood to clear the floor is the wrong correction in the other direction — one new vocabulary entry would refuse calibration library-wide. Pruning keeps the library calibrated on its established moods and simply omits the thin one, which `centeredScores` already drops rather than passing raw. **A pass that could not calibrate stamps `UNCALIBRATED_VERSION` (0), never the real one** (`moodStateHashFor` — never call `composeMoodStateHash` from a pass): those labels came from the raw fallback, so the relabel is still owed, and stamping them as current is what made a station that started under the floor and grew past it keep its original tracks on raw selection forever while only post-crossing tracks were ever calibrated. 0 is deliberately the same value a legacy bare hash parses as, because it means the same thing. **The pass is three phases and the order is load-bearing**: score → compute baselines → derive labels. Labels cannot be picked during scoring, because on a full re-score the baselines are a property of the cosines being written by that very loop. A crash between phases leaves `audio_moods` NULL, which `idsNeedingAudioMoods` re-picks up, so the split is resumable rather than lossy. **`audio_embedding_meta.mood_vocab_hash` now carries TWO things joined by `:`** — the vocabulary hash and `CALIBRATION_VERSION` — because they invalidate different amounts of work: a vocabulary change means the *cosines* are stale (full CLAP re-score, needs the analyzer text tower), a calibration change means only the *labels* are (re-derive from disk, `relabelFromStoredScores`, no analyzer at all). Folding the version into the vocab hash instead would strand every install that doesn't run `ANALYZER_HEAVY` — which is most of them — on stale labels. A legacy bare hash parses as version 0, so an upgrade relabels rather than re-scoring. Composite string, so no schema migration. **Energy correction** (`music/propagated-energy.ts`): a `source = 'propagated'` energy is inherited from embedding neighbours, not judged from the track (41% of that library), and where the measured arousal axis — mean z of `HIGH_ENERGY_MOODS` minus mean z of `LOW_ENERGY_MOODS` — is decisive, it overrules the guess. **Deliberately two-sided, never a three-way bucketing**: `audioEnergy` returns `high`/`low`/**null**, and the ambiguous middle returning null is the whole design — bucketing it to `'medium'` would replace one guess with another and call it evidence, whereas null leaves the existing value alone, so a mis-tuned threshold costs coverage rather than correctness. Scope is `source = 'propagated'` ONLY (an `llm`/`manual`/`uncertain-llm` energy is a real per-track decision and is never touched), and the write is the `energy` column ALONE — source/confidence/moods stay as propagation left them, so a corrected row still reports honestly that its MOODS are inherited. The mood names couple this to the shipped vocabulary and moods are operator-editable, hence the degradation: whichever names survive are used, and fewer than 2 on either side yields null rather than a one-sided answer. Runs after `runAudioMoodPass` in `analyze.ts` AND at the end of the tagger's phase 3/4 — one shared path, because a library can gain audio scores long after it was tagged. `ENERGY_HIGH_Z`/`ENERGY_LOW_Z` (±0.35) and `DEFAULT_MARGIN_SD` are defensible starting points, **not measured optima** — they want a pass against a real library. Pinned by `scripts/audio-calibration.test.ts` (pure) + `scripts/propagated-energy.test.ts` (real SQLite; every query here is new SQL that pure tests would pass right through). Issue #1362's third proposal — weighting scores inside the strict `moodLock`/`energyLock` — is deliberately NOT done: those locks are hard with no never-starve on the agent path, so a continuous score there changes starvation behaviour on thin shows and needs its own spec.

With `llm.pauseWhenEmpty` the DJ stops picking whenever nobody listens and the station coasts on this file until the next rebuild, which the refresh cron (`AUTO_QUEUE_REFRESH_MINUTES`) runs at most an hour apart — on the reported station 22% of the show's plays. The boundary where the DJ stops also rebuilds it when it holds what the queue just aired, which a rotation's always does, since both pickers take the head of this file (#1975, `broadcast/coast-handover.ts`; see broadcast.md). (A stream idle pause, `stream.idleWhenEmpty`, is not that: it freezes the music chain, so nothing coasts while it holds.) The coast used to hard-filter the strict playlist through the station-wide `trackHours` window, and `take()`'s never-starve only fires on ZERO, so a show airing most of the day kept 2–5 tracks and Liquidsoap looped them (one track six times in an hour and forty minutes). An unknown length counts as nothing, so the miss is a longer file, never a shorter loop; the on-air and queued tracks are the last resort; and like every never-starve here it returns a fresh array. A prepared episode keeps its own coast. - **Minimum track length** (#1573): `settings.picker.minTrackLengthSeconds`, with a per-show `minTrackLengthSeconds` override beside `maxTrackSeconds`. **Default 0 = off**, so an upgrade picks byte-identically; a show's `null` means inherit and its `0` is an explicit opt-OUT of a station floor. Asked for by operators whose libraries are full of 40-second skits, interludes and album intros. **It is the CAP's mirror image, not another cap**, and the asymmetry is the whole design: `maxTrackSeconds` in the default `cut` mode is an on-air `liq_cue_out` cut, which is why `filterPickerCandidates` says in as many words that track length is *not* a selection criterion — an over-long track stays in the pool and simply crossfades out at the limit. A short track has no equivalent: it cannot be stretched, so the only place to act is the point of choice. Stamping the floor on the annotation beside `maxDurationSec`, or folding it into that comment's "length is not a selection criterion" rule, silently switches the feature off. **`music/track-floor.ts`** owns the policy — a module, not a branch, because the same decision is reached from four places — and takes the same `{ starve }` fork `show-filter.applyStrictLocks` does: **HARD** in the agent's discovery tools (`picker/scope.ts` `collect`, before the playlist lock so a pinned playlist's own interlude drops too), **never-starve** in the pool picker's final selection (`music/picker.ts`, applied to `selectionPool` before `filterPickerCandidates`) and in the auto.m3u coast (`broadcast/scheduler.ts`, beside the strict-playlist and blocklist blocks) — because those two ARE the dead-air scope the hard one falls back into, and "the station must keep making sound" outranks the floor (but never the opt-in hard ceiling). **An UNKNOWN length passes**: a partly-walked library has rows with no duration, and dropping those would turn a 60s floor into "play only what we happen to have measured"; a `0`/negative/non-finite duration reads as unknown, never as short. Length is read from BOTH field names (`duration` on a Subsonic child, `durationSec` on a library row) — `library.slimTrack`/`songsByMood` already project `durationSec` for the cap, and `library-db.candidateFilterTracks` gained it so the **show-editor candidate diagnostic applies the identical rule the pickers will** (it is NOT gated on `filtersStrict`, so it lands before the strict split and the funnel names it in a warning). `effectiveMinTrackSec` (`settings/persona.ts`) is the one resolver, twinned with `effectiveMaxTrackSec`. **Listener requests are exempt** — an explicit ask is not a pick, and the request scope simply never sets the field. **The key name is deliberately NOT `minTrackSeconds`**: that name is taken by the crossfade-derived floor (`settings/store.ts`, surfaced at `/settings.values.minTrackSeconds`) and means something else entirely — and it is this key's own lower bound, enforced in `update()` where the crossfade is known, on the same reasoning the cap uses (below 2× the crossfade a track gets no solo airtime at all, so a floor under it expresses nothing the mixer does not already impose). **That bound is empirical, not tidiness**: a track whose whole playable span is under the crossfade duration is swallowed by `cross`'s buffer and never airs — it leaves `dj_queue` without a sound and without an error, which is where a 15s stinger requested under an 18s crossfade goes (#1591). Requests are exempt from every length rule the controller owns, so that drop is the MIXER's and the controller cannot see it happen — the resolution probe reports `ready` for any readable file. It is warned about rather than prevented (#1594): `queue.push()` puts one `crossfade` booth-log line in front of the operator when a REQUEST's playable span is under the configured crossfade, and queues the track anyway. The rule lives in `liquidsoap/CLAUDE.md` beside the crossfade rule it belongs to. `0` always passes that check, which is what keeps an untouched station identical. `autoPlaylistShowKey` carries the field, since editing it on the live show changes which tracks the fallback may contain. Pinned by `scripts/track-floor.test.ts` (pure policy, resolver precedence, cold-load round trip, the crossfade bound, the diagnostic funnel, the aliasing contract below), `scripts/show-schema.test.ts` and `scripts/picker-lock-forwarding.test.ts`.

  Three things the first implementation got wrong, each worth keeping in view:

  - **A never-starve filter must never return its INPUT array.** `applyTrackFloor` and `applyStrictLocks` both answer "keep everything" by handing a pool straight back, and the auto.m3u coast rebuilds its pool *in place* (`pool.length = 0; pool.push(...kept)`) — so the rescue cleared the very array it was about to spread back in and wrote an empty `auto.m3u`, turning the last dead-air guard into dead air. Both functions now return a fresh array on every path, and `scheduler.refreshAutoPlaylistInner` funnels all four in-place replacements through one identity-guarded `replacePool` helper. The `applyStrictLocks` half was reachable before the floor existed: a strict show whose only genre resolves to no library tag runs zero lock steps.
  - **"How long is this track?" is answered in ONE place.** `track-floor.trackLengthSeconds` is it, and `recency.durationSeconds` (the cap's reader) delegates to it. It takes the first *usable* value, not the first present one — `duration ?? durationSec` reads a Subsonic child's unmeasured `duration: 0` as a real answer and ignores the library row's true `durationSec` beside it, so the track slips past the floor. The Playlist Builder's `filterByDurationBand` is a deliberate exception, documented at both ends: a recipe band on an operator tool, not a pick-path floor.
  - **Below the crossfade, a track cannot air at all — the lower bound is not a formality.** Measured on the dev stack with `crossfadeDuration: 18`: a 15-second track resolved, queued and reached `next.txt`, but Liquidsoap never took it into `dj_queue` and the reconcile sweep dropped it as stale — *with the floor switched off*, so nothing in this feature was involved. A 31-second track on the same station aired normally. That is the empirical case for `settings.minTrackSeconds()` (`max(30, 2 × crossfade)`) being this key's lower bound rather than a distinct name alone: a floor beneath it could only ever admit tracks the mixer already refuses. It also means an operator who wants 40-second skits gone has nothing to configure below 36s on a default station — those tracks were never going to air.
  - **The diagnostic's INPUT counts stay pre-floor.** `library.indexed` is the indexed library and `playlist.total` is the playlist — the show editor renders the latter as "Playlist anchor: N tracks", and a field labelled with what it counts has to keep counting it. The floor shows up as the drop to the steps below, plus a warning that names it and says the station still plays if it leaves nothing.
- **`artistRootKey` folds verified name variants, not just collaborations** (#1406): a leading article, exact full-name aliases, curly-vs-straight apostrophes and an in-name hyphen or dash (#1983). "The Jimi Hendrix Experience" straight into "Jimi Hendrix" walked past the guard because the keys differed, so the known catalogue forms map to one root. Ensemble suffixes are **not stripped generically**: "The Beta Band", "Manchester Orchestra" and "Kronos Quartet" are complete act names, and collapsing them onto Beta/Manchester/Kronos would feed a false equivalence into `blockedArtists`, which `filterPickerCandidates` treats as a hard drop. Add only a verified full-act alias. Normalisation never empties a key ("The Band" → `band`, "The The" → `the`), and article/alias handling runs AFTER the join split so the `X & the Y` exception still sees the tail it protects. The hyphen/dash fold is the one **generic** fold. A hyphen-minus (U+002D), hyphen (U+2010), non-breaking hyphen (U+2011), figure dash (U+2012) or en dash (U+2013) with a letter or digit on both sides is spelled as a space, so "SCSI-9"/"SCSI 9" (seen back to back on air), "Jay-Z"/"Jay Z" and "The-Dream"/"The Dream" each key as one act. Em dash and minus sign are out of scope, and " - " between credits, a leading or trailing dash, dots and "/" are left alone. It runs after the feat. and join splits, so a hyphen never moves where a credit splits. It runs before the article strip and the alias lookup, so "The-Dream" keys `dream`, and an alias key must be written in folded form. Because it follows the splits, a key can re-split when keyed again (`jay-and-silent-bob` → `jay`), so callers key the raw credit, never a key. It stays out of `nameKey`/`artistParticipantKeys`, so the never-play blocklist does not widen. It does reach `blockedArtists`, which the suffix rule above refuses. That is accepted here for two reasons. A suffix strip would collapse common, real act names onto other real names, while two different acts told apart only by a hyphen versus a space is vanishingly rare. And the hard drop lasts one rescue pool call and over-matches, the safe direction. Pinned by `scripts/artist-key-separators.test.ts`. Both pickers use `neighbourArtistRoots` for configured slot spacing and share this normalisation.
- **Spacing compares credits by overlap, not by equality, and names no separator**: music servers join several credited artists with whatever their scanner chose (Navidrome ` • `, others ` / `, `; `, `, `), so `Pixies • Black Francis` keyed as one act and aired right after `Pixies`. `recency.artistCreditsOverlap` treats any character that cannot be part of a name (anything but letters, digits, whitespace, apostrophe, period, hyphen, and the `&`/`+` that sit inside band names) as a boundary between acts, and two keys match when they are equal or one is a delimited act inside the other: `pixies` matches `black francis / pixies`, while `air` does not match `air supply` (a space alone joins one name). `artistRootIn` applies it over a key set. Used by the agent guard (`artistGuardCause`, `alternativeCandidates`), the album guard's re-pick set (`alternativeAlbumCandidates`) and by `filterPickerCandidates`' spacing and guard-rescue sets, which are preferences, so over-matching only means "pick someone else". **Not used by the blocklist**, which is a hard filter (see the next rule); word joins (`x`, `with`, `vs`) are not boundaries, since they sit inside names too. Pinned by `scripts/artist-credit-overlap.test.ts`.
- **Seed vs pick (#1247)**: every pick/request event message hands the agent a real discovery seed's `[id: …]` — the pick event uses the expected predecessor (the queued tail, or the on-air track when the queue is empty), while a request event uses the on-air track — and the discovery tools all EXCLUDE that seed from their own results (`library-db/vectors.ts` `knnByBuffer` drops `excludeId`), so that id is the one real, well-formed track id in the model's context that no tool returned. `util/pick-seed.ts` owns the one wording that says so (`SEED_NOT_A_PICK_CLAUSE`, shared by the pick + request schema `id` descriptions AND `picker-tools.ts`'s empty-result `rule`) — never inline a second copy, and don't weaken it to "never invent an id", which an echoed seed literally satisfies. The trigger is upstream: the harness allows exactly ONE discovery call (`COMMIT_AFTER_STEPS = 1`) before pinning `activeTools: ['done']`, so a seed tool that returns nothing corners the model with an empty `seen` — where BOTH salvage stages are structurally dead (`nearestId` has no keys, `repickFromSeen` returns null on its first line). Hence `buildPickerTools`'s cross-index rescue: `tracksLikeThis`/`tracksThatSoundLikeThis` answer from the OTHER index when the one asked holds no vector for this seed (gated on the primary matching *nothing* — an all-filtered-by-recency primary keeps its `emptyResult`), and it says which index answered so the model doesn't reason about audio neighbours on the text axis. A zero-candidate run does NOT count against the agent circuit breaker (`classifyPickFailure`) when at least one real discovery call ran (`toolCalls > 0`; `flattenToolCalls` excludes the synthetic `done`): the empty set proves this run cannot validate a pick, but does not by itself distinguish index coverage, active filters, an upstream miss, or recovery behaviour, so it is not evidence that the model cannot drive tool calls. Opening the breaker there would kill the session-aware picker for 10 min while advising "switch model". An empty `seen` with ZERO discovery calls means the model never explored (`no-discovery`), which is exactly the breaker's failure class and still counts.
- **Dead-air trim**: some rips carry seconds of silence before the music starts or after it ends, and on air that plays as dead air. The analyzer measures both edges against an **absolute** dBFS floor (`SILENCE_DBFS`, default -50) as `lead_silence_ms` / `tail_silence_ms` (+ `tail_start_ms`, the same tail measurement as an ABSOLUTE offset — a cue_out derived as `duration - gap` inherits every disagreement between the container tag and the decoded file, so the cut moves by whatever the header got wrong), and `music/silence-trim.ts` turns them into `liq_cue_in` / `liq_cue_out` — `radio.liq`'s existing `cue_cut` (added for the #447 length cap) does the cutting, so no mixer change was needed. **The absolute floor is the whole design.** The two measurements that already looked like the answer — `estimate_intro_ms` and `analyze_outro`'s wind-down — are RELATIVE gates gauged against the track's own loud level, which is the right question for "may the DJ still be talking" and the wrong one here: a quiet piano intro clears neither and is unambiguously music, so reusing them would cut into the record. Never wire a relative gate to a cue point. Three guards bound the damage, each for a different failure: the operator's `silenceTrim.minGapMs` floor (a track legitimately opens a beat after zero, and a segued album's inter-track space is deliberate), a fixed `MARGIN_MS` left in place at each edge (the measurement reports the first frame ABOVE the floor, so cutting exactly there lands on the attack), and a per-edge ceiling. The head's, 30 s (`MAX_LEAD_TRIM_SEC`), is the bad-measurement bound: music still follows a lead-in, so a wrong head reading costs the start of the song, and the ceiling stops one from halving it. The tail's, 600 s (`MAX_TAIL_TRIM_SEC`), bounds a wider tail search, not a bad reading — it cannot stop a wrong one halving any track under 20 minutes. On that edge the protection is the design: the gap is measured back from the file's proven end against the absolute floor, so everything it cuts is trailing audio below the floor with nothing after it. **Today's tail window is `OUTRO_SECONDS` (`ANALYZE_OUTRO_SECONDS`, default 20 s): a gap that fills it reads `None` and is not trimmed at all**, so the tail ceiling binds only once the tail is searched wider than 30 s (a raised `ANALYZE_OUTRO_SECONDS`, or a header that understates the decodable file by more than ~10 s) — until then a hidden-track gap or a DJ set's long silent ending still airs whole. **Off by default** — it acts on a measurement, and an upgrade must sound byte-identical until the operator asks for it; `ANALYSIS_VERSION` 7 re-targets the library so the columns fill on the next pass. Three consumers share the module and must not drift: the queue drain, the `auto.m3u` rewrite (`broadcast/scheduler.ts`) and `/now-playing`'s track clock — the last one publishes the PLAYABLE span (`drain-policy.playableDurationSec`), because a tagged duration runs every skin's progress bar past the end of the song by exactly the silence that was cut — the fallback playlist is exactly where a divergent second copy goes unnoticed, because nobody is watching when it plays. **A trimmed head shifts every onset the analyzer measured from byte zero**: `shiftOnsetMs` is applied inside `introMsFor` / `firstVocalMsFor` / `introMsOf`, at `applyPairStamps`, and on the bed's ramp budget in `maybePushBed` — that last one is the same vocal onset `firstVocalMsFor` shifts, and leaving it raw made the two disagree about one track (the prompt told the runway was 2s while the bed decision still thought it was 8s and declined a bed the link needed). The tail moves things too: the ending-aware exit canvas measures its wind-down to the trimmed end, not the tagged one, or it counts the silence being cut as part of the ramp. **Every consumer of the trimmed timeline is a `resolveSilenceTrim` call, never a local subtraction.** Both cue points also fold into the queue clock: the playable span is `[cue_in, min(duration, cue_out)]`, so pair-drain deadlines do not count either the skipped head or the cut tail as runway. The tail is measurable only off a file the analyzer proved COMPLETE (a byte-capped download's "tail" is mid-song), so it follows `outro_json`'s COALESCE write rule; head trim works either way. That proof has two different shapes and they are not interchangeable: for a normal track the seek to `duration-20s` IS the proof (a truncated file cannot reach it, and the short-decode check catches it), but the short-track path decodes from offset ZERO, where a file truncated to 70% decodes 70% and clears the same check — so a short track is measured **only** when the caller's `complete` flag says so. A rendered stem seam vetoes on either trimmed edge (`maybeRenderBlend`), because the clip is mixed FROM the outgoing tail and the incoming head: a trimmed successor head would be baked into the clip and air the very silence the trim removes. Pinned by `scripts/silence-trim.test.ts` (the arithmetic, including a cold-load round trip on the settings key), `scripts/silence-trim-library.test.ts` (**the plumbing** — nothing in production hands the resolver a track object carrying the measurements, so `library.get()`'s hand-written projection IS the feature: a column missing from that field list doesn't degrade the trim, it disables it silently with the analysis sitting in the row), `scripts/drain-policy.test.ts`, and `scripts/analyzer_silence_test.py`.

- **A request line must name the track that airs** (#1918): the request agent chooses an id AND writes its ack/intro in one answer, and the unknown-id salvage only checks the id. Live, "Michael Jackson please" got one `tracksLikeThis` call on the queued Madonna track and a VALID candidate (Madonna, "La Isla Bonita") under an intro announcing Michael Jackson's "Billie Jean". `util/request-claim.ts` is the policy — a sibling of `request-guard.ts`, not a clause inside it, because it judges whether the words match the QUEUED TRACK rather than what listener text may reach the air. The rule: a line may name what the listener asked for, another candidate the run surfaced, or a quoted title only if it ALSO names the queued track; a wrong artist is excused only by the queued artist, a wrong title only by the queued title, the listener's own words (which could be either) by either. A line naming nothing is vague, not wrong, and passes. Nor is a request claim the line declines or uses as a reference — the honest substitution the frame prompt asks for, which plain copy used to replace with the listener losing the "we don't have them": a short ENGLISH-ONLY cue table (`DECLINES`: "don't have any X", "couldn't/can't find X", "something like X", "if you like X", "not X, but", "X isn't in the crates/library", and "no X" only where the name ends the clause or tonight/in/on/here/for/but follows, since "no" is as often a determiner — "no Michael Jackson fan can resist"). Only the listener's words are excused; a quoted title or another candidate stays a claim. Another language's decline still reads as a claim (a false alarm, never a lie let through), and a lie phrased as a cue ("If you like Michael Jackson, here he is") is an accepted miss; the list is deliberately not grown into a parser. The three claim sources are deliberately ones needing no world knowledge, since the asked-for artist is usually the one the library lacks. A request claim is the NAMES inside a run of words the line shares with the request: a lowercase word splits the run rather than disqualifying it, because judged whole "some upbeat Michael Jackson" (or a possessive, whose "s" keys lower case) read back raised nothing. False positives are bounded by what counts as a NAME: the requester's screened name is never a claim, nor are the station's own (whoever voices the answer, the roster's host and guests, the station name — bare or as "DJ <name>" — and a standalone "DJ", the listener's "hey DJ" read back; "DJ Shadow" is still a name), lowercase words never are, a lone capital at a sentence start is ambiguous and skipped, a word in the run's own genre tags (the queued track's or any candidate's) is a genre — the commonest request is a genre, language or season read back capitalised ("a little Motown magic") in an ack that names no track, and treating it as an artist cost a corrective call to fix a true line — and the queued track's own names (every credited act split wide — over-grounding is the safe direction here, unlike the blocklist — "The"-less forms, a title without its bracket or dash tail, the album) are masked out first; diacritics fold on both sides. A cover passes once the line names the song, so "Leonard Cohen's Hallelujah" over Jeff Buckley's is fine. Caseless scripts carry no capital and so never raise a request or candidate claim — an accepted miss, never a false alarm. The remedy is `runRequestViaAgent`'s, run before the repeat cooldown so a changed track is still cooldown-checked: ONE corrective `repickRequestFromSeen` call (with a reason naming the chosen track from metadata, never the claim — a request claim is listener text) over the run's candidates plus, when the lines repeat the listener's words and the run made no lookup call, one `searchLibrary` execution for that name under the run's own `PickerScope` (`claimLookupQuery`) — the enforced half of "search a named ask", so an artist the library HAS can still be reached. Only a misnamed INTRO earns that call (`claimEarnsRepick`): an ack-only miss, under a fine or absent intro, is replaced with the plain ack outright, with no model call and no lookup — the ack is read rather than aired, and most of the false alarms left are ack-shaped. The price is that such a miss never reaches the lookup, so an asked-for artist the library has is not offered; the plain ack still says what plays. A re-pick that still misnames, or no re-pick, turns each misnamed line (only that one) into fixed copy naming the queued track (`plainRequestIntro` / `plainRequestAck`). The intro is SPOKEN composed English, so it airs only where `broadcast/announce-line.ts`'s `composedEnglishFits` — the gate the announce-mode link already uses — allows it; a persona speaking another language, or a title/artist in a script an English frame can't carry, gets the metadata-only `generateIntro` the echo guard regenerates with instead (no intro if that fails). The ack stays fixed English, like `screenAck`'s fallback, because it is read rather than aired. The unknown-id salvage shares the one-call budget: if it already replaced the answer, a misnamed result goes straight to plain copy. It is never a breaker failure — the harness worked, the words did not — and the verdict (`claim-repicked` / `claim-plain`) joins the request log's `guard`. The stateless cascade is NOT checked: its intros are written by `generateIntro` from the chosen track's own metadata with the artist-miss flag, and that prompt's honest miss is allowed to own the substitution without naming the stand-in, which this rule would flag. The request prompt's `frame` carries the preventive half (search a named artist/song with searchLibrary; the lines describe the returned id). - **A request's stand-in is spaced, not its ask** (#1979, point 3 of #1918): requests are exempt from artist spacing because an explicit ask wins, but a STAND-IN — the listener named an artist or title the library could not meet, and the agent chose something else — is the DJ's choice of artist, and #1918 aired Madonna straight after Madonna for "Michael Jackson please". Whether a track is a stand-in is `util/request-claim.ts`'s `requestStandIn`, read from the run's OWN lines (every ack and intro it wrote, replaced ones included): a line that declines a name from the listener's words or uses it as a reference (the `DECLINES` cues, which `lineClaims` now returns as `declines` instead of dropping), or one that names the listener's words over a track it does not name (the #1918 lie, still evidence after plain copy replaced it). **Not the request text's own capitals**: a nickname, an abbreviation or a typo ("more MJ please", "Madona") reads as an unmet name over the very artist asked for, and a test wrong in that direction steers a genuine request away from its artist — the one outcome the issue rules out. The lie's evidence shares that blind spot — a line reading the listener's "MJ" back names their words over a track it does not name by its library name — so the ask is excused FIRST. `asksForTrack` excuses any track the request's words name, case-blind (a listener's casing is no evidence), by a title form, the album, a credited act, one word of the credit ("some Elvis" is Elvis Presley), the credit written as one word ("more Moosewala" is Sidhu Moose Wala — a library search in that spelling may find them only by feel) or the credit's initials ("more MJ", "M.J.", "RHCP"), each spelled right or a letter off ("Madona", "Micheal Jakson"); a lone request-filler word is not a title ("something by Michael Jackson" does not ask for the Beatles' "Something"), nor is a filler word a misspelling. A nickname no spelling rule reaches ("the King") is excused by the run's OWN named lookups (`requestLookups`: its `searchLibrary` queries, the artists it walked with `topSongsByArtist`/`recentByArtist`, and the tracks `identifyRequestedTrack` resolved), which carry the agent's world knowledge — the accepted cost is that a stand-in artist the agent looked up by name is not spaced. Local models copy the listener's spelling into that query ("Moosewala", "Tupac"), and a query in the listener's spelling only names what the listener wrote, so a lookup whose every word is one the listener wrote (or a letter off one) also excuses the CREDITS it returned: the library's spelling of the ask, which `searchLibrary`'s artist-respelling retry exists to find. Never its vibe fallback, which marks its results `via: 'vibe'` — an absent artist's lookalikes can include the very artist on air, and that is the #1918 shape. An ask that points at what is playing (`DEICTIC`, English and as short: "more of this", "more like that", "another one like this", "same again", "more of the same", "keep it going") names the on-air track, so `runRequestViaAgent` hands `requestStandIn` the track its tail named as playing (`onAir`, data only) and that credit is excused like a lookup from any name a line reads back, but not from one a line DECLINES, which says the listener asked for someone else ("keep it going with some Michael Jackson" answered "No Michael Jackson tonight — here's Madonna" is #1918 again). A "more of this" answer is by the on-air artist, so it is always inside the spacing window, and read only by its lines any capitalised word read back over it — "Greetings back to Leeds!", "Up the Arsenal!", a self-introduction — spaced it. "No more of this" points away, and before a capital "this"/"that" is a determiner ("more of that Michael Jackson please"), so both still read as the incident. Nor is a word the request uses for something other than music evidence (`UNASKED`, an English cue table as short as `DECLINES`, read for stand-ins only): who the request is for ("for Sarah" — never an ask's own "for" after a verb that cannot introduce a person: after "looking", "in the mood", "craving" or "hoping" the name is the ask, and the incident's stand-in is spaced under it; "asking for" and "a request for" name a person as often as an artist, "a request for my wife Sarah", so theirs stays a dedication — "dedicate this to…", "shout out to…", "happy birthday Sarah", "Sarah's birthday"), a feel ("some Friday vibes", "a Sunday mood"), or a day of the week ("it's Friday!"). **The two halves fail in opposite directions, and only one is safe.** A wrong excusal leaves the request exempt — where it started: a credit word shared by chance (`asksForTrack` excuses Janet Jackson and George Michael for "Michael Jackson please", the stand-ins likeliest for exactly that ask), any of the up-to-25 tracks `identifyRequestedTrack`'s title-only and keyword fallbacks returned, a broad lookup's literal hits, a cue slot that swallows a real ask ("some Prince vibes", "asking for Prince" or "a request for Prince", or a "for" after an ask verb the row does not know: "searching for Prince"), a deictic cue beside an ask for someone else that no line declines ("more of that, but Michael Jackson", answered by the on-air artist under a line that reads "Michael Jackson" back), or a substitution owned without a name ("can't do that one"). A MISSED excusal steers a genuine ask away from its artist, at the cost of a model call, and two shapes still do: an alias read back with no lookup that found it literally — none made, or only similarity tools, or only the vibe fallback ("more of the King" answered by `tracksLikeThis`) — and a capitalised word of the listener's that is no dedication, feel or day, read back over a track the line does not name, on an ask that does not point at the on-air track — including a "more of this" sent within `stream.bufferSeconds` of a boundary, which means the track before the live edge's. An ask in other common words ("something chill") names nothing of its own, so only such a word riding beside it ("something chill, greetings from Leeds") can be read back. The remedy is `runRequestViaAgent`'s and keeps the ONE corrective call: whichever corrective call the request makes — the unknown-id salvage or the claim re-pick — is offered `artist-guard.ts`'s `requestRepickCandidates` (the run's candidates minus stand-ins by a `queue.neighbourArtistRoots(settings.llm.artistVarietyWindow)` artist, handed back whole when nothing fresh is left), so the incident's corrective call is never offered Madonna, while what the listener asked for stays on offer however recently it played. With the call unspent, a stand-in by a recently-heard artist goes through `runArtistGuard` itself with NO pick anchor — spacing only, never the pool rescue, since a pool pick is not this listener's request — and with the listener's ask `exempt` from the re-pick's narrowing (asked only of a candidate by a recent artist, since it is the stand-in reading — a pass over every line the run wrote — and a pool of a hundred candidates asking it of each stalled the event loop); its re-pick is `repickRequestFromSeen` with the guard's spacing reason, and the new lines get the claim check and plain copy, never another call. With the call spent, whatever it left stands and the booth log says so (`pick.artistGuard`, `agent: 'request'`, `reason: 'call-spent'`). One naming someone else beside the cue ("keep it going with some Michael Jackson", "more like this, but Michael Jackson") asked for them, and the on-air artist still stands in for it: on the agent path a declining line decides that case, here the matcher's name does. So `noteNames` also accepts the name's core (bracketed tags, a `feat.`/`ft.`/`featuring` tail and a spaced-dash edition suffix stripped — the blocklist's split, never `&`/`,`/`x`), matched as whole words, and refuses a one-word core under four letters ("Up" inside "upbeat"). A note naming another track still becomes plain copy; prefixing the credit onto an unnamed note was rejected because after an artist-guard re-pick that note describes the track the guard threw out. Each first-answer note that becomes plain copy is logged as `pick.notePlain` with the model's text (400 chars), so a remaining formatting miss can be told from a genuinely wrong note. The first live hour of those events showed the bigger leak was one step earlier: `agenticDiscoverySelectionReason` sends any note with a capitalised run of two or more words to that strict check, as a possible recalled track (the one claim `groundPickNote` cannot see, since it knows only the names the model was shown) — and 7 of 13 picks lost an accurate note to it, every run being the track's own act ("Amrinder Gill" from a joint credit) or album ("Coke Studio" from *Very Best of Coke Studio Vol. 1*), the previous track ("Taylor Swift") or the show's genre ("Regional Indian", "Fresh Punjabi"). A run is now foreign only when no known name contains it — the queued track's title, core title, credit and each act in it, album and genres, plus `pick-note.ts` `pickNoteReferences` (the context names `groundPickNote` already treats as references, and the show's genres) — and a run opening a sentence is also known when everything after its first word is, since that capital is grammar. An unaccounted name (a recalled "Elliott Smith's Rose Parade", a sentence-opening "Massive Attack", an unknown act beside a known genre) and any quoted title still make plain copy.
- **Likes + the operator heart** (#991, #1253): `state/likes.json` (`broadcast/likes.ts`) is accountless — one record per apparent listener per AIRING, keyed `HMAC(persisted secret, ip)`; the raw IP is never stored and one NAT is one key. The **operator's own heart** (the admin library row action) is a real record under the reserved `listenerKey: 'operator'` + `via: 'operator'`, paired with a synthetic `${songId}|operator` airing key so the existing dedup makes it idempotent per song. It counts in `countForSong` and reaches the picker like any like — the `via` marker exists so surfaces can tell them apart, not so one is second-class. Every DJ reader of likes goes through ONE gate, `likes.djFavourites` (the `likes.influenceDj` opt-in, windowed and capped by `windowDays`/`maxTracks`): the Agentic pick event's favourites clause, the pool's `listener-liked` source, the `listenerFavourites` discovery tool (registered through `PickerScope.listenerFavourites`, never on the request path) and the Track Shortlist's selection context. Before #1687's review the pool was the only route that turned a like into a candidate. Two exemptions are load-bearing and must not be "simplified" away: an operator record **skips the `topLiked` window cutoff** (a listener like ageing out is a taste snapshot expiring, an operator like ageing out is the DJ forgetting curation the operator set by hand) and **survives the `MAX_RECORDS` trim** (`trimTo` evicts oldest LISTENER records first, falling back to plain oldest-first only when curation alone exceeds the cap, so the bound always holds). Deleting likes never unstars in Navidrome, with ONE deliberate exception: the operator un-hearting when **no likes remain** for the song — that is a toggle, not a purge, and the "none remain" guard is what stops a star earned by twenty listener likes being discarded. Row hearts on every library view read one `GET /likes/index` map rather than per-endpoint annotation, because browse/search/sounds-like come from three different sources and Navidrome search rows have no `library.db` row to annotate. Pinned by `scripts/likes.test.ts`.
- **Blocklist rules** (#1300 FR 1, closes #752): the never-play blocklist carries **rule entries** beside the id entries — attribute predicates (`genre`/`tag`/`mood`/`artist`/`album`/`title`/`playlist` + any-of values) with an optional seasonal **allow-window** (inclusive month/day, wraps year-end, station zone) and an optional show scope — same `blocklist.json`, same routes, same Blocked tab. Pure matching lives in `music/blocklist-rules.ts` (pinned by `scripts/blocklist-rules.test.ts`); `blocklist.ts` owns the evaluation context — a ~15s-memoised active-rule set (clock via `zonedParts`, show via `resolveActiveShow`, both resolved once per sweep, NOT per track) and pre-resolved playlist member sets (the one async input, so `matchOf` stays synchronous). **Enforcement is inherited, not added**: rules ride `hitOf()`/`isBlocked()` inside the existing chokepoints (subsonic reject, library sources, `queue.push` gate, request declines, `annotate`) — never add a second rule-filter at a pick path, that's how the two kinds would drift. `hitOf()` answers entries-FIRST (the UI unblocks exactly the entry), and `BlockRef` is now a `kind: 'entry' | 'rule'` union. Rules are absolute like the id list — no never-starve anywhere, requests included; the row UI deliberately offers **no one-click unblock for a rule ref** (one rule can block hundreds of rows — edits happen on the Blocked tab). `tag` matches EXACT-normalised across every ingested namespace (genres ∪ moods ∪ audioMoods ∪ Last.fm — `show-filter.trackAllTags`); `genre` reuses `genreMatches`' refine direction (blocking "Punk" drops "Punk Rock", not the reverse). Custom file tags (e.g. a country) only work once they land in a field the pipeline ingests — that's an ingestion boundary, not a rules bug. **The playlist member set is read UNFILTERED** (`subsonic.getPlaylist(id, { includeBlocked: true })`, its own memo key): `getPlaylist`'s default return runs through `rejectBlocked`, which consults that very set — so the obvious shape returned the playlist minus its own members on every refresh after the first, and a playlist rule read 0 tracks and blocked nothing for half of every TTL cycle (`scripts/blocklist-playlist-rule-refresh.test.ts`). Spec: `docs/superpowers/specs/2026-08-05-exclusion-rules-design.md`.
- **An artist block reads the whole credit, not just the lead** (#1603): a Subsonic song carries one `artistId` — the act it leads with — and `tracks.artist_id` stores that same single id, so before this both the id tier and the exact-name fallback missed a track credited "Y feat. X" and the operator had to block those one by one. `music/recency.ts` `artistParticipantKeys` splits a credit into its acts beside `artistRootKey`, which answers the opposite question (who LEADS it, for the repeat guard), and both halves of the blocklist read it: `matchOf`'s artist tier and `blocklist-rules`' `field: 'artist'` case, whose comment already declared itself to BE the name fallback's semantics. The WHOLE credit is probed first and the acts after it, in ORDER, so a row several artist entries could claim always names the most specific — `matchOf`'s ordering contract, which the admin badge and its one-click unblock depend on. That first probe is the pre-#1603 tier and is load-bearing, not a leftover: `POST /library/blocklist` resolves an artist block from a track row as `{ id: song.artistId, name: song.artist }`, so blocking "this artist" on a `"Host feat. Guest"` row persists the COMPOSITE as the name — a key no participant walk can ever produce. Matching acts alone stranded every such entry, and on the sources with no `artistId` to fall back on (library rows whose `artist_id` predates migration 23, `ruleMatchRows`, queue items) rows the operator had already blocked would have started airing again. The rule half carries the same probe for the same reason: a rule value can be a pasted credit. **The split is `feat.`/`ft.`/`featuring` and nothing else, and that is the design decision, not a first cut**: `&`, `+`, `,` and `x` sit inside act names far more often than they join two credits (Simon & Garfunkel, Hall & Oates, Florence + the Machine, Earth, Wind & Fire, Tyler, the Creator, Chase & Status), and this list is the one place with **no never-starve behind it** — a wrong key silently removes music the operator never blocked, with no starvation fallback to make the loss visible. `FEATURE_SPLIT` already carries the reason it is the exception (always a credit on someone else's track, never part of a name). The cost is honest under-matching — "Y feat. A & B" keys as `["y", "a & b"]`, so a block on A alone does not fire, and a co-credit "A & B" is reachable only through the id tier migration 23 stored it for. A marker at index 0 is not a marker ("Ft. Lauderdale …"), the same guard `artistRootKey` applies, and the bracket cleanup that follows a split drops ONE orphaned closer from the segments after it — never from the lead, whose brackets are part of its name ("Sunn O)))"). The one shared normaliser is `artistNameKey` (case, curly-vs-straight apostrophes, whitespace — `artistRootKey`'s own base fold), used on BOTH sides so a stored entry name and an incoming credit can't disagree; it is deliberately NOT the rest of `artistRootKey`'s folding (article strip, root aliases, join split), which widens a MATCHING key — right for a preference the repeat guard reads as "pick someone else", wrong for a hard drop. **A participant LIST would be the better source and there isn't one**: OpenSubsonic's per-track `artists`/`participants` are not ingested and `tracks` has no column for them, so the display credit is all there is; adding that ingest is the way to reach the shapes this refuses to guess at. Pinned by `scripts/blocklist-featured-artists.test.ts` (the named bands are the collateral cases).
- **One fold under every blocklist name tier** (#1611): the id list's ALBUM tier used to key through a module-local normaliser that folded case and whitespace only, while #1603 moved the ARTIST tier onto `recency.artistNameKey`, which folds curly-vs-straight apostrophes too — so an album entry stored from a row tagged "Guns N’ Roses" missed the same album tagged "Guns N' Roses" and an artist entry did not. Two tiers of one absolute list disagreeing about what one string means. The fold is now `recency.nameKey`, with `artistNameKey` kept as its artist-facing alias (one function, two names — an album title is not an artist, and a site keying one through a helper named for the other is what invites a local copy back in), and BOTH halves of the album key run it: an album title carries an apostrophe as often as a band name ("Sgt. Pepper’s", "Livin’ La Vida Loca"), so folding the artist half alone would move the disagreement one field over rather than close it. **This WIDENS an absolute list** — two spellings of one name collapse to one key, so album entries now block rows the stored spelling missed — which is why it did not ride inside #1608; it is safe for the same reason the artist fold was, since an apostrophe style is which ripper wrote the file and never which record it is. `schemas/blocklist.ts` `normText` — what the `album`/`title`/`tag`/`mood` RULES compile and match with — moved with it, because rules and id entries answer the same question about the same row and a fold on one side only is the same drift one field over; it RESTATES the fold rather than importing it (a mirrored schema module may import only zod) and the two are pinned in step by a table. Nothing else folds: a hyphen still separates `trip-hop` from `trip hop` (which `music/scene-references.ts`' orphan scan depends on), the album key is still a (title, artist) PAIR so a generic "Greatest Hits" cannot cross-match, and there is still no never-starve behind any of it. Pinned by `scripts/blocklist-name-fold.test.ts`.

- **Prune guard**: every pruning walk is COMPLETE or prunes nothing — the tagger and reconcile walks already ran with `requireComplete`, and the analyzer CLI's `--walk` now does too (it used the best-effort walk, so an album whose `getAlbum` failed was skipped and its tracks deleted). After id adoption, `music/prune-policy.ts` decides whether the orphans may go: **never while Navidrome reports a scan in progress** (`getScanStatus`; an unknown answer does not block), and a removal larger than **max(200, 2 % of the library) is HELD** until the operator passes `--confirm-prune`. A complete walk proves what Navidrome serves now, not that the rest is gone: an unmounted music folder makes Navidrome drop its albums on the next scan, and the reconcile after it used to delete every row it did not see, with tags, analysis, vectors and play history that only a full re-tag and re-analysis rebuild. Held rows stay in the library (they are not hidden: that is the soft delete's job, not this guard's), and the hold is logged as a warning event every nonempty walk until it is mounted back or confirmed. Pinned by `scripts/prune-policy.test.ts` (pure decision + a real-SQLite `adoptAndPrune`) and `scripts/library-prune-integration.test.ts` (analyzer CLI walks + HTTP scan status).

  **Complete empty walks are an exception.** When zero tracks were walked, the tagger, Reconcile and analyzer skip `adoptAndPrune` entirely, even with `--confirm-prune`. No ID adoption, scan-status query or mass-removal confirmation occurs, and all existing rows remain. This preserves the protection against a transient empty catalogue; confirmation cannot authorize deleting the whole library through an empty walk. Reconcile keeps its existing successful exit and "Library is in sync with Navidrome" progress label, with only the console warning that pruning was skipped, rather than a structured hold warning. `scripts/library-prune-integration.test.ts` pins the empty analyzer and reconcile paths.

- **Navidrome 0.64 ID adoption (#1255, #1699)**: every authoritative library walk calls `id-rotation.adoptAndPrune` before deleting orphans. A track is adopted only if its canonical ID is present in the live walk. Derived columns, vectors and play attribution move in one SQLite transaction, which also inserts the confirmed map into `id_rotation_journal` (schema 26). Never publish the only copy of that map after committing adoption: a stopped child would delete the old rows and lose the map. The controller replays journal entries through blocklist, likes, recipes and settings; each replay must persist even when a previous failed write already changed its cache. Likes and blocklist saves share one ordered writer per store, including ordinary/debounced saves: atomic rename alone lets an older in-flight snapshot overwrite migrated IDs after the journal has been acknowledged. A failed save rejects its caller without poisoning the writer queue. Boot can read the journal before the library/vector handle opens. Stem-directory moves are replayable and best-effort. Playlist IDs require a live-index match; an unavailable index keeps the map and suppresses post-tag sync. Only successfully persisted mappings are acknowledged, and acknowledgement deletes just the consumed snapshot so a concurrent adoption survives. Legacy `id-rotation.json` handoffs remain readable; malformed/unreadable handoffs hold sync. Recovery tests exercise process exit after DB commit, transaction rollback, later-batch preservation, and failures in all four state stores. Already-pruned derived data requires a pre-migration backup. A failed Liquidsoap handoff may start this walk automatically only when `id-rotation-recovery.ts` proves the stored ID is absent and its deterministic canonical image resolves live; a generic fetch failure or canonical fixed point never starts maintenance. The detector and the maintenance child are both single-flight. A successful tag/reconcile run refreshes `auto.m3u` only after the rotation journal has settled, so the fallback cannot keep serving the pre-migration IDs until its hourly rebuild.

## Track Shortlist discovery parity

**Deliberate shared-route changes on upgrade:** Agentic Tools remains the default
selection route, but its discovery behavior is expanded by this PR. The four
sources below are part of the shared registry supplied to Agentic picks and
agent-assisted requests, not just Shortlist. `tracksByMood` energy is now a
preference on every route; strict show energy locks remain hard. Agentic results
also carry labelled cosine evidence and measured intro lengths, with explicit
prompt guidance. These changes can alter the tracks an existing Agentic station
finds. They do not add automatic preparation calls to that route. The operator
manual and PR description declare these upgrades rather than claiming Agentic
handling is unchanged.

`music/shortlist.ts` plans the configured one-to-five passes across context,
continuity and diversity. All show mood/energy combinations, genres and bounded
era windows participate in source rotation; a pick remains bounded rather than
querying every configured value. When there are no show moods, the prepared
context's `dominantMood` supplies the mood seed. A soft playlist reserves one
configured pass. Episodes and journeys retain their existing precedence.

The shared registry adds `songsByEra` and `sonicSimilarTracks`. Era sampling uses
the tagged mirror's resolved-original-year query with a random page; an empty
mirror result uses a bounded server year query and rechecks resolved years.
Server sonic discovery is registered only when `PickerScope.sonicSimilarity`
is true, resolved by the existing cached extension probe in `livePickerScope`.
Both tools use the existing collector and source blocklist chokepoints.

The remaining pool sources also use this registry: `frequentAlbums` (scrobble
history), `moodPlaylistTracks` (curated names), `similarArtistTracks` (artist graph
then top songs), and `moodWildcard` (three tracks from another covered mood).
Mood playlists are unavailable whenever a show pins playlists, including a stale
unresolved anchor (`hasPlaylistAnchor`). Both rules live in
`music/discovery-policy.ts`. The pool picker, discovery tools and
auto.m3u coast use `allowsMoodPlaylistDiscovery`: a failed pin cannot borrow
another show's similarly named mood playlist. Other eligible sources retain
their existing recovery behavior. This deliberately changes stale-pin pool and
coast discovery on upgrade. `allowsMoodWildcardDiscovery` hides
wildcards on both routes when show moods are pinned or an episode, journey or
strict playlist owns the direction; all resulting tracks still obey strict locks.
Frequent albums and wildcards use the diversity lane; artist neighbours use
continuity, and mood playlists use context. Family and source rotation remain
independent so a one-pass station can eventually reach every eligible source.

Recently-added sampling now shuffles twelve albums and three tracks per album,
including later track positions. Frequent sampling uses the same wide pool and
rotates offsets 0/12/24, retrying zero on an empty later page. Expensive server
sources cache raw pools for 30 minutes (empty results for five); every invocation
recollects under the current scope/seen set. Empty album/catalogue sources are
hidden until their retry TTL expires. Unknown standard server sources remain
available until probed; an artist-graph source returning no raw songs sets a
source-wide five-minute cooldown, so rotating seed artists cannot spend a pass
on it every pick. This is a temporary sampling decision, not a permanent claim
that every artist lacks neighbours; expiry or invalidation permits another
probe. Unresolved seed names and failed server requests do not set this
source-wide cooldown. The cache is bounded to 128 entries and shares
pool invalidation, including
protection against old in-flight responses after a server change.
Unfinished reads coalesce only for callers with the same cancellation signal;
a request and a live pick with different deadlines fetch independently. Completed
pools remain shared, and cancelled results cannot publish a cooldown.

Energy inside `tracksByMood` is a soft preference: eligible matches lead, then
other tracks in that same mood fill remaining slots. Recency, artist caps,
exclusions and duration limits still apply across both groups. An explicit strict
show energy lock remains hard and cannot be relaxed by this preference.

After the planned passes, fewer than four merged, artist-balanced candidates
may trigger at most two unused top-up sources: `starredSongs`, then `randomSongs`.
These calls use the same scope and never relax locks, exclusions or duration
policy. They are additional recovery calls, not additional model attempts.
Source-run telemetry records each actual call. Every pass supplies the shared
ten-second tool `abortSignal`, so registry `withToolDeadline` releases timed-out
calls and discovery continues. Signal-aware I/O uses that same deadline; the
new album/playlist/artist sources stop collecting after cancellation. The
merged list caps each artist
at three tracks, with the same strict-playlist/artist-episode exemptions as the
collector. This happens at choice time and does not change Agentic collection.

`shortlist-offers.ts` holds bounded, in-memory offer history: 30-minute expiry,
0.15 per offer up to 0.45, and at most 1,000 identities. It orders the merged
set before the artist cap and subtracts the penalty from transition-fit ranking.
It never excludes a track merely for being offered. The live route records
only the actual model-facing list and clears the final queued track, after
Leanings and guards, rather than the preliminary choice. Cache invalidation
clears this history. The Discovery Bench reads it without recording offers or
clearing choices.

`shortlistSituation` whitelists time period/mood/vibe, weather condition,
temperature/unit/mood/daylight and festival name/description/mood from the
prepared selection snapshot; it never copies persona Leanings or private
location. Live and bench calls use the same helper. The compact candidate view
includes `duration_sec`, known measured `intro_ms` and the first discovery
`source`; other controller fields stay private. Intro length is in milliseconds:
zero is a measured immediate start, while absent or invalid measurements are
omitted. The shared `slim` projection uses `silence-trim.shiftOnsetMs`, so both
routes see the playable timeline after any enabled leading-silence trim. When a link is planned, intro space is a soft preference between fitting
tracks; musical flow comes first. Initial and corrective choices receive it.
The separate link writer and shared speech-budget checks still determine what
can actually air. Similarity evidence is a labelled cosine score carrying
its actual `audio` or `text` index and a readable reference. Seed references use
the track title/artist or a generic label; raw seed IDs remain source arguments
and never appear as similarity reference fields. Cross-index seed rescue labels
the index that answered, never the requested one. Query and journey scores name
their own reference; neither cosine is BPM/key transition compatibility. Missing,
non-finite or out-of-range scores are omitted, while zero remains evidence.
Pinned by `scripts/shortlist-candidate-pool-parity.test.ts` and the runner tests.

Shortlist selection receives a compact journey steer and the same occasional
exploration flag used by its discovery plan. Journey choices prefer a fitting
`tracksTowardJourney` result; exploration choices give fitting unaired or
long-unplayed deep cuts extra consideration. Runs and journeys suppress that
exploration steer. Corrective choices keep the same selection context.

**DJ-mode runs and sonic journeys belong to one show (#1911).** A run
(`broadcast/dj-agent/runs.ts`) records the show it started for, and
`advanceRun` compares that with the show resolved at the pick's own look-ahead
clock (`settings.resolveActiveShow(showAt)`, the clock the pick brief and the
discovery locks use). A change ends the run and that pick starts none, so the
first pick of an incoming show is chosen for the show rather than as the next
step of an arc anchored on the outgoing host's last track; the following pick
may start a fresh run. It is checked per pick, not cleared at the session
roll: the incoming show's first pick is made under the look-ahead before the
live session rolls, so a roll-time reset lands one pick late. For the same
reason that pick's window still belongs to the outgoing show, so when the show
the pick is for differs from the live session's, the pick event ends by naming
the show (or autonomous block) its track airs in
(`scripts/changeover-pick-clause.test.ts`). Every autonomous
block shares one run identity, matching the session's soft shift. An in-order
pick takes no run step but still records its show (`notePickShow`): with
`auto` on both sides of an in-order show, a run left going when the show began
would otherwise resume on the first pick after it. The journey
destination comes from `music/journey-destination.ts`. With no show on air it is
still the daypart energy bucket. With a show it is the show's own tracks: a
resolved playlist anchor through `airableAnchorTracks`, otherwise the show's
genre/era/mood/energy/vocal filters applied HARD whether the show is strict or
not (a destination is a direction, not a pick), with dimensions the library
has no data for left out as the pick path does, unresolved genres off, and
excluded playlists removed. The daypart's energy bucket leads that sample when
the show has tracks in it. A show placed by nothing but its free-text brief gets
the tempo/key run and **no** journey: heading for a random energy bucket was
the bug. With a show on air the run, journey and listener-favourites steers
defer to its brief on both routes (the Agentic pick event, and the Shortlist's
one-shot prompt via `shortlistPickPrompt`'s `showOnAir`), and
`tracksTowardJourney` says "prefer when it fits" rather than "strongly prefer".
With no show on air every one of those texts is unchanged. Pinned by
`scripts/journey-follows-show.test.ts`.

**The Leanings review on a journey pick (#1977).** The Agentic pick event tells
the model to call `tracksTowardJourney`, and on a journey it usually calls
nothing else, often several times. The run's candidate map is then the
waypoint's neighbourhood alone, and the review chooses only from that map. With
Leanings pointing at the show's lane it ran and kept, because none of the tracks
those Leanings favour were in its set. On a journey the Shortlist plan pairs the
journey with a context lane and the anchor's continuity lane, and the Agentic
review now gets those companions. `journeyCompanions` (`music/shortlist.ts`)
runs the Shortlist planner without the journey tool for
`JOURNEY_COMPANION_PASSES` (what the default plan spends beside the journey),
through the pick's own scope, with no prepared searches and no model call. One
input differs, and it is the point: a live pick always carries `dominantMood`,
and for a show with no moods that is the station's own (festival, weather, time
of day). The planner lets it stand in ahead of the show's genres, eras and
energies, and a journey fixes the plan's order, so it took the context pass on
every pick and the show's lane never ran. The companions drop that stand-in
whenever the show places itself. The Shortlist's own journey plan still spends
its pass on the station mood; changing that changes what the Shortlist model
chooses from, so it is left as it was. The companions run only on an Agentic
journey pick with Leanings on air. They join the review's pool only; the run's
`seen` stays as discovery left it for the guards and re-picks. Only tracks the
artist guard would accept are offered, so a replacement cannot buy that guard's
corrective re-pick (the album cooldown, when on, judges it as it judges any
review replacement). Two other skips
on journey picks are the design, not a gap. Leanings the journey lane shares
with the pick (a broad genre both carry) cannot distinguish a challenger. And
"avoid that lane" written in a persona's Soul is not a Leaning: the Soul is
voice, never programming input (#1678), and the review verifies positive
preferences only. A show keeps a pick in its lane through its brief and filters,
which #1911 put ahead of the journey. Pinned by
`scripts/leanings-on-journeys.test.ts`.

Conversation continuity uses the same `promptRecapEntries` selector as
`queue.getDjRecap`. Both read the live `djBehaviour.recapLimit`, `recapMinutes`
and `recapChars` controls (defaults 10/120/140), the shared voice-kind registry
and per-kind dedupe rules. There is no separate Shortlist exclusion list.
`session.promptMemory()` still owns show and speaker boundaries, and excludes
private pick rationales and raw listener messages. The excerpts are soft
selection context, not speech to repeat. Live picks, corrections and Discovery
Bench comparisons use `selectionContextForPick`.

**Targeted search preparation** is explicitly opt-in through
`llm.shortlistSearchPreparation`, off by default on new and upgraded stations,
including Candidate Pool migrations. The Music selection UI saves and discards
it with the other selection controls. The shared live/bench helper gates before
any occurrence lookup or preparation, so disabled stations make no extra call.
When enabled for an active show with a nonblank topic or prepared brief,
`broadcast/shortlist-search-preparation.ts` uses `djObject` and its normal
per-provider output strategy for up to three search intents. Structurally grounded
proposals receive a second, independent semantic verification call against the
original brief, without the proposer's intent labels. Each call has its own
ten-second wall-clock deadline covering its internal attempts, so a slow
generation cannot leave the verification no time. The result is cached for the
airing, so only its first pick (or a retry) waits on them. Empty proposals make no
verification call. There are no discovery tools in either call; a provider may
use its structured-response formatting tool. Verification failure or timeout
keeps ordinary discovery and uses the existing preparation retry cooldown.

The model classifies musical requests in the brief's language. General
programming wishes, presenter biographies and exclusions are discarded. Each
query copies a literal subject (at most 120 characters); evidence copies a full
sentence (at most 320 characters) from an input field capped to 2,000 characters.
`shortlist-search.ts` validates sentence quotes with `Intl.Segmenter`, checks the
literal subject and rejects known presenter identities. It contains no English
phrase lists for music/presenter classification. Semantic verification checks
biography and general programming sentences independently of proposed title,
theme or genre labels. This remains a model judgement; literal grounding is
enforced by code, and quoted words alone do not prove an interpretation.
Unsupported, ambiguous or paraphrased subjects are omitted. No persona Leanings,
raw listener text, track IDs or executable tools enter preparation, and its
validated empty result is cached normally. The truncated input remains in scope
for grounding; it is never reconstructed by parsing the outgoing prompt.

Prepared queries, including successful empty results, persist in
`state/shortlist-search-preparations.json` under the scheduled/takeover occurrence
and brief content. Concurrent callers share preparation; later picks and
restarts reuse it. Versions 1 through 3 are discarded because they lacked the
current independent verification; the current store version is 4.
Changed briefs and new airings prepare
separately. Failure
keeps ordinary discovery, with a five-minute retry delay and at most two
preparation attempts per input. Expired results are discarded; the store keeps
at most 64 records. A failed state write retains the in-memory result and logs
the persistence error. Prepared artist catalogues skip this extra call, and
token-budget soft/hard modes do not start it.

The controller maps validated intent to `searchLibrary`, `topSongsByArtist`,
`recentByArtist`, `searchByLyrics` or `searchBySound`, using the existing registry
availability gates, collector and station locks. No model executes those tools.
Multi-pass ordinary discovery reserves at most one configured pass for a
rotating targeted query when at least two passes remain, keeping an ordinary
source pass. With two passes and a soft playlist, the playlist keeps one pass
and targeted queries rotate with ordinary sources in the other;
one-pass discovery rotates searches normally. Episodes, journeys and strict
playlists keep their priority, and soft playlists keep their reserved pass.
An unavailable search is omitted; empty/error results use the existing bounded
recovery sources. No extra discovery passes, tool loops or picking-model calls
are introduced. Search briefs never become speech context. The Discovery Bench supplies the same opt-in prepared searches, saved recap
policy and exploration decision as live selection; it shares the preparation
cache and never queues a diagnostic pick. Regression checks capture real
route/SDK calls with synthetic services, cache recovery, policy filtering and
cancelled I/O.

**Model-failure recovery** matches the pool's own move. When `djPick` fails,
`djObject` has already spent both of its attempts, so the route queues the top
of its own fit-ordered list rather than handing the slot to the pool, which
would spend two more attempts on the model that just failed. Nothing
model-shaped runs after that: the Leanings review is skipped, and the artist
and album guards still choose WHICH candidates are eligible but take the first
of them instead of asking for a re-pick (`guardRepick`). The pick carries the
neutral Booth clause and no transition gesture. It is not a success: the route
reports `health.modelFailed` and `runTrackEvent` counts a breaker failure, never
a `breakerSuccess`, so three in a row still open the breaker. The spoken link is
still attempted, as the pool's is, because a model that cannot hold a structured
pick can often still write free text. Pinned by
`scripts/shortlist-model-fallback.test.ts`. A failed corrective Shortlist re-pick
(or an unusable corrective ID) likewise takes the first track from that call's
already-guarded subset, preserving fit order and artist/album exclusions. It
marks the same breaker failure, carries a neutral reason and no transition, and
prevents subsequent model-shaped corrections. Empty subsets retain the existing
starvation/recovery policy. Agentic and request corrective calls keep their
existing failure handling. Initial, corrective and already-failed guard choices
all use `guardedShortlistFallback`, with one `shortlist.modelFallback` event name
(`stage` identifies the path) and one Booth line per controller choice. Pinned by `scripts/shortlist-corrective-fallback.test.ts`.
The additional discovery/energy/similarity guards are pinned by
`scripts/shortlist-remaining-discovery.test.ts` and
`scripts/picker-soft-energy-similarity.test.ts`.

## Targeted acoustic analysis

Facet rows describe retained measurements even after a failed retry. Their
`attempts` mirror the track's consecutive failure count on every status, so
`needs` and `outdated` stop selecting head-only or older measurements after three
failures. Explicit `failed` and `all` runs can retry them. Clearing failure
history resets attempts on retained rows too. The open-time derivation stamp
upgrades existing rows without promoting their measurement versions.

A vocal row's `head-only` reason comes from its current columns, including on
upgrade. Tail reasons such as `capped-download` describe the measuring pass and
survive unrelated writes and resynchronization. Head-only vocal work requires
confirmed `tailVocalAvailable()` support through the shared capability policy;
unknown support still allows missing head vocals but never widens tail backfill.
Targeted runs that disable vocals preserve stored tail vocal ranges, including
an instrumental `[]`, without marking the carried measurement fresh.

## Prepared artist episodes

`broadcast/show-preparation.ts` owns `state/show-preparations.json`. Its key is a
scheduled occurrence or a takeover start, resolved by `show-occurrence.ts`, rather
than a chat session or a spoken handoff. It saves the validated skill result
before catalogue work and a ready result before exposing it to music or speech.
Concurrent callers share one preparation. A restart never re-executes a tool whose
subject was accepted. Arbitrary tool side effects before that save are not
transactional.

`music/episode-source.ts` validates the artist ID through Navidrome, reads the
complete mirror or bounded album fetches, and applies show safety filters. The
live album path accepts an exact track artist ID or the first explicit track or
album artist ID, never a name match. The album artist matters for collaboration
tracks whose combined track credit has its own Navidrome ID. Random preparation
intersects mirrored candidates with the artist index so track-only combined
credits cannot masquerade as an indexed artist with albums. Catalogue retries
reuse the durable result; the admin retry can recheck a failed source without
re-executing its tool.
An initially selected result whose catalogue failed recovers as `degraded`, with
its saved reason and editor retry action. Restart preserves the two-attempt
automatic catalogue limit; an explicit retry can recover the same subject after
that limit is exhausted.
Its `ArtistEpisodeSource` travels whole through `PickerScope`; every discovery tool
intersects with it before recording candidates. `episodeArtistTracks` is the
in-catalogue source. The pool picker and auto-playlist draw directly from the same
catalogue. Requests do not receive this scope. The auto-playlist build key carries
the occurrence and prepared source identity, and publication checks the current
show and settings epoch before replacing `auto.m3u`.
