# Internals: analyzer, Icecast rendering and state layout

Why the sidecars, the Icecast config rendering and the state directory are
shaped the way they are. The short invariants are in the root `CLAUDE.md`; read
the matching section here before changing any of them.

The recurring trap: **`docker/broadcast-entrypoint.sh` and the AIO supervisor's
`render_icecast()` / `bootstrap_state_dirs` must stay in lockstep.** Five things
live in both — per-mount burst/queue sizing, the listener-auth blocks, the
trusted-proxy list, the state-dir bootstrap, and `resolve_max_clients` — and a
fix applied to one is a bug in the other.

Covers: the analyzer service and its two flavours, public persona disclosure,
real listener IPs, the non-fatal state bootstrap, and multi-station profiles.

`settings.stream.bufferSeconds` is the single source of truth for listener
delay. Both Icecast renderers read the controller-written handoff file; neither
accepts an environment override, because the controller would keep advertising
the stored value and every listener-facing timestamp would drift.

`settings.stream.maxListeners` takes the **opposite** precedence, deliberately.
Both renderers resolve it through `resolve_max_clients`, which prefers
`ICECAST_MAX_CLIENTS` and only falls back to the handoff file
(`liquidsoap_icecast_max_clients.txt`, default 100). The asymmetry with
`bufferSeconds` is the point: nothing the controller publishes depends on the
listener ceiling, so an env override cannot desynchronise a clock — while the
var predates the setting and rides all three compose files, so demoting it
would silently re-ceiling a station on upgrade. What that costs is a setting
that can save and do nothing, so **the winning source is logged on every boot**
(`max listeners N (from ICECAST_MAX_CLIENTS|settings|fallback:…)`) and the admin
hint says so. Junk from either source falls back to 100 rather than rendering
invalid XML — or a `0` that would serve a station nobody can connect to.

The setting exists for the AIO image, which is where the gap was: the Unraid
template exposes no `ICECAST_MAX_CLIENTS` and there is no `.env` in that
container, so the ceiling was literally unsettable there. Licensing bodies in
some countries calculate fees on simultaneous listener capacity, which is what
made it worth a setting rather than a docs line (#1300 FR 15). Both copies of
the function are driven from one table by `scripts/max-listeners.test.ts`.

**Default-on `analyzer` service** — the acoustic-analysis sidecar (`subwave-analyzer` image, `docker/Dockerfile.analyzer` + `docker/analyzer/server.py`). **Starts by default** in all three composes (no profile gate — like controller/web); only `tts-heavy` (voices) stays opt-in. It's the librosa (+ optional CLAP + Demucs) analyzer **split out of tts-heavy**: bpm/key/intro/loudness always, plus **outro analysis** on every tier (last ~20s of each *complete* file → `tracks.outro_json`: fade-vs-cold ending, tail LUFS/tempo/bars; a byte-capped download skips it — the completeness flag rides the analyze request). The outro is what makes transitions ending-aware: `queue.applyMixTransition` stamps each DJ-mode track's OWN exit canvas from its measured ending via `mix.endingCrossSecondsFor` (a fade rides out 8–12s, a cold end cuts ~4s; washout/loop overwrite it) — the per-track answer to #749, which blocks the pair-sized `crossSecondsFor` from ever being applied — and a measured fade vetoes the `chop` effect (`effectAllowedFor`). **Vocal-aware transitions** (heavy tier, vocal detection on): the outro window gets its own Demucs pass → `outro.vocalRanges` (absolute ms, `[]` = instrumental tail; backfill widened via the `tail_vocal` capability flag so stale analyzer images never churn; lyric-decided tracks skip the tail Demucs pass like the head one — their tail ranges are clipped from the synced-lyric timing instead, `lyric-vocal.clipRangesToTail`) — a sung fade pulls its exit canvas to the 8s floor (`Analysis.vocalTail`), a sung ending vetoes `chop`, and a *measured* first-vocal entry under 2.5s drops the DJ link outright (`enforceIntroBudget` — see `docs/stem-transitions-research.md`); "sounds-like" embeddings (multi-window CLAP — start/mid/late windows averaged, so quiet intros don't misrepresent the track), vocal ranges, and the CLAP **text tower** (`POST /embed-text`, capability-flagged in `/health`) are the heavy tier. Text and audio vectors share one 512-d space, which powers the picker's `searchBySound` tool (describe a sound in words → audio KNN) and zero-shot audio moods (`music/audio-moods.ts`: mood-vocab prompts scored against stored audio vectors at the end of every analysis pass → `tracks.audio_moods`, blended into `songsByMood`/`trackMoods`; vocab/prompt changes re-score via `mood_vocab_hash`). **Two published flavours**: `subwave-analyzer` — **LEAN, multi-arch** (~1.1GB — librosa + ffmpeg, no torch — the default everyone pulls), `WITH_CLAP=0 WITH_DEMUCS=0`; and `subwave-analyzer-heavy` — CLAP+Demucs baked (~1.9GB, amd64-only), `WITH_CLAP=1 WITH_DEMUCS=1`. **Opt-in switch is `ANALYZER_HEAVY=1` in `.env`** — the compose `analyzer` service resolves `image: …/subwave-analyzer${ANALYZER_HEAVY:+-heavy}:…` and its `build.args` key off the same var (so pull and local build agree). No `platform` pin (lean is native arm64; heavy on arm64 needs `DOCKER_DEFAULT_PLATFORM=linux/amd64`). Uses the **same `analyze_worker.py`** as the offline CLI (single source of truth). The controller resolves its analysis backend from `config.analyzer.urls` — **`ANALYZE_URL`** (`music/analyzer.ts` probes `/health`), then a local venv (`ANALYZE_PYTHON`). tts-heavy is TTS-only now and is **not** an analysis backend (no `TTS_HEAVY_URL` fallback). **AIO (`Dockerfile.aio`) bundles the analyzer in-process** (local venv, `ANALYZE_PYTHON` + `HF_HOME` under the state dir) rather than a service; `subwave-aio` is lean, `subwave-aio-heavy` bakes CLAP+Demucs. The analyze worker lives in the analyzer image(s) and the AIO. **Remote path fallback (#1331)**: the controller still prefers its one-ahead shared-path handoff, but a sidecar's typed `path_unavailable` response earns exactly one retry by URL; `complete` and `stems_dir` are removed because they describe controller-local files. Never retry generic DSP/decode failures. Shared state remains required for remote stem output and recommended for prefetch throughput.

**Analyzer concurrency (`ANALYZE_CONCURRENCY`, #1538).** One env var, read on BOTH sides and bounded `1-8` with a fall-back-to-1 (not a clamp) on anything empty, non-integer or out of range — `envInt` in `controller/src/config.ts`, `_bounded_int_env` in `docker/analyzer/server.py`. **The default of 1 is the pre-change station, byte for byte**, which is the whole reason the two code paths are kept side by side rather than unified: `music/analyze.ts` keeps its original one-ahead `prefetch()` loop verbatim at 1 and only takes `music/analyze-dispatch.ts` above it. Above 1 the pass admits jobs in **source order** through `dispatchAnalysis`, bounded by live count, and commits every outcome back **in source order too** — the systemic-failure guard (`failureCountsAgainstTrack`, the buffered `pendingFailureStamps`) reads a run of consecutive failures, so out-of-order commits would condemn tracks over a bad *pass*. The quiet gate is evaluated **before every admission and before that job's download** (`beforeStart`), so a paused pass never keeps pulling audio for work it isn't going to compute; its fail-open direction is untouched, and it still resolves through the one `analyze-quiet-pure.ts` decision. The win is specifically the **share-less remote topology**, where the path probe 422s and the analyzer fetches each track itself; a local shared-mount setup already overlapped via the prefetch, and **local `ANALYZE_PYTHON` stays single-flight regardless** (`backend === 'sidecar' ? requested : 1`) because one line-protocol stdio worker cannot multiplex.

**The download cap (`ANALYZE_MAX_BYTES`, #1549) is the other two-sided env var**, and it is parsed with the same posture for the same reason: `envInt` in `music/analyzer.ts` for the controller's own prefetch, `_env_int` in `scripts/analyze_worker.py` when the worker fetches the audio itself, both falling back to the shared 12 MB default on anything empty, non-integer or below 1. The two used to disagree on a typo — TS `parseInt` produced **NaN**, which is false in both comparisons (cap off AND every file flagged incomplete, so outro analysis went off library-wide with nothing logged), while Python's bare `int()` RAISED and killed the download. `_env_int` matches `envInt`'s grammar rather than deferring to `int()`, which is looser (`1_000`, non-ASCII digits) and would put the two fetch paths back on different caps. Pinned by `scripts/analyzer-max-bytes.test.ts`, which drives both sides from one table.

The sidecar half is **N independent single-flight worker processes**, not one worker with a bigger queue — same `analyze_worker.py`, each with its own stdio lock, fronted by `AnalyzerWorkerPool`. Three rules that are expensive to rediscover:

- **A recycling member is "coming back", not "gone".** `_acquire_worker` raises `WorkerUnavailableError` (→ the controller's clean fall-through, analysis row stays NULL) only when nothing is ready AND nothing is recycling. When a member is mid-recycle it **waits on the condition** instead, bounded by `recycle_loop`'s own 180s respawn budget and its `finally` that always clears the claim. At the default concurrency of 1 that recycle window is the entire pool, and failing fast there would 500 every request for up to three minutes — the single worker used to hold its request lock across the respawn for exactly this reason. Selection failing is therefore **not** retryable in `pool.request` (it would spin on the same verdict); a worker going bad *after* selection is, and picks another member.
- **Reservation and the recycle claim are each taken without yielding**, which is what makes them mutually exclusive on the event loop: `reserve_if_available()` tests `available` and sets `_reserved` with no `await` between, and `recycle_loop` tests `_reserved` and sets `_recycling` the same way. Whichever lands first wins — admitted work finishes on that member, or the pool routes past it. Inserting an `await` into either sequence reintroduces the race.
- **Capability aggregation reads the SELECTABLE members only, and only unanimity earns a `False`.** Iterating every configured member instead makes one booting or recycling worker report `None` for the whole pool, and the controller's tail-vocal backfill requires `=== true` — a healthy heavy pool would intermittently read as a stale analyzer image. And because `capability_errors` deliberately survives its own worker's respawn (#1300 bug 3), a single member's bad load hour would otherwise latch `False` pool-wide until the container restarts; a split verdict is `None` (some member can still serve it) and only an all-members loss — the lean-image case, where they share one build — is `False`. `/health`'s other aggregates follow the same shape: `analyze_models_resident` is an `all()` over ready members, `analyze_heavy_idle_s` the least-idle of them, `analyze_worker_recycles` a sum. All of it is identical to the old single-worker answers at N=1. Pinned by `controller/scripts/analyzer_sidecar_contract_test.py`, which drives the real `StdioWorker` state transitions (not a stand-in) for the recycle cases.

**Private station mode (#478).** `settings.privacy` holds two independent locks over ONE shared `password`: `privatePlayer` (the web player pages ask for it before rendering — shell-level in `PlayerShell`, rides `/state`, applies live) and `listenerAuth` (Icecast listener auth on every stream mount). Either lock being on requires a password — `settings.update()` throws otherwise, because a lock with no password behind it either fails every listener closed or renders a prompt nobody can satisfy. Listener auth uses Icecast **URL auth**, not htpasswd: `settings.update()` writes `state/icecast_listener_auth.txt`, and the broadcast entrypoint (+ AIO supervisor's `render_icecast()`, re-run on every pair relaunch) renders per-mount `<authentication type="url">` blocks pointing at `POST /listener-auth`. External clients send basic auth (`user:pass@`), the web player rides `?auth=` on the mount query (Icecast forwards the query string in the auth callback; browsers can't basic-auth an `<audio>` element). **Two endpoints, opposite failure modes — do not merge them**: `POST /listener-auth` (Icecast) fails OPEN when `listenerAuth` is off, covering the window where icecast.xml still carries the auth blocks but the setting is already off; `POST /station-auth` (the web gate, rate-limited) fails CLOSED, because `privatePlayer` can be on while `listenerAuth` is off and reusing the Icecast decision there would accept any password. Both live in `util/listener-auth.ts`, pinned by `scripts/listener-auth.test.ts`. Toggling `listenerAuth` needs a mixer restart (rides `requiresRestart`); password changes apply live. `/listen.pls`/`/listen.m3u` 403 while auth is on. Settings UI lives in the **Station** section. Operator-facing writeup: `docs/private-station.md`.

**Public persona disclosure.** `settings.privacy.publishPersonaSouls` (default `false`) sits in the same `settings.privacy` block but is **a disclosure toggle, not a lock** — it takes no part in the password invariant above, needs no restart, and applies live. It governs the ROSTER-WIDE public reads: `GET /schedule`'s persona index and `GET /personas`. Those always publish `id`/`name`/`tagline`/`avatar` (and each show's `guestPersonaIds`, resolved against the live roster so a deleted guest vanishes); a persona's `soul` rides only when the toggle is on, because a soul is the persona's **system prompt**, not a written bio, and these reads hand over every persona at once. When off the key is **absent, not empty**, so a client can tell "not published" from "published but blank" (`/personas` also reports `soulsPublished`). `GET /dj` is deliberately **out of scope** — it has always published the ON-AIR persona's soul, one at a time, and gating it would break existing public clients. The shape + rule live only in `util/public-persona.ts` (never inline in the route), pinned by `scripts/public-persona.test.ts`. Never widen the shape to TTS config, skills, or the behaviour dials.
- **Real listener IPs / trusted proxies**: Icecast's only peer is the edge, so admin → Listeners shows the proxy's container IP unless `<x-forwarded-for>` names that proxy. Rendered into the template's `<!--@TRUSTED_PROXIES@-->` marker by `docker/broadcast-entrypoint.sh` and the AIO's `render_icecast()` — the **third** thing those two must keep in lockstep, alongside the per-mount burst/queue and the listener-auth blocks. Two icecast-KH facts pin the design: it matches an **EXACT IP** (a CIDR is accepted and then silently never matches, so no subnet shorthand), and it reads the **left-most** entry of the chain (the real client, even though Caddy appends its own peer). Source order is `ICECAST_TRUSTED_PROXY_IPS` (explicit, wins) → DNS for `ICECAST_TRUSTED_PROXY_HOSTS` (default `caddy`). The DNS path is **deliberately best-effort and misses the first cold boot** — caddy `depends_on` broadcast being healthy, which needs icecast already serving, so the name cannot resolve at render time (measured: ~6s unresolved); every later restart picks it up. A miss degrades to the old behaviour (proxy IP shown), never to a wrong IP, so nothing downstream handles a half-applied state. The AIO trusts loopback outright (Caddy is in-container). Malformed entries are dropped rather than interpolated — invalid XML here would turn a cosmetic setting into a station that won't boot. Counting still must NOT key on IP (`groupConnections`): the header may be untrusted, and one NAT is many listeners.
- **State bootstrap is never fatal (#1300 bug 10)**: `bootstrap_state_dirs` in `docker/broadcast-entrypoint.sh` and the AIO's `supervisor.sh` (same function, same list, same messages — the **fourth** thing those two keep in lockstep) creates the shared state dirs and opens them to 777, because the controller and analyzer write there as other uids. Every step is guarded and warns instead of aborting. The entrypoint runs `set -eu`, so the old bulk `mkdir -p a b c` / `chmod 777 a b c` made **every state path load-bearing**: one on a mount that refuses the change — a read-only bind, an NFS export, the exFAT/NTFS disk people move the stem cache to — exited the entrypoint BEFORE icecast started, and compose reported only `dependency failed to start: container sub-wave-broadcast is unhealthy`, naming neither path nor cause (measured: `exit=1`, `health=unhealthy`, one `chmod:` line). A station that refuses to boot over a permission convenience is strictly worse than one on a degraded mount — icecast still serves and the dead-air guard still airs the emergency loop, but an exited container airs nothing. The warning keys on **writability, not on chmod's exit status**: a mount already world-writable that merely refuses chmod is a WORKING config, and a line printed on every boot of a healthy station is one operators learn to skip. `stems` + `transitions` are in the list because a bind mount there lands root-owned 755, which the analyzer (uid 10001) cannot write — measured `ANALYZER_WRITE_DENIED` before, `_OK` after. **A relocated stem cache gets its own entry**, guarded the same way: `STEMS_DIR` (a HOST path in `.env`) is mounted at a fixed container path that compose passes down as `SUBWAVE_STEMS_DIR`, and that path is OUTSIDE `$dir`, so the subdir loop never reaches it — without the extra `state_prepare_dir` the relocation reproduces the same root-owned 755 it exists to escape. Two names on purpose: the controller reads `.env` through `env_file:`, so the host value is visible inside the container and means nothing there. `music/stem-cache.ts` `resolveStemsRoot()` is the other half — it re-appends the per-station segment under the relocated root, because compose cannot read `stations/active.json` and Navidrome creds are per-station, so one shared root would let station B render a transition from station A's audio. Unset reproduces `<stateDir>/stems` exactly, which is what makes deleting the line a clean undo. Pinned by `scripts/state-bootstrap.test.ts`, which drives BOTH scripts through one table, and `scripts/stem-cache-root.test.ts`.
- **Multi-station profiles**: `state/stations/<id>/` + `stations/active.json` decide the ACTIVE station dir, resolved once per boot in four places — `config.ts` (`STATE_DIR` = resolved dir, `STATE_ROOT` = root), `radio.liq` (`SUBWAVE_STATE_DIR` env), `docker/broadcast-entrypoint.sh`, and the AIO supervisor (kept in lockstep). No `stations/` dir → single-station, everything at the root as before. Switching = pointer write + mixer restart + controller `process.exit` (docker restart policy reboots both against the new dir) — never hot-swap state paths in-process. Only `icecast-secrets.env`, `hf-cache`, `analyze-tmp` stay install-level at the root (`conversionAction` in `stations/pure.ts` is the classifier; new root-level state files must be classified there and in `duplicateAction`). State files holding **absolute paths** must be re-derived at boot rather than trusted — `jingles.m3u` is the one such file today (`ensureDefaultIdent` rewrites it every boot so conversion/duplicate can't leave it pointing at a moved dir).
