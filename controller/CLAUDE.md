# CLAUDE.md — `controller/`

Loaded when working under `controller/`. Station-wide architecture lives in the root `CLAUDE.md`.

### Controller (`controller/src/`, ESM Node.js)

Grouped by domain: `server.js`, `config.js`, `settings.js`, `context.js` at the root; everything else under `routes/`, `middleware/`, `music/`, `broadcast/`, `audio/`, `llm/`, `skills/`.

- `server.js` — thin Express entry: applies middleware, mounts routes, runs startup. **`routes/`** splits the API by surface: `public.js` (`/health`, `/now-playing`, `/state`, `/dj`, `/cover/:id`), `request.js` (`POST /request`), `settings.js` (`/settings`, `/restart-mixer`, `/auto-pick`), `jingles.js`, `debug.js`. **`middleware/`** holds `cors.js` (wide open `*`), `auth.js` (the `requireAdmin` Basic-auth gate via `ADMIN_USER`/`ADMIN_PASS`), `ratelimit.js`. **In prod (`NODE_ENV=production`, set by both prod compose files) the gate is mandatory** — the controller exits on boot if `ADMIN_USER`/`ADMIN_PASS` aren't set. Listener-request safety (scripted-opener stripping, verbatim-echo guard, requester-name screening) lives entirely in `util/request-guard.ts` — the one policy chokepoint shared by `request.js`'s `POST /request` and the session DJ agent's request path; `settings.requests` is the gate config (pause toggle, queue depth, per-IP/global rate caps), never inlined at either call site.
- `broadcast/queue.js` — in-memory `upcoming`/`history`/`djLog` + `drainToLiquidsoap()`, the **single writer of `next.txt`** (and request-intro `say.txt` via `tts.speak`). `announce()` is the **single writer of scheduled `say.txt`/`intro.txt`** (picks target by kind: `'link'` → `intro.txt`, else `say.txt`). All track playback goes through `queue.push()`; all spoken segments through `queue.announce()`. Request-intro TTS is written ~250ms before the track URI so Liquidsoap picks up the voice file first. `djLog` remains station-wide for the booth UI/stats; it is NOT prompt memory — `getDjRecap()` / `getRecentOpeners()` format the current session's aired turns through `broadcast/prompt-memory.ts`.
- `broadcast/block-queue.ts` — the pure half of **album / block queueing** (#1622 FR 4): `orderAlbumTracks` (disc, then track, source order as the stable tiebreak — a music server's return order is conventional, not contractual, and this is the one queue where a wrong order IS the failure), `planBlock` (order → partition → cap, and the order of those three is load-bearing) and `blockPlayableSec`. The Subsonic lookups and the pushes stay in `routes/dj.ts`'s `POST /dj/queue-block`; `blocklist.hitOf` is INJECTED, like `album-guard.ts` takes `albumKeyOf`, so every read stays at the call site. The route reads the blocklist only to NAME a skip — `queue.push()` is still the refusal — and re-reads it per push, since a seasonal rule can turn between the plan and the queue. `queueBlockSchema` (`schemas/dj.ts`) REFUSES `order: 'shuffle'` and `limit` on an album rather than ignoring them, the same both-halves-of-one-rule posture `schemas/schedule.ts` takes with `until`/`minutes`. Pinned by `scripts/queue-block.test.ts` (the plan) and `scripts/queue-block-wiring.test.ts` (the schema refusals, the block stamp, the partial cancel, the listener's wait clause).
- **LLM layer (`llm/`)** — every model call goes through the Vercel AI SDK (`ai` package), so the provider is swappable with no call-site change. The eight public modules (`llm/{sdk,provider,dj,agent,tools,segment-tools,speech,log}.js`) are **thin barrels**; the implementation lives under `llm/internal/**`, grouped by concern (`core/`, `provider/`, `strategy/`, `prompts/`, `tools/`, `speech/`, `telemetry/`). Call sites import the stable barrel paths only — never `internal/`.
  - `llm/provider.js` → `internal/provider/**` — `registry.ts` resolves + caches a `LanguageModel` from `settings.llm` (`provider` ∈ ollama | openai-compatible | anthropic | openai | google | deepseek | openrouter | gateway; `model`; optional `apiKey`); `legs.ts` is the primary/fallback legs + reachability probe; `embedding.ts` the embedding models. **`capabilities.ts`** holds the per-provider **capability descriptors** — the single chokepoint translating `settings.llm.reasoning` into each provider's native thinking knob and declaring which providers need the forced-tool object path; strategy code has **no `provider ===` branches**. It also owns the tool-loop's **shape**: `discoverySteps` is how many FREE discovery steps the agent gets before `done` is forced. Forced-tool providers (ollama, openai-compatible, locca) keep **1** — they ignore `toolChoice` with several tools visible and emit schema-valid objects without exploring, so the single cornered call is what holds them; native-strategy providers get **3**. The step cap is **derived** (`gatedMaxStepsFor` = budget + 1), never taken from the caller, which keeps the invariant that the main run makes **exactly ONE forced-`done` attempt** at any budget before handing off to the recovery cascade — extra `done` steps grow an "I already declined" trail and make GLM-class compliance worse. The per-provider budget is **opt-in per agent** (`providerDiscoveryBudget` on the definition — the pick/request agents set it; `runDiscoverySteps` resolves the budget in force): a `djAgent` caller that doesn't opt in keeps the historical single discovery step, because a caller's pinned cap can be load-bearing — the segment director's `maxSteps: 2` (`skills/_agent.ts`) documents a run burning the full `agentTimeoutMs` when its loop silently widened, so the widening must never apply implicitly to every agent on a provider. Clamped to [1, 5]; a zero budget would force `done` at step 0 with an empty `seen` map, where the model could only fabricate an id. **`settings.llm.discoverySteps`** (per-leg, like `toolChoice`/`numCtx`; default `0` = follow the descriptor, `1`–`5` overrides) is the operator lever — the descriptor keys off the PROVIDER and cannot know which MODEL it serves, and the two failure directions are opposite (a capable local model behind openai-compatible wants more than its cautious 1; a wandering cloud model wants fewer than 3). The override is read off the **leg's cfg**, never from settings, so `capabilities.ts` stays a pure function of its argument. Adding it needed the usual THREE edits (`DEFAULTS` + `applyLlmLegPatch` + `load()`'s composition) and is pinned by a **cold-load** round trip, `scripts/llm-discovery-steps.test.ts` — verified to fail 6/9 with the `load()` line removed. `legs.promptDiscoverySteps()` is the figure a PROMPT may promise — the **minimum** across primary and fallback, because the system prompt is built before failover picks a leg and over-promising a second look the model never gets is the expensive direction to be wrong. `ollama` is the homelab default, no key. `openai-compatible` targets self-hosted servers (llama.cpp, vLLM, LM Studio) via `llm.baseUrl` + `/v1/chat/completions`. **`settings.llm.headers` / `llm.fallback.headers`** (#1618) are extra request headers the openai-compatible transport (openai-compatible + locca, the one builder) sends on every call — for a gateway that routes on a header of its own rather than the bearer token alone, and nothing in the code names a specific one. Absent (the default) the client is built with no `headers` option at all, so an upgraded station is byte-identical. They are captured at CONSTRUCTION like `repeat_penalty` and `num_ctx`, so `headersSig` is in the client cache signature — without it an operator's edit reads as ignored until a restart, and the FALLBACK leg is handed the primary's client and therefore the primary's session header. The shape rules (an RFC 7230 token name, printable-ASCII single-line values, 10 entries, 500 chars) live once in `schemas/settings.ts` and are imported by both the strict save path (`applyLlmLegPatch`, whole-map REPLACE so the editor's Remove works) and the lenient load path (`normalizeLlmHeaders`). Values are **redacted to the `'set'` sentinel** by `getRedacted()` — a routing header and a credential header are the same field — and `'set'` on the way back in means "keep what is stored", which is what lets the admin form round-trip. Needed the usual THREE edits and is pinned by a cold-load round trip plus a wire capture, `scripts/llm-custom-headers.test.ts`.
  - `llm/sdk.js` → `internal/strategy/**` over `internal/core/**` — three primitives: `djText` (free text), `djObject` (Zod structured output), `djAgent` (a `ToolLoopAgent` tool-loop — the primitive behind `broadcast/dj-agent.js`). `djAgent`'s native-first → done-tool → recovery → **terminal collapse** → text-salvage cascade dispatches off the pure `agentPlan()` (`strategy/plan.ts`). The terminal collapse (#1157) is the last leg before salvage: when a model declines the forced `done` call twice, `renderTerminalPrompt` (`core/pure.ts`) flattens the chat window + the discovery trail into ONE user prompt and asks via `objectViaToolCall`'s forced `emit` tool. **The fix is the conversation SHAPE, not more forcing** — llama.cpp/LM Studio + Hermes-class models return `tool_calls: []` on a terminal `done` step no matter what `tool_choice` says, yet call a forced tool reliably from a single-turn prompt (which is exactly why the stateless pool picker keeps working on the same backend); GLM keeps declining once it has declined in a conversation. Flattening the **trail** into the prompt is load-bearing — it carries the real candidate ids, without which a cornered model can only fabricate one. Leg count is a budget decision too: all legs share ONE deadline (`llm.agentTimeoutMs`, 45s), so an extra leg would never be reached on the slow local rigs that need it most. `core/` is the shared runtime: `pure.ts` (side-effect-free helpers — the unit-test seam, `scripts/llm-pure.test.ts` via `npm run test:llm`), `retry.ts` (transient retry + wall-clock deadline), `failover.ts` (primary→fallback, only on a host-unreachable error — see `isUnreachable`).
  - `llm/log.js` → `internal/telemetry/log.ts` — 120-entry ring buffer of recent calls for `/debug` + durable pick log. `internal/telemetry/export.ts` is the downloadable form of that ring (`GET /debug/llm-calls/export`, `?format=ndjson` for one call per line) and writes each call **verbatim** — the export is safe precisely because it shows nothing `/debug` does not already show to the same admin credential, so a field added or filtered there is a second, divergent reader of the log. It is deliberately outside the `/debug` snapshot cache (that cache coalesces a 2s poll; this is a one-shot download that must reflect the ring at the moment the button was pressed), and outside the Connect catalog, like every other internal operator route. `llm/tools.js` + `llm/segment-tools.js` → `internal/tools/**` — `tool()` defs wrapping Subsonic/library discovery (picker) and real-world data (segment director). The picker set is **one file per tool** under `internal/tools/picker/tools/`, each declaring its own `available` gate (a tool offered without its backing index spends the single discovery call on a guaranteed-empty result); `picker/index.ts` is the registry and holds only the order the model sees. Every constraint a pick runs under travels as ONE **`PickerScope`** value (`picker/scope.ts`) that is **never unpacked into per-field lists** on the way from `pickViaAgent` to the tools — the previous three-list hand-off let a lock be named in one list and forgotten in another, silently falling to a `null` default so the agent path stopped enforcing it while the pool picker still did (#1300 FR 13, `vocalLock`). Do not reintroduce a per-field hand-off. `defineAgent` is generic over its run args so that hand-off is typechecked. Note **`outputSchema` is deliberately absent** on AI SDK tools: in ai@7 it is neither sent to the provider (the spec carries name/description/inputSchema/inputExamples/providerOptions/strict) nor validated on execute — only `validateUIMessages` reads it. `src/mcp/tools.ts` keeps output schemas because there the schema IS the published contract. Pinned by `scripts/picker-lock-forwarding.test.ts` + `scripts/picker-registry.test.ts`. `llm/speech.js` → `internal/speech/cloud-speech.ts` — the `cloud` TTS engine (AI SDK `experimental_generateSpeech` → OpenAI/ElevenLabs). `llm/agent.js` → `internal/agent-factory.ts` (`defineAgent()`).
- **Authored prompt text (`llm/instructions/*.md`)** — the static prose blocks of the agent system prompts, addressed as `instruction(file, section, vars)` (`internal/prompts/instructions.ts`). Sections are `## name` headings; `{placeholder}` substitution follows `renderDjPrompt`'s convention. Everything is parsed and validated **once at module load**, and a missing file/section or an unsubstituted placeholder **throws** — a prompt that ships the literal text `{topic}` to a model is worse than one that fails at boot. Only STATIC blocks live here; the conditional assembly (which blocks apply to this persona/show/run) stays in TS, because it is logic. These are **source, not operator config**: they ship in the image (the controller runs from `src/` via tsx and both Dockerfiles `COPY controller/src`) and are never read from the state dir — the picker prompt is coupled to the harness (`finding-candidates` must agree with `discoverySteps`) and, unlike a skill, a broken one breaks the core loop with no graceful degradation. Operator-facing prompt surfaces stay separate (persona souls, `djHouseRules`, SKILL.md briefs). Pinned verbatim by `scripts/instructions.test.ts`.
- `llm/dj.js` → `internal/prompts/**` (`system`/`context`/`intro-budget`/`request`/`scripts`/`picker`) — the DJ **prompt layer**. Builds prompts and hands them to the strategy primitives: `matchRequest` (structured output, Zod-validated) and `generate*` (intro/link/weather/station-ID/hourly, free text). Each free-text call picks a **random soul** from `settings.dj.souls` + a random narrative angle, on top of an opener-anti-repeat list from `queue.getRecentOpeners()`. Hard rules live in the prompt template — don't loosen without reason.
- `broadcast/session.js` — the **stream session**: the DJ's current run as a `messages` chat history of timestamped turns. Persisted to `state/session.json`; archived on roll. `sessionKeyFor()` derives identity from the active show (`show:<id>`) or time-period+mood (`auto:<period>:<mood>`); `maybeRoll()` hard-rolls on a genuine show boundary or at 4h, while autonomous daypart/mood changes are soft shifts. Prompt memory follows this lifecycle: a hard roll starts clean, a soft shift retains aired turns. The compact hard-roll handoff carries previous show/host/mood identity only — never the previous raw spoken line — and the on-air greeting acknowledges the outgoing presenter by name without receiving their sign-off text. `promptMemory()` also drops the aired sign-off, which the mic-pass stores in the session that just started; `priorPromptMemory()` is the hard roll in-memory snapshot used by post-roll sign-offs; a boundary handoff is generated before the roll and therefore reads the still-live `promptMemory()` instead. `windowMessages()` maps the last ~40 turns to an AI SDK `messages` array; `recover()` resumes on boot if the key still matches.
- `broadcast/dj-agent.js` — the **session DJ agent**: `runTrackEvent` (track started → pick next + maybe a link) and `runRequest` (listener requested X). Posts an event turn, runs a `ToolLoopAgent` over `session.windowMessages()` with `llm/tools.js`, enqueues the output and appends it back as turns. Gated on `settings.llm.pickerAgent` (default **on**); off or on any failure, falls back to the stateless pool picker + `dj.generateLink` / the `/request` matcher — still inside the session, still logged.
- `music/picker.js` — the stateless **pool picker** (dj-agent's fallback). `pickViaPool()` builds a balanced pool from 7 sources (similar-songs, mood-tagged library, mood playlists, recently-added/frequent albums, similar-artist top songs, starred+random), caps/dedupes to ≤18 candidates + last 8 plays, one `djObject` call. Expensive Subsonic calls memoised 30 min.
- `music/prune-policy.ts` — the one answer to "may the orphan reconcile DELETE?", shared by the tagger, the standalone reconcile and the analyzer. `db.pruneMissingTracks` drops a track's row and both its vectors for every id a full walk missed, so the old inline `walked > 0` guard (which only catches a wholly empty walk) is not enough for a source that degrades **partially** — Spotify's pool comes back short from a 403, a rate-limit window or a `maxTracks` cap, and every missing track then looks exactly like one the operator deleted. The source answers for itself via the optional `MusicSource.catalogHealth()`, whose **absence means `complete: true`** so Subsonic reconciles byte-identically; the gate itself fails closed on everything it is told about, including a probe that throws. That asymmetry is the point — do not "unify" the two directions. A skipped prune must always be reported, in the caller's own channel: silence reads as "nothing was orphaned".
- `music/source.js` — the **music-source facade** (upstream #843's seam): every name callers reach for, delegating to the source `settings.music.source` selects (`music/sources/registry.js`); `music/sources/types.js` is the contract, `music/sources/capabilities.js` the per-source table the facade and the picker tools gate on, `music/sources/subsonic.js` the by-reference adapter over the client below. Call sites import the facade (mostly still as `subsonic`), never the client — see `docs/internals/music.md`.
- `music/sources/spotify/` — the Spotify source (experimental): `client.ts` (the only HTTP surface; injected fetch), `map.ts` (pure mappers → Subsonic-child shape), `pool.ts` (the operator's playlists/saved tracks as the station's library), `source.ts` (the `MusicSource`, registered in `sources/registry.ts`), `playback.ts` (device resolution + play/transfer over Spotify Connect), `seam-pure.ts` (every transport decision, pure) and `transport.ts` (the queue's `PlaybackTransport`, started from `server.ts` when the active source has `hasLiveTransport`). Credentials are secrets (`routes/settings/spotify.ts` owns the OAuth connect flow); knobs are `settings.spotify`. **`client.ts` targets the post-February-2026 Web API** and its header comment lists every endpoint the Development Mode restrictions took away — a removed route answers a bare 403 that reads as a permissions fault and is not one, so check that list before "restoring" a call. The consequences that reach other files: `hasTopSongs` is false for spotify (`capabilities.ts`), `unwrapItem` accepts both the `item` and `track` row keys, and an empty pool is held two minutes rather than thirty. **Rate limiting is SHARED STATE, not per request** — a 429 closes one gate every caller reads, and requests come in THREE lanes on one rule (*the gate slows what the station can afford to lose, never what keeps it on air*): `critical: true` = the whole `/me/player/*` block, which bypasses the gate; foreground = catalogue reads, which wait out a short window only; `background: true` = droppable enrichment, abandoned without touching the network while the gate is closed. The critical lane is not optional politeness — without it a 1800s window was thirty minutes of guaranteed silence, since `play()` resolves the device first and `getDevices()` was foreground. The transport already owns that backoff (3s floor + 30s→10min hold), so gating a once-per-track call protects nothing and only delays recovery. Development Mode is permanent here (extended quota is organisations-only, ≥250k MAU), so the fix for a rate limit is always fewer requests, never more retry — which is what the rest of this paragraph is.

**AVAILABILITY IS ONLY KNOWABLE AT PLAY TIME, so it has to be REMEMBERED.** February 2026 took `available_markets` and `/markets` away and the client sends no `market`, so Spotify never fills in `is_playable` and `map.ts`'s flag is `true` for every track the station will ever see — `keep()`'s availability half is inert, and `unplayable-file.ts` is what actually knows. Before it existed the knowledge died with the log line (`onPushResolveFailed` wrote the id nowhere, not even into the log entry's meta bag), and one refused track was picked, commanded and refused **212 times in a row**. The store is applied at exactly three chokepoints and there is no fourth: `keep()` (every list the source returns, so both pick paths and every agent tool inherit it), the pool's two publish points, and `handoff()`/`command()` on the transport — the last because an agent can name an id from its own conversation memory that no tool returned. Entries EXPIRE (30 days): a refusal is a statement about one account's licensing today, and a permanent list would shrink the library for good; `at` is therefore never moved by a repeat, or a track being hammered would postpone its own expiry forever. **The snapshot keeps a row the published pool drops** (`publishable()` / `dropTrack()` / `republish()` in `pool.ts`) — `pool.json` is the only copy of a walk that cost ~100 requests, so making a refusal reversible must not mean re-walking the catalogue; `publishable()` therefore always returns a NEW Map, because handing the walked map back as the published one is the obvious saving and it aliases the two so `dropTrack` deletes from both. **The alternative-release search is FOREGROUND and skipped outright under a hold.** Not `critical` — that is the `/me/player/*` block and nothing else, and an exempt lane may not arm the gate — and not merely left to the foreground lane either, because that lane WAITS a short window out and the wait would land in the seam for a lookup the station can do without. Ten results exactly, so it is one page (`/search` caps `limit` at 10 and `searchPaged` would issue three requests for more); one per queue item (`altTried`); never for a pool fallback, where drawing another pool track is free. `alternative-pure.ts` rejects a candidate that ADDS a performance marker (live/karaoke/remix/…) before it compares titles, so the log says what is actually wrong rather than "different title". The substitute is **re-queued through `pending`, never commanded inline**: `command()` early-returns under the 3s floor and would swallow it — and `resumeNow` is what stops it then waiting out the 15s idle window, since `seamDecision` reads "nothing playing, commanded recently" as "wait for the player", which is wrong once a refusal has told us nothing is coming. Pinned by `scripts/spotify-unplayable.test.ts` plus the refusal block in `spotify-transport.test.ts`.

**A HOLD IS A DEADLINE, SET ONCE PER EPISODE — never moved by a refusal that arrived while the gate was already shut.** This is the single most expensive lesson in the file. `noteRateLimited` used to compute `until = now + Retry-After` on every 429 and keep it whenever it was later, which with a constant header is *always* (the clock moved on), so each refusal slid the wall a full window out. And the `critical` lane bypasses the gate by design, so it kept hitting the network and re-arming the gate for everybody else: with music playing normally a player command every ~100s pinned a 3706-second hold open for a full day, restarts included, because the slid deadline was persisted each time. **An exempt lane may not arm the gate** — `critical` and `operator` refusals are recorded for the operator surface and nothing else, and they never `penalisePacer()` either (the pacer cannot slow them, so it would be steering on a signal it cannot act on; four player 429s took the ceiling to its floor and pinned it there). `wasGated` in `send()` is what enforces all of this: only a request the gate ALLOWED — found it open, or waited a short window out — may say when to stop asking. If Spotify needs longer, the gate opens, one probe is refused, and a new episode starts: self-correcting at the cost of one request. The exempt lanes also never take the post-429 retry, or a player 429 would double the player's rate during exactly the outage that caused it. `MAX_RESTORED_HOLD_MS` refuses to honour an implausible persisted hold across a restart, and `clearHold()` (route + admin button) is the operator's way out — before it existed there was none, and disconnecting Spotify did not help because the client is a process singleton. Pinned by the ratchet test in `scripts/spotify-client.test.ts`.

**`invalidate()` does NOT throw the pool away, and a failed walk never replaces a working library.** It used to null the pool *and* set `snapshotLoaded = true` before attempting anything, which made "Rebuild pool now" a grenade: pressed during a hold it discarded the library, every request was refused, an empty pool was published, and the good snapshot on disk became unreachable for the life of the process — dead air on the emergency loop until a restart. `invalidate()` now only marks a refresh owed (`forceRefresh`) and drops the shared reads; `finish()` keeps the existing pool when a walk comes back empty AND `partial`. The two empty pools are different things and must stay so: an account that genuinely has no playlists still publishes an empty pool with its explanation. An empty pool is also a transport FAILURE now (`commandNext` calls `noteFailure`) — that branch used to return without touching `lastCommandAt`/`failStreak`/`holdUntil`, and since the seam returns `command-next` unconditionally once a track has ended, the 500ms tick drove `pool.get()` at 2 Hz into a full catalogue walk every two minutes: 1,800–4,500 requests/hour, with `logOnce`'s 60s throttle making it look idle.

**The gate is REACTIVE; the pacer is PROACTIVE, and both live in `client.ts`.** The gate only learns a limit by being refused by one. The pacer is a rolling-30s ceiling on non-critical request STARTS (`spotify.quota.requestsPer30s`), so a burst never earns the 429 — it replaced background-only spacing, which left the catalogue walk (the biggest burst there is) completely unspaced. It is **adaptive on purpose**: Spotify publishes no Development Mode figure on either the rate-limit or the quota-modes page, and since **2026-07-23 the quota is counted per DEVELOPER ACCOUNT**, shared with every other app that account owns — so no compiled-in constant can be right. Halve on any 429, ease back ~10% per clean window. **A 429 now comes in two kinds** and they must not be conflated: a quota-exhaustion 429 carries `{"reason":"QUOTA_EXCEEDED"}` and clears on Spotify's schedule (own hold cap, own operator wording), an ordinary window 429 clears in seconds — `MAX_GATE_MS` was sized for the latter and is the wrong bound for the former. **The hold is persisted** through injected sinks (`hold-file.ts`, so `client.ts` keeps no filesystem edge): a restart is exactly when the pool rebuilds, so forgetting the window meant walking the catalogue straight back into it, on a loop under a Docker restart policy.

**The pool is persisted and REVALIDATED, not rebuilt** (`pool-store.ts` + `pool.ts`). `state/spotify/pool.json` holds compact rows — everything `map.ts` derives (`coverArt`, `spotifyUri`, `genre`, `genres`) is stripped and rebuilt on load so those conventions keep one definition — plus each row's `srcPlaylistId` and each playlist's `snapshot_id`. A stale-but-usable pool is **served while it refreshes behind** (`get()` returns it; `settled()` is how you await the refresh), because the station must never wait on Spotify to answer a pick; an EMPTY or wrong-`cfgSig` pool still waits, since neither is an answer. A refresh re-walks only the playlists whose `snapshot_id` moved and probes saved tracks/albums with a one-item `total` + newest-id fingerprint: ~100 requests becomes ~5–25. Spotify's own rate-limit page names `snapshot_id` as the mitigation, and `GET /me/playlists` — already walked — carries it. A full walk still runs on `spotify.pool.fullWalkHours`, tracked by `walkedAt` and **not** `builtAt` (a revalidate moves `builtAt`, so riding the full-walk clock on it would postpone the walk forever). Era suspicion is stamped from the MAPPED rows (`stampEraSuspicion`), which is what lets reused and freshly-walked rows be treated identically. **`fromDisk` is load-bearing**: `catalogHealth()` fails closed on it, because the orphan reconcile deletes the tags, moods and vectors of every track a walk did not yield and a snapshot is by definition a walk from an earlier process.

**The pacer recovers on the CLOCK, not on traffic.** `recoverPacer` used to advance one step and only when a non-critical request happened to be made — and during a hold, by definition, none is. So the ceiling sat at its floor of 10 and then climbed +1 per window, needing ~80 requests to reach 90: throttled by exactly the traffic it was suppressing. It now recovers for every clean window elapsed and is applied whenever the ceiling is READ (`pace()` and `pacerState()`), so a quiet hour recovers in one step. A lowered setting still applies at once — an operator turning it down is not something to climb down to.

**`deviceId()` caches past a track, and remembers a MISS.** At 60s against a ~200s track the cache never hit, so every track paid a fresh `getDevices()` on top of its play — doubling the player lane. And only successes were cached, so while the receiver was down every call re-asked, at the worst possible moment. `DEVICE_CACHE_MS` is 10 min (a device id is stable for a librespot session; a stale one costs one refused play, which `play()` already retries with `force`) and a miss is held `DEVICE_MISS_TTL_MS`. `force` overrides both.

**`spotify.healthPollSec` is GONE.** It was defaulted, clamped, patchable, schema'd and documented — and read by nothing. Implementing it would have added a periodic poll, which is the opposite of what this source needs; the transport already reconciles from librespot's own events. A stored value is now stripped like any other unknown key (`settingsBlockOf` is non-strict), so old backups restore fine.

**Genre enrichment is a paced DRIP, not a per-build burst.** Losing the batch artist read made it the highest-volume call the station makes. **Every repeated catalogue read is memoised, because the per-pick fan-outs were the budget.** `GET /albums/{id}` was cached NOWHERE while the picker's recently-added tool fanned out over five albums per invocation and the pool picker over fourteen — per pick. `/search` is THREE HTTP requests per logical search since February 2026 capped a page at ten, and the picker's retry cascade plus the listener-request matcher reissue the same query constantly. `keyedMemo` (`reads.ts`) is one `memoRead` per key, **bounded** (the key space is the operator's whole catalogue, so an unbounded map is a leak wearing a cache's clothes) and insertion-order evicted. Search paging is capped at 3 pages — every page is a metered request, and a search that has to walk further is not finding anything. Do NOT "fix" this in `llm/internal/tools/picker/tools/search-library.ts`: its cascade is Navidrome-tuned and each branch has a measured reason; the multiplier is in Spotify's adapter, which is where it is now handled.

- `schemas/` — shared zod schemas, the source of truth for validated request/form shapes, mirrored into `web/lib/schemas.generated.ts` (see root `CLAUDE.md`). Import-restricted to `zod` only (and to the ONE form `import { z } from 'zod'` — `gen-schemas.ts` rejects a namespace/default/extra-named zod import rather than rewriting it); stateful rules live in `*-server.ts` siblings. **The mirror is one flat file**, so every top-level name across `schemas/*.ts` shares a single scope *including module-private ones* — the generator throws on a duplicate, naming both files, because the drift check happily passes on a mirror that faithfully reproduces a collision and the failure would otherwise land as a `tsc` error inside a generated file nobody may edit (`scripts/gen-schemas.test.ts`). Names are collected by a real **TypeScript parse**, not a line regex — a MISS is the dangerous direction (the guard can only throw on names it was told about), and a regex missed `export default function f()`, the second declarator of `const A = 1, B = 2`, destructured `const { a } = …` and `export { x as y }`, while also judging nesting by indentation, which is not what nesting is. Export names and `default` count alongside bindings, since the flat file shares one export namespace too. The same parse enforces the zod-only rule: **any statement carrying a module specifier that isn't `'zod'` fails at generate time**, re-exports (`export { x } from './y.js'`) included — those name no `import` keyword, so the earlier line-wise check never saw them, and a non-zod import was copied into the mirror verbatim to fail later in the WEB build, inside the generated file nobody may edit. The eslint rule states the same restriction and is the merge gate; the generator is the half that fires for whoever runs `gen:schemas` first. `middleware/validate.ts` applies the schemas at the route boundary; `settings/validate.ts`'s `validate*Strict` functions apply the same schemas at the persistence chokepoint, and **`settings/normalize.ts`'s lenient `normalize*` functions run them too** — a rule restated in the load path is a rule that can disagree with the save path, and for webhooks the id pattern is the sharp end (the id resolves the redacted `authHeader` sentinel, so a row that changes identity across a save loses its stored secret). Hence `WEBHOOK_ID_RE` is exported rather than module-private, and id minting + collision de-duplication live once in `resolveWebhookIds` (`webhook-server.ts`), shared by both paths. What normalize keeps is only the **leniency**: it repairs or drops a row and never throws, so a hand-edited `settings.json` can't wedge boot — an unknown event name is filtered out rather than failing the row (retiring an event costs a hook its subscription, not the operator's webhook), a malformed id is re-minted, a non-boolean `enabled` falls back to on, and an over-long `authHeader` is clamped, all of which the strict path rejects instead. Pinned by the load-path half of `scripts/schemas.test.ts`. **A `validate*Strict` must `safeParse` and rethrow a plain `Error`, never let a `ZodError` escape** — `update()` is reached by backup restore and `PUT /settings`, which both answer `{ error: err.message }`, and a raw ZodError's `.message` is a ~15-line JSON blob. The readable-string helpers (`firstMessage`, `flattenIssues`) live in `util/zod-error.ts`, neutral ground shared by both call sites: `settings/` must not import `middleware/`. **`firstMessage` prefixes the dotted path unconditionally** — zod's built-in messages name a CONSTRAINT and never a location (`invalid_format` reports the pattern, `too_big` reports the limit), and even a custom message never names the array INDEX, so without the prefix two rows failing the same rule read identically and the operator can't tell which to fix. Don't reintroduce a per-code heuristic: the set of codes carrying field-agnostic messages is open, and the earlier `code !== 'invalid_type'` test silently stopped applying the moment a schema used `.regex()`/`.max()` without a custom message. A `validate*Strict` parsing a BARE array passes its settings key as `firstMessage`'s second arg (`firstMessage(err, 'webhooks')` → `webhooks.0.url: …`) rather than string-prefixing the result, which would read `webhooks: 0.url: …`. `flattenIssues` accumulates into an `Object.create(null)` because field names come from user data — on a `{}` literal a field named `toString` is swallowed by the first-wins guard and a `__proto__` field is dropped outright. The webhook schema is deliberately stricter than the validator it replaced in three spots — `enabled` no longer coerces a non-boolean, `authHeader` no longer truncates at 500 or defaults a non-string, and a malformed `id` no longer silently re-mints — pinned by `scripts/schemas.test.ts`.

- **`feed:` is a MECHANISM, not news' config** (`skills/feed.ts`, #1616). A skill declaring a feed and no `tool.mjs` gets a generated `skill_<name>` tool over it — `resolveFeedConfig` reads the declaration, `makeFeedTool` builds the fetch + burn-on-read dedupe + truncation, and `loader.ts` attaches it in the `else` of the tool.mjs branch. **News takes that path like everything else and ships no `tool.mjs`** — it was the hand-rolled original, and leaving it beside the generic path is the shape the bug had (a field that validated, saved and read back everywhere while reaching the model as nothing at all). Three asymmetries are deliberate: the URL is STRICT (a non-http(s) value warns and yields no tool — silence is what was reported), `feedMaxItems` is LENIENT (a broken count has an obvious right answer, `config.news.maxItems`), and the knobs are declared for every tool.mjs-less skill whether or not a value exists, since the edit sheet is where the first feed gets set. `FEED_ITEMS_PER_FIRE` (6) is news' historical return cap kept for all of them; `feedMaxItems` caps the READ and so lowers it. Dedup memory is per-kind on `segmentState.feedSeen`. A station seeded before this keeps its own `state/skills/news/tool.mjs` and runs it unchanged — `resetBuiltinSkill` removes a `tool.mjs` the template no longer ships, which is the migration. Pinned by `scripts/skill-feed-tool.test.ts`.
- **Feed parsing goes through `fast-xml-parser`** (`skills/feed.ts`, was `skills/news.ts`), not a regex scanner. The feed URL is operator input — any URL typed into a skill's `feed:` field — and the old shallow `<item>` matcher returned ZERO items for Atom (`<entry>`/`<summary>`), RDF/RSS-1.0 (items at the document root, no `<channel>`) or a namespaced tag, which presents as the beat quietly never airing. `removeNSPrefix` collapses the dialects; `parseTagValue: false` keeps a headline of `2026` a string; `parseFeed(xml, cap)` is the pure, network-free seam (`scripts/feed-parse.test.ts`).
- **`state/secrets.env` is read by `dotenv`, through ONE parse** (`setup/secrets.ts` `readSecretsFile`). The file is deliberately hand-editable and holds every cloud API key, so a misread is a wrong SECRET — which surfaces only as a provider 401, pointing nowhere near the file. The splitter it replaced understood `KEY=value` plus one pair of surrounding quotes, so `export KEY=…` was dropped entirely and a trailing `# note` became part of the value. The parse used to exist TWICE (boot path + `saveSecrets`' merge) and the copies must agree by construction: **`saveSecrets` reads then rewrites the whole file**, so a value the merge misreads is a stored secret destroyed on disk, not merely one that fails to load. Reader and writer stay a designed pair — `envEscape` single-quotes anything outside `[A-Za-z0-9_./:@,+\-]` precisely so the reader gets it back verbatim, and refuses a newline outright. Two dotenv behaviours are **warned about rather than silently accepted**: an unquoted `#` truncates the value (correct .env semantics, and the ONE place this swap is less forgiving than the old splitter — the warning names the fix), and a multi-line quoted value is dropped, because `envEscape` cannot persist one and carrying it would make the next save throw on a key the operator never touched. Never reintroduce a second parse. Pinned by `scripts/secrets-env.test.ts`, whose load-bearing case is the save→read round trip.
- **Env vars are read through `util/env.ts`** (`envInt`/`envFloat`/`envUrl`/`envEnum`/`envStr`, zod-backed), never `parseInt(process.env.X || '…')` — that idiom yields **NaN** for anything non-numeric and the NaN then travels (`NEWS_MAX_ITEMS=ten` removed the headline cap, a bad `PORT` bound a random port, a bad `PIPER_SPEED` reached ffmpeg as `atempo=NaN`). The posture is **warn and fall back, never throw**, the same reasoning as the state bootstrap in `docker/broadcast-entrypoint.sh`: a station that refuses to boot over one malformed convenience var is strictly worse than one that boots on the default and says so. Absent and EMPTY both mean "not set" (`ANALYZE_PYTHON=` is an ordinary compose line, not a mistake), so a var whose default names a compose service — `NAVIDROME_URL`, `ANALYZE_URL` — resolves that service rather than switching the feature off. Issues collect in `envIssues()` and `server.ts` repeats them into the booth log, since container stdout is not a surface operators read. `envUrl` parses inside its own predicate rather than chaining `z.url().refine(…)` — zod runs every check even after one fails, so the refine saw unparseable input and `new URL()` threw straight out of the reader, breaking the never-throw contract. Pinned by `scripts/env-config.test.ts`.
- **`helmet` sits above every route** in `server.ts` with three deliberate overrides. `crossOriginResourcePolicy` MUST stay `'cross-origin'`: helmet's `same-origin` default tells the browser to refuse the response to any other origin, which would blank `/cover/:id` artwork, persona avatars and the sfx/jingle/bed previews in every deployment where the player is not same-origin with the controller — exactly what `middleware/cors.ts`'s wide-open `*` exists to allow. CSP is off because no document is served from here (a CSP on JSON or an image is inert; the web app ships its own), and HSTS is off because TLS is not this process's to assert — Cloudflare/Caddy terminate it, and helmet's default carries `includeSubDomains`.
- `config.ts` — single source of truth for env-derived config. Defaults to `localhost`; override every URL via root `.env`. After `settings.load()` + `loadSetupConfig()`, `server.ts` mutates `config.*` to apply persisted values — **env always wins**, settings/wizard fills the gaps.


### Heavy TTS engines (Chatterbox + PocketTTS)

Both are heavy PyTorch engines the controller image deliberately doesn't carry by default. Two modes, **env-switched**: if `TTS_HEAVY_URL` is set, the engine routes `speak()` over HTTP to the sidecar (which writes the WAV onto the shared volume and returns the path); otherwise it spawns a local Python worker over stdio. Both paths must keep working.

- **Sidecar (recommended)**: `subwave-tts-heavy` image, started via `--profile tts-heavy`. Controller wired with `TTS_HEAVY_URL=http://tts-heavy:8080` in all three composes; when the profile is off the URL is unreachable, `isAvailable()` is false, dispatcher falls back to Piper. See `docker/Dockerfile.tts-heavy` + `docker/tts-heavy/server.py` (FastAPI, one asyncio.Lock per engine). Client: `controller/src/audio/ttsHeavyClient.ts` (caches a 30s `/health` probe so `isAvailable()` is synchronous).
- **Legacy in-process** (still supported): `--build-arg WITH_CHATTERBOX=1` / `WITH_POCKETTTS=1` build a venv at `/opt/{chatterbox,pocket-tts}/venv`; workers at `controller/scripts/{chatterbox,pocket_tts}_worker.py`.
- **Shared reference-WAV folder**: clone references live in `config.voices.dir` (default `<STATE_DIR>/voices`, override `TTS_VOICE_DIR`; `CHATTERBOX_VOICE_DIR` honoured for back-compat). `chatterbox.listReferenceVoices()` is the single listing path (`/settings` returns it as both `chatterboxVoices` and `pocketTtsCustomVoices`), and it delegates to the folder's single owner, `audio/voice-library.ts`. That module splits deliberately: **`scan()`** is readdir+stat (what `listReferenceVoices()` and therefore every 3s `/settings` poll uses — never let it spawn a subprocess) and **`list()`** adds ffprobe'd durations for the admin routes only. Operators import clips from `/admin/imaging?tab=voices` (`routes/voices.ts`), stored as mono 24 kHz WAV — note this diverges from `sfx.importAudio`'s no-ffmpeg fallback, because the `.wav` extension is load-bearing twice (`scan()` filters on it; the workers need real WAV bytes), so without ffmpeg a non-wav upload is refused rather than stored raw. There is **no JSON sidecar** (unlike sfx/beds/jingles) precisely because this folder stays operator-writable by hand — a sidecar would carry no entry for a hand-dropped file; durations are memoised on path+size+mtime instead. Clip length is **advisory only** (`voiceWarning()`, 4–20s), never enforced. `:file` route params resolve through `voice-library.resolve()` (basename check + must be present in the real scan) and are never interpolated into a path. Pinned by `scripts/voice-library.test.ts`. Pre-#213 `<STATE_DIR>/chatterbox-voices/` still scanned as fallback. The same folder holds **custom Piper voices** (#230): a `<name>.onnx` + `<name>.onnx.json` pair; `piper.resolvePiperVoice()` resolves a persona's `tts.voice` against it, falling back to the default voice if absent.
- **Chatterbox specifics**: (1) per-request `reference_wav` enables zero-shot cloning (each persona's `tts.voice` is a filename in `config.voices.dir`). (2) Paralinguistic tags (`[laugh]`, `[sigh]`, `[chuckle]`, `[cough]`) render as non-verbal sounds — `llm/internal/prompts/system.ts` (`djSystem`) only mentions them in the system prompt when the on-air engine is `chatterbox` (other engines would speak the literal word). That check runs on the **resolved** slot, not `persona.tts.engine`: a persona on the `inherit` sentinel has no engine of its own, so a raw read drops the hint on exactly the station whose default IS chatterbox.
- **PocketTTS specifics**: kyutai-labs 100M CPU model, ~6× real-time. `tts.voice` accepts a built-in id (`alba`/`anna`/`charles`/`estelle`/`giovanni`/`juergen`/`lola`/`rafael`) OR a `.wav` filename for cloning (#213); `pocketTts.ts:resolveVoice` splits them. The shared worker (`pocket_tts_worker.py`) RMS-normalises then soft-knee limits output, driven hot via `POCKET_TTS_TARGET_RMS` (default `0.245`, env-tunable). One worker file → constants can't drift between modes.
