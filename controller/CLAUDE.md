# CLAUDE.md — `controller/`

Loaded when working under `controller/`. Station-wide architecture lives in the root `CLAUDE.md`.

### Controller (`controller/src/`, ESM Node.js)

Grouped by domain: `server.js`, `config.js`, `settings.js`, `context.js` at the root; everything else under `routes/`, `middleware/`, `music/`, `broadcast/`, `audio/`, `llm/`, `skills/`.

- `server.js` — thin Express entry: applies middleware, mounts routes, runs startup. **`routes/`** splits the API by surface: `public.js` (`/health`, `/now-playing`, `/state`, `/dj`, `/cover/:id`), `request.js` (`POST /request`), `settings.js` (`/settings`, `/restart-mixer`, `/auto-pick`), `jingles.js`, `debug.js`. **`middleware/`** holds `cors.js` (wide open `*`), `auth.js` (the `requireAdmin` Basic-auth gate via `ADMIN_USER`/`ADMIN_PASS`), `ratelimit.js`. **In prod (`NODE_ENV=production`, set by both prod compose files) the gate is mandatory** — the controller exits on boot if `ADMIN_USER`/`ADMIN_PASS` aren't set. Listener-request safety (scripted-opener stripping, verbatim-echo guard, requester-name screening) lives entirely in `util/request-guard.ts` — the one policy chokepoint shared by `request.js`'s `POST /request` and the session DJ agent's request path; `settings.requests` is the gate config (pause toggle, queue depth, per-IP/global rate caps), never inlined at either call site.
- `broadcast/queue.js` — in-memory `upcoming`/`history`/`djLog` + `drainToLiquidsoap()`, the **single writer of `next.txt`** (and request-intro `say.txt` via `tts.speak`). `announce()` is the **single writer of scheduled `say.txt`/`intro.txt`** (picks target by kind: `'link'` → `intro.txt`, else `say.txt`). All track playback goes through `queue.push()`; all spoken segments through `queue.announce()`. Request-intro TTS is written ~250ms before the track URI so Liquidsoap picks up the voice file first.
- **LLM layer (`llm/`)** — every model call goes through the Vercel AI SDK (`ai` package), so the provider is swappable with no call-site change. The eight public modules (`llm/{sdk,provider,dj,agent,tools,segment-tools,speech,log}.js`) are **thin barrels**; the implementation lives under `llm/internal/**`, grouped by concern (`core/`, `provider/`, `strategy/`, `prompts/`, `tools/`, `speech/`, `telemetry/`). Call sites import the stable barrel paths only — never `internal/`.
  - `llm/provider.js` → `internal/provider/**` — `registry.ts` resolves + caches a `LanguageModel` from `settings.llm` (`provider` ∈ ollama | openai-compatible | anthropic | openai | google | deepseek | openrouter | gateway; `model`; optional `apiKey`); `legs.ts` is the primary/fallback legs + reachability probe; `embedding.ts` the embedding models. **`capabilities.ts`** holds the per-provider **capability descriptors** — the single chokepoint translating `settings.llm.reasoning` into each provider's native thinking knob and declaring which providers need the forced-tool object path; strategy code has **no `provider ===` branches**. It also owns the tool-loop's **shape**: `discoverySteps` is how many FREE discovery steps the agent gets before `done` is forced. Forced-tool providers (ollama, openai-compatible, locca) keep **1** — they ignore `toolChoice` with several tools visible and emit schema-valid objects without exploring, so the single cornered call is what holds them; native-strategy providers get **3**. The step cap is **derived** (`gatedMaxStepsFor` = budget + 1), never taken from the caller, which keeps the invariant that the main run makes **exactly ONE forced-`done` attempt** at any budget before handing off to the recovery cascade — extra `done` steps grow an "I already declined" trail and make GLM-class compliance worse. The per-provider budget is **opt-in per agent** (`providerDiscoveryBudget` on the definition — the pick/request agents set it; `runDiscoverySteps` resolves the budget in force): a `djAgent` caller that doesn't opt in keeps the historical single discovery step, because a caller's pinned cap can be load-bearing — the segment director's `maxSteps: 2` (`skills/_agent.ts`) documents a run burning the full `agentTimeoutMs` when its loop silently widened, so the widening must never apply implicitly to every agent on a provider. Clamped to [1, 5]; a zero budget would force `done` at step 0 with an empty `seen` map, where the model could only fabricate an id. **`settings.llm.discoverySteps`** (per-leg, like `toolChoice`/`numCtx`; default `0` = follow the descriptor, `1`–`5` overrides) is the operator lever — the descriptor keys off the PROVIDER and cannot know which MODEL it serves, and the two failure directions are opposite (a capable local model behind openai-compatible wants more than its cautious 1; a wandering cloud model wants fewer than 3). The override is read off the **leg's cfg**, never from settings, so `capabilities.ts` stays a pure function of its argument. Adding it needed the usual THREE edits (`DEFAULTS` + `applyLlmLegPatch` + `load()`'s composition) and is pinned by a **cold-load** round trip, `scripts/llm-discovery-steps.test.ts` — verified to fail 6/9 with the `load()` line removed. `legs.promptDiscoverySteps()` is the figure a PROMPT may promise — the **minimum** across primary and fallback, because the system prompt is built before failover picks a leg and over-promising a second look the model never gets is the expensive direction to be wrong. `ollama` is the homelab default, no key. `openai-compatible` targets self-hosted servers (llama.cpp, vLLM, LM Studio) via `llm.baseUrl` + `/v1/chat/completions`.
  - `llm/sdk.js` → `internal/strategy/**` over `internal/core/**` — three primitives: `djText` (free text), `djObject` (Zod structured output), `djAgent` (a `ToolLoopAgent` tool-loop — the primitive behind `broadcast/dj-agent.js`). `djAgent`'s native-first → done-tool → recovery → **terminal collapse** → text-salvage cascade dispatches off the pure `agentPlan()` (`strategy/plan.ts`). The terminal collapse (#1157) is the last leg before salvage: when a model declines the forced `done` call twice, `renderTerminalPrompt` (`core/pure.ts`) flattens the chat window + the discovery trail into ONE user prompt and asks via `objectViaToolCall`'s forced `emit` tool. **The fix is the conversation SHAPE, not more forcing** — llama.cpp/LM Studio + Hermes-class models return `tool_calls: []` on a terminal `done` step no matter what `tool_choice` says, yet call a forced tool reliably from a single-turn prompt (which is exactly why the stateless pool picker keeps working on the same backend); GLM keeps declining once it has declined in a conversation. Flattening the **trail** into the prompt is load-bearing — it carries the real candidate ids, without which a cornered model can only fabricate one. Leg count is a budget decision too: all legs share ONE deadline (`llm.agentTimeoutMs`, 45s), so an extra leg would never be reached on the slow local rigs that need it most. `core/` is the shared runtime: `pure.ts` (side-effect-free helpers — the unit-test seam, `scripts/llm-pure.test.ts` via `npm run test:llm`), `retry.ts` (transient retry + wall-clock deadline), `failover.ts` (primary→fallback, only on a host-unreachable error — see `isUnreachable`).
  - `llm/log.js` → `internal/telemetry/log.ts` — 120-entry ring buffer of recent calls for `/debug` + durable pick log. `llm/tools.js` + `llm/segment-tools.js` → `internal/tools/**` — `tool()` defs wrapping Subsonic/library discovery (picker) and real-world data (segment director). The picker set is **one file per tool** under `internal/tools/picker/tools/`, each declaring its own `available` gate (a tool offered without its backing index spends the single discovery call on a guaranteed-empty result); `picker/index.ts` is the registry and holds only the order the model sees. Every constraint a pick runs under travels as ONE **`PickerScope`** value (`picker/scope.ts`) that is **never unpacked into per-field lists** on the way from `pickViaAgent` to the tools — the previous three-list hand-off let a lock be named in one list and forgotten in another, silently falling to a `null` default so the agent path stopped enforcing it while the pool picker still did (#1300 FR 13, `vocalLock`). Do not reintroduce a per-field hand-off. `defineAgent` is generic over its run args so that hand-off is typechecked. Note **`outputSchema` is deliberately absent** on AI SDK tools: in ai@7 it is neither sent to the provider (the spec carries name/description/inputSchema/inputExamples/providerOptions/strict) nor validated on execute — only `validateUIMessages` reads it. `src/mcp/tools.ts` keeps output schemas because there the schema IS the published contract. Pinned by `scripts/picker-lock-forwarding.test.ts` + `scripts/picker-registry.test.ts`. `llm/speech.js` → `internal/speech/cloud-speech.ts` — the `cloud` TTS engine (AI SDK `experimental_generateSpeech` → OpenAI/ElevenLabs). `llm/agent.js` → `internal/agent-factory.ts` (`defineAgent()`).
- **Authored prompt text (`llm/instructions/*.md`)** — the static prose blocks of the agent system prompts, addressed as `instruction(file, section, vars)` (`internal/prompts/instructions.ts`). Sections are `## name` headings; `{placeholder}` substitution follows `renderDjPrompt`'s convention. Everything is parsed and validated **once at module load**, and a missing file/section or an unsubstituted placeholder **throws** — a prompt that ships the literal text `{topic}` to a model is worse than one that fails at boot. Only STATIC blocks live here; the conditional assembly (which blocks apply to this persona/show/run) stays in TS, because it is logic. These are **source, not operator config**: they ship in the image (the controller runs from `src/` via tsx and both Dockerfiles `COPY controller/src`) and are never read from the state dir — the picker prompt is coupled to the harness (`finding-candidates` must agree with `discoverySteps`) and, unlike a skill, a broken one breaks the core loop with no graceful degradation. Operator-facing prompt surfaces stay separate (persona souls, `djHouseRules`, SKILL.md briefs). Pinned verbatim by `scripts/instructions.test.ts`.
- `llm/dj.js` → `internal/prompts/**` (`system`/`context`/`intro-budget`/`request`/`scripts`/`picker`) — the DJ **prompt layer**. Builds prompts and hands them to the strategy primitives: `matchRequest` (structured output, Zod-validated) and `generate*` (intro/link/weather/station-ID/hourly, free text). Each free-text call picks a **random soul** from `settings.dj.souls` + a random narrative angle, on top of an opener-anti-repeat list from `queue.getRecentOpeners()`. Hard rules live in the prompt template — don't loosen without reason.
- `broadcast/session.js` — the **stream session**: the DJ's current run as a `messages` chat history of timestamped turns. Persisted to `state/session.json`; archived on roll. `sessionKeyFor()` derives identity from the active show (`show:<id>`) or time-period+mood (`auto:<period>:<mood>`); `maybeRoll()` ends+restarts when that key changes or it ages past 4h. `windowMessages()` maps the last ~40 turns to an AI SDK `messages` array; `recover()` resumes on boot if the key still matches.
- `broadcast/dj-agent.js` — the **session DJ agent**: `runTrackEvent` (track started → pick next + maybe a link) and `runRequest` (listener requested X). Posts an event turn, runs a `ToolLoopAgent` over `session.windowMessages()` with `llm/tools.js`, enqueues the output and appends it back as turns. Gated on `settings.llm.pickerAgent` (default **on**); off or on any failure, falls back to the stateless pool picker + `dj.generateLink` / the `/request` matcher — still inside the session, still logged.
- `music/picker.js` — the stateless **pool picker** (dj-agent's fallback). `pickViaPool()` builds a balanced pool from 7 sources (similar-songs, mood-tagged library, mood playlists, recently-added/frequent albums, similar-artist top songs, starred+random), caps/dedupes to ≤18 candidates + last 8 plays, one `djObject` call. Expensive Subsonic calls memoised 30 min.
- `music/subsonic.js` — Navidrome client, proper Subsonic salt+token MD5 auth (never plaintext). **`getAnnotatedUri(song)`** wraps the URI in `annotate:title=…,artist=…,subsonic_id=…:<uri>` so Liquidsoap reports metadata immediately (not waiting on ID3) and the `on_metadata` hook can recover the song id for `/cover/:id`. Also `getSimilarSongs`, `getArtistInfo`, `getTopSongs`, `getPlaylists`, `getRecentlyAddedAlbums`, `getFrequentAlbums`, `getCoverArtUrl`. **`isStationArchive(song)`** is the guard that keeps SUB/WAVE's own hourly archive mixdowns (path `archive/YYYY-MM-DD/HH-00.mp3`) out of selection/enumeration when a co-located Navidrome scans the archive dir — every song-returning function filters through it, so the picker/tagger/library UI never see junk `HH-00` "tracks" (issue #273). The `state/archive` dir should not be inside the Navidrome music library; the broadcast entrypoint also drops a `.ndignore` there as belt-and-suspenders.
- `settings.js` — durable settings at `/var/sub-wave/settings.json`. Validates+persists; on save also writes the `liquidsoap_*.txt` files. `renderDjPrompt({name, soul, …})` substitutes into the operator template; legacy `dj.soul` string is migrated into `dj.souls[]` on load. **`{name}` is mandatory in the template** — `update()` refuses any custom prompt that drops it. **A new settings field needs THREE edits, not two**: the `DEFAULTS` entry, the `update()` patch handler (`settings/vocab.ts`), and a line in `load()`'s composition for that section. Those section blocks compose explicitly and do **not** spread `DEFAULTS`, so a field missing from `load()` still validates, still saves to `settings.json`, and still works for the rest of that process — then silently vanishes on the next cold load, with the feature reverting to whatever the downstream default is and nothing in the logs. It has bitten twice: `tts.cloud.compatParams` (#1317) and `llm.repeatPenalty` (#918 → #1327, dead on arrival for every restarted controller). Pin new fields with a **cold-load** round trip (`setCache(null)` + `load()`, as in `scripts/llm-repeat-penalty.test.ts`) — an in-process assertion passes on the broken code.
- `schemas/` — shared zod schemas, the source of truth for validated request/form shapes, mirrored into `web/lib/schemas.generated.ts` (see root `CLAUDE.md`). Import-restricted to `zod` only (and to the ONE form `import { z } from 'zod'` — `gen-schemas.ts` rejects a namespace/default/extra-named zod import rather than rewriting it); stateful rules live in `*-server.ts` siblings. **The mirror is one flat file**, so every top-level name across `schemas/*.ts` shares a single scope *including module-private ones* — the generator throws on a duplicate, naming both files, because the drift check happily passes on a mirror that faithfully reproduces a collision and the failure would otherwise land as a `tsc` error inside a generated file nobody may edit (`scripts/gen-schemas.test.ts`). Names are collected by a real **TypeScript parse**, not a line regex — a MISS is the dangerous direction (the guard can only throw on names it was told about), and a regex missed `export default function f()`, the second declarator of `const A = 1, B = 2`, destructured `const { a } = …` and `export { x as y }`, while also judging nesting by indentation, which is not what nesting is. Export names and `default` count alongside bindings, since the flat file shares one export namespace too. The same parse enforces the zod-only rule: **any statement carrying a module specifier that isn't `'zod'` fails at generate time**, re-exports (`export { x } from './y.js'`) included — those name no `import` keyword, so the earlier line-wise check never saw them, and a non-zod import was copied into the mirror verbatim to fail later in the WEB build, inside the generated file nobody may edit. The eslint rule states the same restriction and is the merge gate; the generator is the half that fires for whoever runs `gen:schemas` first. `middleware/validate.ts` applies the schemas at the route boundary; `settings/validate.ts`'s `validate*Strict` functions apply the same schemas at the persistence chokepoint, and **`settings/normalize.ts`'s lenient `normalize*` functions run them too** — a rule restated in the load path is a rule that can disagree with the save path, and for webhooks the id pattern is the sharp end (the id resolves the redacted `authHeader` sentinel, so a row that changes identity across a save loses its stored secret). Hence `WEBHOOK_ID_RE` is exported rather than module-private, and id minting + collision de-duplication live once in `resolveWebhookIds` (`webhook-server.ts`), shared by both paths. What normalize keeps is only the **leniency**: it repairs or drops a row and never throws, so a hand-edited `settings.json` can't wedge boot — an unknown event name is filtered out rather than failing the row (retiring an event costs a hook its subscription, not the operator's webhook), a malformed id is re-minted, a non-boolean `enabled` falls back to on, and an over-long `authHeader` is clamped, all of which the strict path rejects instead. Pinned by the load-path half of `scripts/schemas.test.ts`. **A `validate*Strict` must `safeParse` and rethrow a plain `Error`, never let a `ZodError` escape** — `update()` is reached by backup restore and `PUT /settings`, which both answer `{ error: err.message }`, and a raw ZodError's `.message` is a ~15-line JSON blob. The readable-string helpers (`firstMessage`, `flattenIssues`) live in `util/zod-error.ts`, neutral ground shared by both call sites: `settings/` must not import `middleware/`. **`firstMessage` prefixes the dotted path unconditionally** — zod's built-in messages name a CONSTRAINT and never a location (`invalid_format` reports the pattern, `too_big` reports the limit), and even a custom message never names the array INDEX, so without the prefix two rows failing the same rule read identically and the operator can't tell which to fix. Don't reintroduce a per-code heuristic: the set of codes carrying field-agnostic messages is open, and the earlier `code !== 'invalid_type'` test silently stopped applying the moment a schema used `.regex()`/`.max()` without a custom message. A `validate*Strict` parsing a BARE array passes its settings key as `firstMessage`'s second arg (`firstMessage(err, 'webhooks')` → `webhooks.0.url: …`) rather than string-prefixing the result, which would read `webhooks: 0.url: …`. `flattenIssues` accumulates into an `Object.create(null)` because field names come from user data — on a `{}` literal a field named `toString` is swallowed by the first-wins guard and a `__proto__` field is dropped outright. The webhook schema is deliberately stricter than the validator it replaced in three spots — `enabled` no longer coerces a non-boolean, `authHeader` no longer truncates at 500 or defaults a non-string, and a malformed `id` no longer silently re-mints — pinned by `scripts/schemas.test.ts`.
- `audio/tts.js` — engine dispatcher across `piper`, `kokoro`, `chatterbox`, `pocket-tts`, `cloud`. Per-kind override (`settings.tts.byKind`) falls through to `settings.tts.defaultEngine` (default `piper`). On any failure falls back so the DJ never goes silent: the operator's configured rescue voice (`settings.tts.fallback`, engine + voice, default off) then `defaultEngine` → `piper` → `kokoro`, ordered by the pure `audio/tts-fallback.ts`. `resolveEngine()` returns a **slot** (`{engine, personaTts}`) rather than an engine id, because a reroute can now carry the operator's chosen voice; `speakWith()` consumes that slot as a synthetic persona, the same trick `synthesizeSample()` uses for previews. **All callers go through `tts.speak(text, {kind})`** — never the engine modules directly. The `{engine, voice, cloudProvider}` slot shape is shared with every persona's `tts` block, and so are its validators — `validateTtsBlock()` / `normalizeTts()` (`settings/{validate,normalize}.ts`) are the one place the per-engine voice rules live, on both the controller and (via `tts/EngineVoiceFields.tsx`) the admin UI.
- `audio/piper.js` — Piper CLI, WAV to `config.piper.outDir`, cleans files >1h. Fast (~30ms/word). `audio/kokoro.js` — persistent Python worker (`controller/scripts/kokoro_worker.py`) holding the kokoro-onnx model resident; slower (~300–800ms/line CPU) but more natural. `isAvailable()` short-circuits the fallback chain if the venv/model is absent.
- `context.js` — `getFullContext()` → `{ time, weather, festival, dominantMood }`. **`dominantMood` priority is festival > weather > time** — what `refreshAutoPlaylist` and the picker key off. Open-Meteo cached 30 min; festivals settings-backed (`settings.festivals`, admin-editable, seeded from `FESTIVAL_DEFAULTS` in `settings.ts`; fixed month/day schema, so lunar holidays need per-year entries).
- `broadcast/scheduler.js` — node-cron. Auto-playlist refresh every `autoQueueRefreshMinutes` (default 60). Ticks fire at the most aggressive cadence (`:00/:15/:30/:45`); `shouldFire(kind)` (`broadcast/dj-gate.js`) gates each handler on `settings.dj.frequency` (quiet/moderate/aggressive). Weather only announces on condition change.
- `skills/` — between-track segment capabilities. `skills/_agent.js` holds the `CAPABILITIES` table (the 7 built-ins: weather, news, traffic, curiosity, album-anniversary, library-deep-cut, web-search) and the segment-director agent. `skills/loader.js` loads operator skills from `state/skills/<slug>/SKILL.md`; a file **named after a built-in kind** (`BUILTIN_KINDS`) is an **override** of that built-in's brief/cooldown/label rather than a new skill — merged over `CAPABILITIES` by `builtinCapabilities()`. **Operator knobs are declared by the skill, never by the route**: a `tool.mjs` may export `configFields` (`skills/config-fields.ts` — parse/read/coerce, all pure, pinned by `scripts/skill-config-fields.test.ts`), whose values live in that skill's OWN frontmatter and reach it as the tool's 4th arg. News' `feed`/`feedMaxItems` are just the first two; the gate used to be `isNews: kind === 'news'` in `routes/dj.ts`, which meant a renamed copy of News had no way to set a feed (#1300). Since the declaration rides in `tool.mjs`, a duplicate keeps its form by construction. `writeSkillFile` **rewrites SKILL.md from typed fields**, so it also carries through every frontmatter key it doesn't own (`preservedFrontmatter`) — that is what keeps a hand-authored knob, or a declared one whose `tool.mjs` currently fails to import, from being deleted by the operator's next save. `skills/scaffold.js` writes editable `state/skills/<kind>/SKILL.md` files for all 7 built-ins on first boot (idempotent; news `feed:` seeded from `NEWS_FEED_URL` or BBC, **file wins after first boot**). Edit them via `/admin/skills` (`GET`/`PUT /dj/skills/:kind/file`) or on disk + Rescan. Data tools stay keyed by `kind` in `llm/segment-tools.js`. **A forced run may stand down**: `skills/abstain-policy.ts` is the single chokepoint deciding whether a skill speaking from fetched data must stay silent when that data comes back `{ available: false }` or errored (#1412). The three forced callers — Run now, the per-skill cron, the programme feature beat — each hear the same `{ aired: false, reason }` and answer it differently (operator sees why, cron logs it, programme falls to straight talk); `runCapability` logs the one stand-down line so the wording can't drift between them. The autonomous pool path applies the same decision before `generateSegment` (#1446), logs the selected skill's pre-LLM skip, and backs an unavailable skill off in memory for the shorter of its configured cooldown or 15 minutes; successful-air cooldowns stay separate. The default is keyed **by kind in code, not read from the skill's files**, because `state/skills` is seeded once and never re-seeded — a declaration shipped in a new image never reaches an upgraded station, which is precisely the install the fix is for. `requiresData` (tool.mjs export, or an operator frontmatter line that outranks it) overrides per skill; `curiosity` is the shipped exemption, since its `{ available: false }` is the designed hand-off to free generation. In agent mode the check runs on what the tool actually returned (`buildSegmentTools`' `onResult`), not only on what the prompt asked for — a model told not to invent and inventing anyway is the bug being fixed. Pinned by `scripts/skill-abstain.test.ts`. See `docs/custom-skills.md`. Backed by `searchWeb()` in `skills/web-search.ts`, with four provider options selectable in the admin UI: DuckDuckGo (default, free, sparse), Tavily (paid, rich results, needs `SEARCH_API_KEY`), Brave Search (metered, $5/mo free credits, shares `SEARCH_API_KEY`), and SearXNG (self-hosted meta-search, needs only a base URL).
- `broadcast/liquidsoap-control.js` — telnet to Liquidsoap port 1234, custom `restart` command (`shutdown()` + restart policy brings it back ~3s later with new `liquidsoap_*.txt` values).
- `music/library.js` / `music/tag-library.js` — `moods.json` store + resumable standalone tagger (`npm run tag [-- --limit N]`, saves every 25). `broadcast/jingles.js` — pre-rendered TTS stinger management (WAVs into `${STATE_DIR}/jingles/`, rewrites `jingles.m3u`/`jingles.json`; `default-id` protected from deletion). It has **two air paths**: the `jingles.m3u` rotate that Liquidsoap draws from on its own, and the on-demand `POST /jingles/:filename/play` → `queue.playJingle` → `jingleUri` → `jingle-now.txt`, drained into a dedicated priority queue. That queue wraps both `dj_queue` and the automatic rotate, so an existing pick cannot delay the press; `source.available` preserves it until voice and bed gates clear, then it wins the next safe boundary. The on-demand path is the one to reach for when a clip is longer than a stinger: `/sfx/:name/play` mixes UNDER the programme at 0.7 gain with a light duck, which is what `SFX_MAX_SEC` (10s) exists to bound, whereas a jingle is its own full-level item with no cap. Manual trigger, so it ignores `jingleRatio` like every explicit operator press. Presses are **de-duplicated, not rate-limited**: that priority queue is a FIFO with no remove path (`dj_queue` has `cancelQueued`; this has nothing) and the fallback keeps selecting it while it is non-empty, so a retried tool call or a double-clicked button airs the same announcement twice with no way back short of `/restart-mixer`. A repeat of a jingle that is still pending answers **409**; two *different* announcements queue normally, because an explicit operator action always fires. Pending entries retire when the marker reports the clip aired, and expire on their own — a mixer restart empties the queue silently, and that must never wedge the button shut. `broadcast/tagger.js` tracks the background tagger child process.
- **SKILL.md frontmatter is real YAML** (`skills/loader.ts` `parseFrontmatter`, via the `yaml` package), but `data` stays a flat `Record<string, string>` — the tool's 4th `config` arg, `config-fields` coercion, `preservedFrontmatter` and `parseTags` are all built on strings, and lists flatten to the comma-joined form those already accept (so `tags: [a, b]` and `tags: a, b` are the same thing); nested maps have no consumer and are dropped. **A block YAML refuses falls back to the legacy line parser** and reports `malformed` so `loadSkillDir` can warn — the sharp case is an unquoted colon (`label: News: Today`), which the pre-YAML parser accepted and is therefore on operators' disks today; a skill must not vanish at boot over it. The writer is the other half of one round trip: `writeSkillFile`'s `yamlScalar` (`skills/scaffold.ts`) quotes a value **only when it would not survive being emitted bare**, and it tests that by actually round-tripping it rather than by a dangerous-character list — `6` needs no quotes (it parses as a number and the loader flattens it straight back to `"6"`) while `007` does. Being minimal there is not cosmetic: this rewrites files operators hand-edit, so quoting values that never needed it would churn every SKILL.md on the first save after an upgrade. Pinned by `scripts/skill-frontmatter.test.ts` + the round-trip block in `scripts/skill-scaffold-preserve.test.ts`.
- **Feed parsing goes through `fast-xml-parser`** (`skills/news.ts`), not a regex scanner. The feed URL is operator input — any URL typed into the news skill's `feed:` field — and the old shallow `<item>` matcher returned ZERO items for Atom (`<entry>`/`<summary>`), RDF/RSS-1.0 (items at the document root, no `<channel>`) or a namespaced tag, which presents as the news beat quietly never airing. `removeNSPrefix` collapses the dialects; `parseTagValue: false` keeps a headline of `2026` a string; `parseFeed(xml, cap)` is the pure, network-free seam (`scripts/news-feed.test.ts`).
- **`state/secrets.env` is read by `dotenv`, through ONE parse** (`setup/secrets.ts` `readSecretsFile`). The file is deliberately hand-editable and holds every cloud API key, so a misread is a wrong SECRET — which surfaces only as a provider 401, pointing nowhere near the file. The splitter it replaced understood `KEY=value` plus one pair of surrounding quotes, so `export KEY=…` was dropped entirely and a trailing `# note` became part of the value. The parse used to exist TWICE (boot path + `saveSecrets`' merge) and the copies must agree by construction: **`saveSecrets` reads then rewrites the whole file**, so a value the merge misreads is a stored secret destroyed on disk, not merely one that fails to load. Reader and writer stay a designed pair — `envEscape` single-quotes anything outside `[A-Za-z0-9_./:@,+\-]` precisely so the reader gets it back verbatim, and refuses a newline outright. Two dotenv behaviours are **warned about rather than silently accepted**: an unquoted `#` truncates the value (correct .env semantics, and the ONE place this swap is less forgiving than the old splitter — the warning names the fix), and a multi-line quoted value is dropped, because `envEscape` cannot persist one and carrying it would make the next save throw on a key the operator never touched. Never reintroduce a second parse. Pinned by `scripts/secrets-env.test.ts`, whose load-bearing case is the save→read round trip.
- **Env vars are read through `util/env.ts`** (`envInt`/`envFloat`/`envUrl`/`envEnum`/`envStr`, zod-backed), never `parseInt(process.env.X || '…')` — that idiom yields **NaN** for anything non-numeric and the NaN then travels (`NEWS_MAX_ITEMS=ten` removed the headline cap, a bad `PORT` bound a random port, a bad `PIPER_SPEED` reached ffmpeg as `atempo=NaN`). The posture is **warn and fall back, never throw**, the same reasoning as the state bootstrap in `docker/broadcast-entrypoint.sh`: a station that refuses to boot over one malformed convenience var is strictly worse than one that boots on the default and says so. Absent and EMPTY both mean "not set" (`ANALYZE_URL=` is an ordinary compose line, not a mistake). Issues collect in `envIssues()` and `server.ts` repeats them into the booth log, since container stdout is not a surface operators read. `envUrl` parses inside its own predicate rather than chaining `z.url().refine(…)` — zod runs every check even after one fails, so the refine saw unparseable input and `new URL()` threw straight out of the reader, breaking the never-throw contract. Pinned by `scripts/env-config.test.ts`.
- **`helmet` sits above every route** in `server.ts` with three deliberate overrides. `crossOriginResourcePolicy` MUST stay `'cross-origin'`: helmet's `same-origin` default tells the browser to refuse the response to any other origin, which would blank `/cover/:id` artwork, persona avatars and the sfx/jingle/bed previews in every deployment where the player is not same-origin with the controller — exactly what `middleware/cors.ts`'s wide-open `*` exists to allow. CSP is off because no document is served from here (a CSP on JSON or an image is inert; the web app ships its own), and HSTS is off because TLS is not this process's to assert — Cloudflare/Caddy terminate it, and helmet's default carries `includeSubDomains`.
- `config.ts` — single source of truth for env-derived config. Defaults to `localhost`; override every URL via root `.env`. After `settings.load()` + `loadSetupConfig()`, `server.ts` mutates `config.*` to apply persisted values — **env always wins**, settings/wizard fills the gaps.


### Heavy TTS engines (Chatterbox + PocketTTS)

Both are heavy PyTorch engines the controller image deliberately doesn't carry by default. Two modes, **env-switched**: if `TTS_HEAVY_URL` is set, the engine routes `speak()` over HTTP to the sidecar (which writes the WAV onto the shared volume and returns the path); otherwise it spawns a local Python worker over stdio. Both paths must keep working.

- **Sidecar (recommended)**: `subwave-tts-heavy` image, started via `--profile tts-heavy`. Controller wired with `TTS_HEAVY_URL=http://tts-heavy:8080` in all three composes; when the profile is off the URL is unreachable, `isAvailable()` is false, dispatcher falls back to Piper. See `docker/Dockerfile.tts-heavy` + `docker/tts-heavy/server.py` (FastAPI, one asyncio.Lock per engine). Client: `controller/src/audio/ttsHeavyClient.ts` (caches a 30s `/health` probe so `isAvailable()` is synchronous).
- **Legacy in-process** (still supported): `--build-arg WITH_CHATTERBOX=1` / `WITH_POCKETTTS=1` build a venv at `/opt/{chatterbox,pocket-tts}/venv`; workers at `controller/scripts/{chatterbox,pocket_tts}_worker.py`.
- **Shared reference-WAV folder**: clone references live in `config.voices.dir` (default `<STATE_DIR>/voices`, override `TTS_VOICE_DIR`; `CHATTERBOX_VOICE_DIR` honoured for back-compat). `chatterbox.listReferenceVoices()` is the single listing path (`/settings` returns it as both `chatterboxVoices` and `pocketTtsCustomVoices`), and it delegates to the folder's single owner, `audio/voice-library.ts`. That module splits deliberately: **`scan()`** is readdir+stat (what `listReferenceVoices()` and therefore every 3s `/settings` poll uses — never let it spawn a subprocess) and **`list()`** adds ffprobe'd durations for the admin routes only. Operators import clips from `/admin/imaging?tab=voices` (`routes/voices.ts`), stored as mono 24 kHz WAV — note this diverges from `sfx.importAudio`'s no-ffmpeg fallback, because the `.wav` extension is load-bearing twice (`scan()` filters on it; the workers need real WAV bytes), so without ffmpeg a non-wav upload is refused rather than stored raw. There is **no JSON sidecar** (unlike sfx/beds/jingles) precisely because this folder stays operator-writable by hand — a sidecar would carry no entry for a hand-dropped file; durations are memoised on path+size+mtime instead. Clip length is **advisory only** (`voiceWarning()`, 4–20s), never enforced. `:file` route params resolve through `voice-library.resolve()` (basename check + must be present in the real scan) and are never interpolated into a path. Pinned by `scripts/voice-library.test.ts`. Pre-#213 `<STATE_DIR>/chatterbox-voices/` still scanned as fallback. The same folder holds **custom Piper voices** (#230): a `<name>.onnx` + `<name>.onnx.json` pair; `piper.resolvePiperVoice()` resolves a persona's `tts.voice` against it, falling back to the default voice if absent.
- **Chatterbox specifics**: (1) per-request `reference_wav` enables zero-shot cloning (each persona's `tts.voice` is a filename in `config.voices.dir`). (2) Paralinguistic tags (`[laugh]`, `[sigh]`, `[chuckle]`, `[cough]`) render as non-verbal sounds — `llm/internal/prompts/system.ts` (`djSystem`) only mentions them in the system prompt when the on-air engine is `chatterbox` (other engines would speak the literal word).
- **PocketTTS specifics**: kyutai-labs 100M CPU model, ~6× real-time. `tts.voice` accepts a built-in id (`alba`/`anna`/`charles`/`estelle`/`giovanni`/`juergen`/`lola`/`rafael`) OR a `.wav` filename for cloning (#213); `pocketTts.ts:resolveVoice` splits them. The shared worker (`pocket_tts_worker.py`) RMS-normalises then soft-knee limits output, driven hot via `POCKET_TTS_TARGET_RMS` (default `0.245`, env-tunable). One worker file → constants can't drift between modes.
